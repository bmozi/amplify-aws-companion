# Amplify capability atlas: choose a promise before a product

**Research checkpoint: October 19, 2026.** This is a reader's decision map, not an inventory of live AWS resources or a promise that every catalog item works in this account. Recheck the linked AWS documentation, Region, account eligibility, service lifecycle and price when starting an exercise.

Imagine a bakery. Its first promise is simple: anyone can read today's menu. A published static page can fulfill it. Next month the bakery promises each customer a private order history. Now it needs an identity, a durable record and an authorization rule. A reusable sign-in screen makes the interface easier to build, but it cannot make an order private by itself. This is why [AWS calls Amplify four independent parts](https://docs.amplify.aws/react/how-amplify-works/), rather than one switch to turn on.

| Amplify part | ELI5 job | What it can do without the other parts | Field Lab source and ownership |
| --- | --- | --- | --- |
| Hosting | Put the built website where visitors can get it | Serve a static site with no Amplify backend | Terraform declares a **managed Amplify Hosting** app and `lab` branch in [`infra/hosting/main.tf`](../infra/hosting/main.tf); automatic branch builds are off. AWS also documents a separate preview self-managed hosting route; it is not declared here |
| Backend | Specify and provision the back room | Create selected AWS resources without using Amplify Hosting | Gen 2 [`app/amplify/backend.ts`](../app/amplify/backend.ts) declares auth, data, storage and `inspect`; its stacks are managed through CloudFormation |
| Frontend Libraries | Give browser/mobile code configured ways to call services | [Connect to existing AWS resources](https://docs.amplify.aws/javascript/frontend/) managed by another infrastructure tool | [`app/src/main.tsx`](../app/src/main.tsx) configures generated outputs and calls the selected categories |
| UI Libraries | Provide reusable visible components | Supply an interface independently of whether an actual backend is available | The Field Lab uses `Authenticator`; its appearance alone does not prove sign-in succeeds |

“Available in Amplify” means **a supported development path to investigate**. “Declared in source” means a recipe exists. “Provisioned” needs a current AWS inventory. “Working” needs a customer-path test, including a denied unauthorized path where privacy matters. Those are four different statements. The [reader playbook](FIELD-LAB-READER-PLAYBOOK.md) explains the checks and summarizes an earlier bounded case; its detailed owner receipt is separate. This atlas made no fresh AWS call.

## Choose a capability by the changed customer promise

The [current Gen 2 backend catalog](https://docs.amplify.aws/react/build-a-backend/) and [JavaScript frontend catalog](https://docs.amplify.aws/javascript/frontend/) contain more than this lab uses. The rows group a large menu by the job the customer needs. They are not an instruction to deploy all of it.

| Customer promise or problem | Candidate path | Current lab status | New proof and meter to check |
| --- | --- | --- | --- |
| Visitors can read the menu | Hosting: static artifact, branch, route and optional custom domain | Hosting app/branch **declared** in Terraform; manual publication is separate | Served revision and deep-link load; build minutes, stored site bytes and transfer; DNS/domain costs if added |
| A server must use a private key without giving it to visitors | Keep public client configuration separate from a Gen 2 function secret reference | [Local two-build lesson](../examples/amplify-secret-boundary/README.md) demonstrates what Vite serves; no new cloud secret is provisioned | Inspect the built artifact and served response, then verify the function only returns approved data; count Secrets Manager/API/function/log usage |
| A developer needs a disposable backend while editing locally | Gen 2 **cloud sandbox** plus generated client outputs | **Not created for this lesson**; the recorded lab uses its existing deployed branch backend | Exact sandbox stack, test-data lifecycle and denied API path; underlying Auth/Data/Storage/function/log meters and verified deletion |
| A team needs direct control of its CDN and hosting resources | Preview self-managed hosting: `defineHosting()` and `ampx deploy` synthesize customer-owned CDK stacks for S3, CloudFront and selected compute | **Design-only alternative**; no `@aws-amplify/hosting` package, hosting stack or self-managed pipeline is installed here | Preview suitability and exact generated resources; scoped deploy identity, S3/CloudFront/compute, logs/alarms/WAF/CI costs, retained stacks and teardown |
| Only this customer can see this order | Auth + Data + configured client calls; sign-in UI optional | Cognito and AppSync/DynamoDB **declared**; owner rule in source | Owner read/write **and** unrelated-user API denial; auth/API/data usage and retained records |
| Customers can attach a private photo | Storage + identity-scoped path and file-handling policy | S3 storage **declared** | Cross-user file denial, size/content handling, retention and deletion; stored bytes, requests and transfer |
| A server must validate or transform text | Function called from an authorized API route | `inspect` Lambda **declared**; it counts words, not AI | Handler-side rejection, logs and bounded retry; invocations, duration, logs and dependent services |
| Updates should appear without refresh | Data subscriptions or another real-time path | Data client uses `observeQuery`; no general PubSub system is declared | Two-session update and authorization under reconnect; message/API usage and connections |
| Each change should have a preview | Hosting branches and PR previews | **Not declared** for this lab | Branch isolation, artifacts, teardown; additional builds/storage/transfer and any backend copies |
| A shared web team serves apps whose backends belong to separate accounts | Managed Hosting plus a reviewed cross-account Gen 2 backend pipeline and environment-specific generated outputs | **Design only**; this personal-account lab has no cross-account trust or second account. See the [four changed cases](../examples/amplify-cross-account/README.md) | Target account/Region/role, deployed backend, final browser destination and allowed/denied requests; separate Hosting and backend bills and teardown owners |
| Pages must render on a server | Supported SSR hosting/runtime plus compatible app design | **Not this static manual-upload lab**; see the [mode decision lesson and cases](../examples/amplify-hosting-modes/README.md) | First-response behavior, server authority, cache, rollback and supported release path; SSR requests/duration, transfer, storage and builds |
| The app needs maps or place search | Geo / Amazon Location path | **Not declared** | Allowed place data, map/search behavior and usage; location requests and transfer |
| The app needs a tailored AI conversation | AI Kit conversation route, or a separately designed model/API path if its current authorization limits do not fit | **Not declared**; `inspect` is deterministic; [AI-route lesson and cases](../examples/amplify-ai-route/README.md) are design-only | Model/Region access, per-order data authority, history retention, quality and safety tests; model calls/tokens and supporting AppSync/Lambda/DynamoDB/log resources |
| A team needs REST or a special AWS service | REST API, custom CDK resource, or existing Terraform-owned service connected to Amplify libraries | **Not declared** as a separate REST API | Endpoint auth, IAM, schema and owner; API plus every underlying service meter |
| The app needs signed-in device registration for push | Current Amplify `defineNotifications()` path backed by Amazon Connect Customer Profiles and an End User Messaging push application | **Not declared**; [three-route choice](../examples/notification-evidence/ROUTE-CHOICE.md) is design-only | Auth, consent, APNs/FCM secrets, generated resources and registration proof; Connect/profile, push and supporting meters |
| The app needs one direct push to a known recipient | AWS End User Messaging direct send with an application-owned consent and device route | **Not declared** | Authorized recipient, send/provider result and separate customer observation; sending, events and logs |
| The app needs analytics or a private in-app offer | Design event streaming separately; build an authorized Auth/Data page for the offer if that meets the promise | **Not declared**; neither is an automatic Pinpoint migration | Event destination, page authorization and customer observation; stream, API, data, hosting and logs |
| The app needs another catalog category | Investigate Predictions, Interactions or PubSub against current provider lifecycle and the precise outcome | **Not declared** | Selected service, authority, behavior and current price rather than a catalog label |
| A backend capability should run locally before AWS | [AWS Blocks preview with Gen 2](https://docs.amplify.aws/react/build-a-backend/aws-blocks/), if its current integration fits | **Not installed or declared**; [five changed cases](../examples/amplify-blocks-boundary/README.md) are cloud-free | Local behavior, explicit method authorization, integration owner and generated infrastructure; inspect the block's deployed AWS resources and prices before a cloud run |

The last row is an extension choice, not a fifth mandatory Amplify pillar. Likewise, a client SDK or UI component does not pay for, create or authorize the backend it calls. [AWS's Amplify price page](https://aws.amazon.com/amplify/pricing/) separates Hosting build, storage, transfer and SSR meters from the underlying Cognito, AppSync, DynamoDB, Lambda and S3 meters. A zero-price interface component is not a zero-cost application. Do not copy a published free-tier allowance into a personal estimate without checking account eligibility and current usage.

AWS Blocks is currently a **separately published preview extension**. Its [Amplify integration](https://docs.amplify.aws/react/build-a-backend/aws-blocks/how-it-works/) adds a nested CDK stack to the Gen 2 backend, sends its API URL through `amplify_outputs.json`, and can reuse the Amplify Cognito pool for protected methods. Local memory/filesystem behavior needs no account; the AWS path adds an API, Lambda and selected resources. Methods in the backend-only scaffold are public unless their code calls an auth check. The [illustrated lesson](../reader/BOOK-LOCATORS.md#book-6dda7767ab0d34a9) and [changed-case packet](../examples/amplify-blocks-boundary/README.md) keep those paths separate. An isolated October 21 local scaffold answered one public greeting and reported 31 affected package entries at install; it did not become this lab's dependency or validate the Gen 2 integration. Treat version, authorization, generated resources and full cost as fresh adoption questions.

A cloud sandbox is still an AWS deployment. The [illustrated sandbox/branch/preview lesson](../reader/BOOK-LOCATORS.md#book-1b66ea0493099d51) and [six changed environment cases](../examples/amplify-environments/README.md) make the lifecycle visible. Generating outputs for an existing branch only reads its client configuration; it is not a backend deploy or proof that a preview has separate data. Stopping a local watcher is not deletion evidence. [AWS sandbox setup](https://docs.amplify.aws/react/deploy-and-host/sandbox-environments/setup/), [custom pipelines](https://docs.amplify.aws/react/deploy-and-host/amplify-hosting/custom-pipelines/), [branch sharing](https://docs.amplify.aws/react/deploy-and-host/amplify-hosting/share-resources/).

The [read-only outputs inspector](../examples/environment-boundary/README.md#inspect-a-real-local-address-book-without-publishing-its-identifiers) compares the actual local Gen 2 configuration with another file or a separately reviewed SHA-256 without printing selected backend identifiers. The existing local Field Lab file parsed with Auth, Data and Storage in one Region and unauthenticated identities disabled. That is local client-configuration evidence only; no current AWS resource, branch binding, effective permission, served-browser destination or cost was checked. The companion's fictional wrong-backend cases and the real-file inspector teach complementary boundaries.

AWS's [deployment overview](https://docs.amplify.aws/react/deploy-and-host/) now separates managed Amplify Hosting from [preview self-managed hosting](https://docs.amplify.aws/react/deploy-and-host/self-hosting/). The latter is not recommended for production yet. It uses `defineHosting()` to create account-owned resources and can deploy through `ampx deploy`, an optional CodePipeline or external CI. That is a different ownership, IAM, cost and off-switch review from this lab's manual Amplify Hosting API. The [illustrated three-route lesson](../reader/BOOK-LOCATORS.md#book-7f3911d418d814d9) and [changed cases](../examples/amplify-hosting-modes/README.md#change-who-owns-hosting) keep these paths separate. A self-managed design must price its selected AWS services rather than reuse this lab's managed Hosting worksheet.

The [fictional self-managed cost lab](../examples/costs/self-managed-hosting/README.md) adds an explicit inventory for S3/CloudFront, default monitoring/SNS, selected WAF/domain/logging/SSR/pipeline paths, backend and retention. Its passing invented arithmetic is not a current account estimate or live authorization.

For AI Kit, first choose the request shape. The current [Amplify architecture guide](https://docs.amplify.aws/react/ai/concepts/architecture/) distinguishes one-request generation from stored multi-turn conversation, and the [setup guide](https://docs.amplify.aws/react/ai/set-up-ai/) documents different route-authorization limits. Read the [illustrated lesson](../reader/BOOK-LOCATORS.md#book-9c1c5544f5e73527) before treating a sign-in widget as permission to read a particular order. The [Knowledge Base example](https://docs.amplify.aws/react/frontend/ai/conversation/knowledge-base/) warns that default OpenSearch Serverless infrastructure has a continuing idle cost. AI Kit and retrieval remain unprovisioned in this lab; before any separately authorized live run, price the entire path, eligibility, selected model and cleanup against limits chosen for the account.

## Watch the service lifecycle, not just the catalog label

AWS's [Amplify migration guide](https://docs.amplify.aws/react/build-a-backend/add-aws-services/pinpoint-migration/) says Pinpoint-backed Amplify analytics and push features stop functioning after **October 30, 2026**. It maps user identification and device registration to Amazon Connect Customer Profiles and event recording to Kinesis Data Streams or Data Firehose. It names Connect outbound campaigns as a possible campaign route, but AWS's separate [Pinpoint end-of-support guide](https://docs.aws.amazon.com/pinpoint/latest/userguide/migrate.html) says native push is not currently supported in Connect campaigns; a journey can invoke Lambda with push templates. This is a design change, not automatic campaign migration. The service guide explicitly lists **in-app messaging as unsupported after that date** and unavailable in Connect Customer. The Amplify migration page gives no replacement for that category. Do not start a new Pinpoint-backed in-app-messaging lab; a supported replacement design remains to be researched.

This does not mean every analytics event requires Pinpoint, nor that all push support disappears. The [Pinpoint service guide](https://docs.aws.amazon.com/pinpoint/latest/userguide/migrate.html) says push sending APIs continue under AWS End User Messaging, while stored Pinpoint endpoints, campaigns and analytics do not. A working push delivery API is not a working Pinpoint campaign or an automatically migrated Amplify client. The **specific backend and library path** matters. Write the proposed provider, version and replacement path before any feature or cost estimate. The same discipline applies to Predictions, Interactions and PubSub: a category name is too broad to establish a suitable service design.

The [current Amplify notifications setup](https://docs.amplify.aws/react/build-a-backend/add-aws-services/notifications/set-up-notifications/) documents a new `defineNotifications()` path. Think of it as giving a signed-in app a route to register its device and profile, not as pressing a campaign's Send button. It requires Auth for signed requests, uses Customer Profiles and an End User Messaging push application, and keeps APNs/FCM credentials in secrets. Unless an existing Customer Profiles `domainName` is supplied, the default setup creates an Amazon Connect instance and Customer Profiles domain. Campaign audience, consent, schedule, measurement and cost remain separate decisions. The [route-choice packet](../examples/notification-evidence/ROUTE-CHOICE.md) compares this with a direct push and a custom signed-in page. None has been provisioned or priced for this account.

The [illustrated notification lesson](../reader/BOOK-LOCATORS.md#book-655d767c170529a1) and [fictional evidence lab](../examples/notification-evidence/README.md) separate consent, an accepted send request, a push-provider event and an app observation. They also compare a direct push with a custom signed-in offer page. The page is a possible application design, not an AWS-provided replacement for retired Pinpoint in-app campaigns. No notification resources are declared in this lab.

## A small decision record before adding a box

For each proposed feature, fill one row before editing infrastructure:

| Question | What a usable answer contains |
| --- | --- |
| What exact user promise changes? | One observable behavior and who may use it |
| Which Amplify part and AWS service do the work? | The client/UI path **and** the backing service, if any |
| Who owns each resource? | Terraform, Gen 2/CloudFormation, a separately managed service, or existing infrastructure; one owner per resource |
| What is the authority boundary? | Caller identity, backend authorization, least-privilege role and one negative test |
| What must be measured? | A success result, denied/failed result, logs and a customer-visible outcome |
| What can keep charging? | Build, storage, transfer, request, compute, model, logs, retained copies and optional service meters |
| How does it end? | Stop the trigger, inspect running work, delete the owned resources, then verify residuals and billing |

For any live lab, check the selected account identity, Region, resources, credits and current terms. Estimate the complete run, including verification and cleanup, against spending and reserve limits chosen for that account. Keep Organization-dependent paths as designs until an authorized estate and budget exist. A chosen limit is an operating guardrail, not proof of the current balance or prices. See [Field Lab reader playbook](FIELD-LAB-READER-PLAYBOOK.md) before any deployment.

## Practice transferring the idea

Use the [four changed-condition cases and assessor](../examples/amplify-capability-choice/README.md) to choose the smallest sufficient path, name missing evidence and revise the design when the bakery's promise changes.
