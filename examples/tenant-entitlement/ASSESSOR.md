# Assessor: tenant plan changes and paid-feature access

Use after the first unaided attempt. This is reasoning for the fictional contract in the [reader case](README.md), not a universal SaaS billing policy or evidence from a live provider.

1. Alice's first export is locally accepted. Her second export at time 101 is denied because Shop A's current entitlement expired at time 100. An old browser label does not extend the server's current rule. Bob's Shop B request remains accepted: a change to A cannot silently change B's authority.
2. Alice's `shop-b` request is denied at membership. Knowing the tenant name or sharing an app does not grant her access. If a user legitimately belongs to both tenants, the selected tenant must still be checked against that user's current memberships; the fixture models one membership each.
3. Revision 3 applies the downgrade. Revision 2 arriving later is stale, and the duplicate revision 3 is ignored. A different payload with revision 3 is a conflict requiring investigation. These local revisions are assumed to come from a trusted source; an attacker-controlled revision field would defeat the model.
4. A new premium export is denied under standard. A standard read is accepted and its same-ID retry returns the original local receipt. A retry with a different intended feature under that ID is a conflict. The fixture's one SQLite transaction protects its local row, not an external download or invoice.
5. Closure stops new Shop A use without erasing its earlier receipts. A later `active` plan event cannot silently reopen the tenant; a new onboarding and copy/retention decision is required. Shop B's rows remain independent. Closure also needs to account for queued work, already generated files, backups and outside effects.

**Downgrade with in-flight export.** A policy that finishes previously accepted work needs a durable acceptance time, tenant and feature identity, a protected worker rule and a statement about when the exported file may be read. A policy that cancels it needs a cancellation boundary, a status the customer can see, and reconciliation if the export already escaped. Neither policy can retroactively erase a delivered copy. An invoice or refund rule is a separate business decision with provider evidence; the local usage row does not decide it.

**Architecture choice.** Feature entitlement and resource topology are two dimensions. A premium feature can use pooled compute/data if the promised isolation and performance are demonstrably met. A dedicated selected store may help a tenant's recovery or contractual boundary but adds provisioning, backup, monitoring, migration and fixed-cost work. Compare both on the same workload and failure cases. The local fixture establishes neither AWS isolation nor a real price.

**Evidence to seek before a live claim:** permitted and denied requests under real scoped identities; changed membership and tier propagation; event authenticity and replay; accepted-work behavior across expiry, downgrade and closure; direct API/file bypass tests; per-tenant usage-to-invoice reconciliation; restore and retained-copy behavior; whole-run cost and cleanup. An AI answer can suggest a missing path but cannot supply those observations.
