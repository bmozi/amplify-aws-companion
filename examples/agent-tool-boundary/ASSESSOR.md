# Assessor notes: application control of agent tools

1. Maya may read `policy-a` under the fixture grant; a shop-B document is denied even if its text would answer the question better. Relevance is not authority.
2. `export_all_customer_records` is not on the tool allowlist. A retrieved sentence proposing it must remain untrusted data. This fixture does not run a model against that sentence, so it cannot demonstrate prompt-injection resistance.
3. A model-proposed `actor` field is rejected as unexpected. The handler uses the separately supplied trusted actor fixture. In a real application, that value must come from validated authentication and current authorization, not from a browser field or model response.
4. `issue_credit` is accepted only for Maya's shop-A job, a separately trusted current intent for the exact actor/tool/job/amount/operation, current job revision, valid approval record and unexpired time. An approval by itself is insufficient to start work after a retrieved note suggests using it. The intent and approval live in application fixtures, not in the model proposal. An amount formatted as text, a Boolean, zero or above the chosen cap is rejected. The cap is a fictional product rule, not an AWS cost cap.
5. An identical operation ID reports the recorded tuple without another local effect, even after the original approval expires. Changing intent under the same ID conflicts. A production external payment/credit API would require its own idempotency and reconciliation contract; this dictionary does not provide that.
6. The new-action limit stops a second distinct action after the quota is reached, while a valid replay remains available. This is a single-process fixture with no persistence, concurrency, multi-tenant quota policy or model token meter.

The strongest answer draws the boundary between **evidence retrieved**, **model proposal**, **application authorization**, **human approval**, **tool execution** and **observed business effect**. It says which of those were actually exercised. A new Bedrock/AgentCore implementation needs current service/Region support, access control, logging/privacy, complete pricing, cleanup and live allow/deny verification before it can inherit any claim from this exercise.

In the joined [source-to-action journey](journey.py), the first proposal exactly matches a stored approval but has no trusted current intent; it must leave the credit map empty. Test code then inserts one intent and allows one fictional effect. The later revoked excerpt must be denied, while the already recorded effect remains. Do not claim the hand-authored proposal was produced by a model, that the trusted intent came from a real human, or that revocation reversed an effect.
