# Assessor notes — storage auto scaling

- Case A runway is `50 GiB / 100 GiB per day = 0.5 day`, or 12 hours under the simplified steady-rate assumption. A weekly response misses that window. An automated action is a candidate, but the design needs an explicit maximum, IAM authority, quota handling, duplicate-request guard, action status and alert, plus verification through the EBS volume, partition, filesystem and application layers. If automation is not chosen, a more frequent staffed response or a changed architecture must fit the same recovery window.
- An EBS size-change request can take time and be subject to limits. The OS may require separate partition/file-system extension, and EBS size increases cannot be undone by shrinking that same volume. A failed or partial action needs a safe path; do not keep increasing size without checking why the filesystem is not using it.
- Case B: EFS storage capacity grows and shrinks with stored files; manually preallocating extra capacity is unnecessary for this basic storage boundary. Teams still own data retention, access, costs, performance/throughput mode, backups and application correctness. EFS elasticity is not a cost cap.
- Case C: S3 avoids provisioned-capacity resizing, but stored bytes and operations still cost money; retention and lifecycle need policy; request rates and application paths need monitoring; object count and query structure can affect downstream work; account quotas and spending controls still matter. Automatic service scaling does not stop charges.
- Changed Case A: 600 GiB at 10 GiB/week provides about 60 weeks of simple runway. If a monthly maintenance response is acceptable and observed growth remains stable, a documented manual resize may be adequate. The decision changes if growth accelerates, the response window shrinks, or maintenance becomes unreliable.
- All rates are fictional and steady for arithmetic only. No AWS alarm, scaling action, live metric, cost or recovery operation is verified here; independent learner review remains pending.
