# Transfer-selection assessor notes

These are authored design criteria, not service execution results. Several architectures can be justified when their assumptions and tests fit the business.

## Write-gap assessor reasoning

The unsafe path checks equal rows, then a source-side SQLite transaction commits `late` while the selector is paused. The selected pointer changes to target, but the target has no `late`. This is a real local check-to-switch gap; an earlier true comparison did not remain true. The controlled path serializes all *participating* fixture writers with the selector. Its writer starts while the selector holds the gate, then commits to target after selection. The observed store contents support that one-process outcome only.

For transfer, ask where direct database clients, scheduled jobs, queue consumers and users with old endpoint configuration would write. A suitable production plan must pause or fence those paths, or capture and reconcile their changes through a reviewed final position. It must verify the application route and business results afterward. A Python lock shared by two local threads cannot coordinate independent hosts or prove CDC completeness. Neither path measures AWS migration behavior or customer downtime.

## Database-epoch assessor reasoning

The negative control compares equal rows outside the selector transaction, then `late` commits to the old store. Advancing the route afterward chooses the new store without `late`. In the controlled path, a SQLite `BEGIN IMMEDIATE` transaction holds the selector's comparison and epoch change together. A separate connection trying to write through the participating application function sees epoch 1 when it obtains write authority, so its stale epoch 0 request is refused. A fresh epoch 1 request writes `late` to the new store. These are two local SQLite connection outcomes, stronger than a Python-only lock but narrower than a distributed migration.

The direct SQL bypass test can insert into the old store after route selection because the example has no database privilege or trigger that forbids it. A real independent old writer might be a scheduled job, old application instance or operator. If route and stores move to different authorities, this single-file transaction no longer gives one atomic boundary. A useful answer names every writer and its actual authority, demonstrates a denied stale request at the authoritative write point, reconciles the final change position, then checks the customer read and any outside effect. The fixture proves none of those cloud or customer claims.

## Customer-route assessor reasoning

The first selection fails because the old source has order `d` while the target does not. Replaying that known record and reconciling IDs and values lets the local route select the target. A subsequent `201` for target-only order `e` establishes that this toy server committed a SQLite row before replying. It does not establish that a real external system performed an associated effect.

The guarded fallback refuses to move the selection while the old source lacks `e`. The forced fallback is the negative control: the same `GET /orders/e` returns 404 from the old source, then 200 again when the target is reselected. After the fixture copies `e` to the old source and compares all local IDs and amounts, guarded selection permits the return and the same route reads `e` from the old source. A real rollback would need a reviewed reverse-data and external-effect plan, not merely a DNS reversal. If email or payment was proposed, record its independently observed receipt and reconcile uncertain outcomes; do not invent either effect from the local 201.

The route selector is a trusted file in one process, and the requests are sequential. These observations cannot establish concurrent-writer safety, traffic convergence, live identity, AWS data migration, payment state or actual customer recovery.

## Reverse-replay assessor reasoning

The first attempted replay raises after inserting `e` but before committing the source transaction. SQLite rolls the local transaction back, so `e` and `f` remain absent from the source and the guard refuses the return. A complete attempt adds both missing rows. A retry inserts zero, which matters if an operator cannot tell whether the prior attempt finished. A source row with the same ID but a different value is a conflict, not evidence that either side wins; the fixture rejects it and keeps target authority. A source-only row also fails the final full comparison even though the replay itself only adds missing target rows.

The fixture reads the target before opening a transaction on the source. It cannot stop a target write after that read, coordinate independent applications, model updates or deletions, or verify payment/email/shipment effects. A production proposal must define the write fence or captured final change position, complete business reconciliation, conflict policy, outside-effect receipts, and a tested route under the real identity and traffic paths. The local successful return is not evidence of those properties.

## Outside-effect assessor reasoning

Equal order rows establish only the local data match. The separate provider may already have recorded the invented authorization even though the application lost its reply. The guard therefore refuses to return while the target receipt state is `unknown`. A matching provider lookup confirms the fixture effect, but a return still fails while the old application lacks that exact operation and receipt. Copying the confirmed receipt lets the sequential local guard pass without asking the provider to authorize again. The repeated copy inserts zero rows. A wrong provider amount, a changed old receipt, or an unavailable lookup stops the claim; none should be repaired by inventing success or silently overwriting a conflict.

The observed provider is another SQLite file under the same program's control. Its deterministic hash is not an authenticated financial receipt, and a real provider may have different authorization, settlement, reversal, lookup and idempotency contracts. The local gate also has a check-to-switch interval and no independent writer fence. A strong changed-case answer names the accountable owner, preserves the operation ID, holds on the working target while the outside outcome is uncertain, and distinguishes a data repair from a provider action and from the customer's observed result.

## Versioned-change assessor reasoning

The injected replay applies two changes inside the old store's uncommitted SQLite transaction, then raises. The transaction rolls back both, leaving live `e` at 250 cents and live `f` at 375 cents; the pointer stays on target. The full replay produces live `e` at 300 cents/revision 2, deleted `f` at revision 2 with its previous amount retained, and new `g` at 425 cents/revision 1. The complete journal and rows match, so the **sequential fixture** guard selects the old source. An identical retry applies zero changes because the old journal is a complete prefix of the target journal.

A same-revision but different old amount and a higher old revision are both conflicts: the expected predecessor does not match, so the replay refuses to overwrite it. Physically removing `f` loses the tombstone needed to reject a stale recreation; the full-row guard refuses. Corrupting a journal entry also blocks return even when final rows match. A changed target after the journal read could make the comparison expire before pointer selection. This model has no independent CDC capture, writer fence, common transaction, provider-effect reconciliation or routed customer validation. The changed-case answer holds authority on the target until those conditions are separately observed; a passing local replay is not a safe cloud rollback.

## Lowest-cost transfer case

The ideal 6 TiB transfer at a continuously available 200 Mbit/s is approximately 73.3 hours: `6 × 1024^4 bytes × 8 ÷ 200,000,000 bits/second`. This excludes shared use, protocol overhead, scanning one million files, retries, verification and the final change/cutover pass. The estimate is a lower bound, not a guarantee that ten days is sufficient.

- Direct client transfer can avoid a DataSync service fee, but it still needs a supported source/client path, bounded network use, inventory, retries, integrity evidence, operator time, S3 requests/storage and a final reconciliation. Check the source-provider's egress or circuit costs; do not assume they are zero.
- DataSync can supply managed task behavior, integrity checks and task reports for supported pairings. Its current pricing describes a per-GB data-transfer charge and an additional per-task-execution charge for Enhanced mode. S3 destinations can also incur LIST, HEAD, GET and PUT requests. Price the selected mode and data processed, source/destination request costs, agent/hosting/network, destination storage, verification, retries and overlapping operation. DataSync's verification is limited to what the selected mode, configuration and manifest cover.
- The business has not asked to keep using an office file interface after cutover. A continuing Storage Gateway therefore adds an ongoing requirement and cost that this one-time transfer does not need. If that interface is a requirement, compare it as an access architecture, not as a like-for-like copy command.
- No actual regional prices or source-circuit cost are in the prompt. The defensible result is a completed comparison method plus an explicit request for current inputs, not a made-up winner. Estimate the options that meet both the deadline and the correctness/retirement criteria, then select the lowest total cost among those eligible designs.
