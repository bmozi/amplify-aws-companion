# Legacy state and failover: assessor reasoning

Use this after preserving the learner's first prediction. These explanations describe a fictional design, not a deployed AWS service.

The local proxy can select B after A's HTTP server stops, and B's `/health` returns 200. B has its own empty session set and temporary directory. The old cookie identifies a session only A had, so `/me` returns 401 on B. The photo is absent from B before the copy. Copying those bytes changes the file inventory, not the session inventory. A new toy sign-in on B can then read the file. A reader who reports “the site is up” from `/health` has observed a narrower condition than the customer's authenticated photo path.

The lab's copy is possible because it stops only A's HTTP service and retains A's folder on the same host. If the disk is destroyed and no independently retained copy exists, the lab's recovery step has no source. A backup success marker would still need an exact restore and customer read check, with version, owner, integrity, time and permission evidence. A local shared folder or one post-failure copy does not establish an appropriate durable multi-AZ file service or ongoing consistency.

Under a no-source-change constraint, inspect the application's documented clustering/session and file interfaces. A supported shared-state mode is a candidate only after compatibility, access and failure tests. Active/passive operation with backup and an honest interruption window can be a defensible alternative when the vendor cannot share state. Sticky sessions may reduce routine cross-node surprises, but the failed target's in-memory state is gone from the survivor. If the business permits a fresh sign-in, that concession should be explicit; if it forbids one, the plan needs a supported way to preserve or re-establish sessions or a revised promise. Neither answer may silently lose confirmed files.

The toy proxy returns 503 for an unavailable selected node. Do not generalize that result to ALB's documented all-unhealthy case, which can fail open. A correct explanation separates target health, traffic selection, application state, authorization and the observed customer task. It also names the extra cost and work of a shared store, replicated files, running standby, backups, tests and retained copies where applicable, without inventing a price. A two-target drawing or a passing unit test does not prove effective AWS permissions, sustained capacity, failure-domain isolation or recovery time.
