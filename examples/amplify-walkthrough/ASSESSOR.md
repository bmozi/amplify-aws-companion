**Local HTTP result:** Bob's list is `200` with no items in all three modes. In the list-only handler, Bob's direct read of Alice's known note is `200` and includes her synthetic text; in the guarded handler it is `403` with no note. Alice's direct read is `200`, and an unlabelled request is `401`. The claimed `X-Lab-Actor: alice` header can be sent by anyone running this fixture; the `bob_claims_alice_header_get` case therefore returns `200` even in the guarded version. This proves the fixture has no authentication. It does not test Cognito, AppSync, the generated owner rule or durable data.

**Existence changed case:** The guarded handler returns `403` and an owner-denial body for Bob's request for `note-1`, but `404` and an unknown-note body for `not-a-note`. This fixture therefore distinguishes an existing forbidden ID from an absent ID even though it withholds Alice's text. The third mode returns the same 404 and body for those two requests while allowing Alice's claimed label to read. That is a narrower local status/body observation, not proof of indistinguishable timing, headers, other routes or a real identity; the forgeable actor label remains a separate failure. Restricted internal diagnosis is not implemented. Do not assume every business requires the same response or infer actual Amplify behavior.

1. **Save:** The client create/update call and returned error check matter, along with the `Entry` model and its owner rule. A React state change can disappear on refresh. A later authenticated read of the saved record is stronger persistence evidence; the source still cannot prove that a deployed resolver or table accepts it.
2. **Identities:** Cognito user-pool sign-in, identity-pool-derived storage scope and operator or service AWS authority have different jobs. Display email is neither deployment authorization nor the storage identity path.
3. **Destination:** The local browser uses the backend named in `amplify_outputs.json`; `localhost` does not isolate data or costs. Inspect the actual outputs and built configuration before assuming a safe destination.
4. **Bypass:** The 5 MiB check is in browser code and does not establish a server-side S3 size policy. The handler's 10,000-character check executes in the text-inspector function. A direct oversized upload denial would need an actual backend rule and test; do not perform one merely for this paper lesson.
5. **Green Hosting:** The job supports publication of browser files, not successful sign-in. Wrong backend outputs and an authentication-flow failure are distinct hypotheses. Compare the built destination with the intended backend and inspect sanitized request/error evidence without exposing tokens or personal data.
6. **Category:** Review backend schema, client edit/display code and tests. Decide whether existing records get a default, remain uncategorized or require migration before making the field mandatory. A UI-only label is not stored data or authorization.
7. **Capabilities:** A static menu can use Hosting without Cognito or a database. Private orders need identity, authorized data access and relevant client calls; photos add storage and file-handling rules. UI components are optional. Terraform and Gen 2 must not both own the same resource. Each added service needs a meter and cleanup path. An available client API does not prove deployed backend configuration.
8. **Publication:** The push saved source; this manual workflow's false flag prevents a new publication job. A matching served marker supports static artifact identity, not note authorization. A second-user API read is a material privacy failure: repair the server-side owner rule and verify direct denial, rather than hiding a button. Turning the flag off does not remove the hosted site, backend, retained data or logs; inventory and cleanup need separate evidence. Other authorized workflows or already issued sessions need their own route checks.

**Changed fact:** An empty second-user list is insufficient because the direct read may still succeed. Attempt a synthetic unrelated-user API read of a known first-user record in an authorized test environment. Record the effective deny and source revision before claiming owner isolation. A local fixture would establish only its modeled boundary; a live claim needs an actual deployed denial.

**Owner transfer:** The current model-level `allow.owner()` rule alone does not establish that the owner field is immutable. AWS documents default owner reassignment by the existing owner and a field-level authorization pattern to restrict it. If the business forbids transfer, the learner should specify that invariant, review the actual schema and generated behavior, and design an owner-update denial test. The local HTTP lab does not model reassignment.
