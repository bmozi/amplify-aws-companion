# Lambda release: expected reasoning

These are editorial criteria for the original design cases. They do not establish an assessed learner outcome or a live AWS deployment.

1. Only the API integration uses the `live` alias. The nightly program targets numbered version 7 directly, while the unqualified test call targets `$LATEST`. Inspect actual integration/SDK/event-source configuration and effective invocation permissions. Moving an alias does not rewrite those other destinations. Reject an answer that calls the unqualified target “current production” without evidence.
2. A small probabilistic sample need not match the configured weight. Zero candidate observations supplies no candidate correctness evidence; one success does not justify a broad safety claim. First verify target and routing configuration, then collect version-attributed qualifying and nonqualifying responses and relevant failures/latency. Define an observation threshold from workload and consequences, and hold when evidence is insufficient. Do not copy the deterministic local canary's two-request teaching threshold into AWS.
3. Read the complete alias configuration, including additional weights, and establish the intended previous-version-only state. Direct version-8 callers need a separate decision. Observe subsequent executed versions and customer results; a successful update command is narrower evidence. Investigate in-flight and already completed payments with the business operation identifier and provider evidence. Do not automatically retry a payment whose result is unknown.
4. Both versions share data, so candidate writes can affect old-version reads. Introduce a compatible representation, prepare readers/writers, verify mixed-version behavior and preserve a compatible recovery target before contracting the schema. Low traffic weight does not establish data isolation. Returning traffic to 7 can worsen impact if 7 cannot read existing candidate writes.
5. Weighted invocation routing alone does not establish stable per-customer assignment or membership in an approved cohort. Define a trusted assignment/routing boundary and enforce access independently of a client-provided group claim. Evaluate repeat calls, changes in eligibility and observability. A design may use another supported mechanism, but must show how it satisfies the requirement rather than assuming the alias does so.

For the queue transfer, require separate units for invocations, records, customers and effects. Verify the actual mapping target, batching, failures, retries, concurrency and version observations for the chosen integration. Do not claim that a ten-percent invocation weight limits ten percent of records or financial loss. Preserve the cost ceiling and reserve before any cloud run; retained versions and monitoring need explicit cleanup decisions.
