# Which caller follows the Lambda release?

Design-only companion to [delivery and recovery](../../reader/BOOK-LOCATORS.md#book-02b8b1e13a935d6d). This worksheet creates no AWS resources and contains no deployment commands. The identifiers and observations below are fictional. Read the lesson's official references for service behavior; these cases are original teaching material, not AWS exam questions.

Write a decision and a missing observation for each case before reading [assessor notes](ASSESSOR.md). Use the [learning record](../../curriculum/LEARNING-RECORD.md) to separate your first answer from any Codex assistance.

1. **Three destinations.** An API integration invokes `quote:live`, a nightly program invokes `quote:7`, and a manual tester invokes `quote`. The `live` alias currently selects version 7; the proposed rollout adds version 8. `$LATEST` contains an unfinished experiment. Draw all three paths. Which callers follow the alias change, and which require separate investigation? Do not assume their permissions are interchangeable.
2. **Wrong denominator.** A ten-percent candidate weight is configured. An operator sends ten requests, sees only the old version and declares routing broken. Another operator sees one successful candidate request and declares the release safe. Explain why neither conclusion follows. Specify version-attributed business evidence and a stop/hold rule without inventing a universal sample threshold.
3. **Partial recovery.** An incident record says “primary version restored to 7.” The alias still lists version 8 with an additional weight. Some jobs invoke version 8 directly; one payment invocation was already running. Identify the separate paths and effects to reconcile before claiming recovery. State what must be read back and what must be observed from callers.
4. **Shared dependency.** Version 8 changes stored values to a representation version 7 cannot read. Most alias traffic still reaches 7. A teammate argues that the small candidate weight confines the problem to candidate callers. Explain the failed isolation assumption and design a compatible transition before increasing exposure.
5. **Wrong mechanism for the requirement.** Maya wants the same customer to keep seeing the same experiment and no customer outside a reviewed group to receive it. A proposal uses only a random weighted alias. Explain why an invocation share does not establish that requirement. Identify the trusted assignment, authorization and observation design still needed; do not invent a targeting feature from the alias name.

Transfer: the quote function becomes a queue consumer that processes multiple records per invocation. Explain why invocation share, records processed, unique customers and money at risk are different quantities. Identify the selected event-source behavior you would verify before proposing a rollout. This paper exercise does not test queues, retries, permissions or weighted AWS routing.

Ask Codex to change one caller target after you finish, then explain which part of your answer must change. Do not let it substitute generated logs for missing observations. The exercise does not perform a live release.
