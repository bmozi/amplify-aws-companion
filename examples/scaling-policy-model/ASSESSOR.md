## Local model

At 0.1 seconds per sequential message, one task could process 10 messages per second under the stated simplifying assumptions. A 10-second wait target implies 100 messages of backlog per task. A backlog of 1,500 divided among 10 running tasks is 150 per task; 1,500 divided by 100 is 15 candidate tasks. The model does not include in-flight work, message groups, initialization, retries, variation, target tracking timing, available capacity or the downstream service. It must not be presented as an AWS simulation.

For the second scenario, completion is bounded by the lowest of arrival demand and each serial stage's capacity. `min(12, 20, 8) = 8` jobs complete per second, so unfinished work grows by four per second while the rates remain fixed. Doubling workers does not help. If a verified improvement raises the save stage to 16, 16 can complete while backlog remains, and the surplus above 12 arrivals is four jobs per second. `1,440 / 4 = 360` seconds to clear that backlog. If the queue is empty, completions do not exceed arrivals. The arithmetic does not imply a particular database resize or real capacity.

## Design cases

1. **Diagnosis:** Rising customer latency/errors with normal average CPU and higher database wait makes the database path a leading hypothesis, not a proven root cause. Check per-query or connection evidence, saturation and customer outcomes before changing the API fleet. If the database recovers and CPU is the constrained resource, task scaling may be a candidate; verify that adding replicas increases useful throughput and that storage, quota and downstream limits allow it.
2. **Controls:** Static public help content may be cacheable if its freshness and invalidation behavior are acceptable. Tenant-specific authenticated records need an authorization-preserving request path and a cache policy/key that accounts for every relevant identity and variation dimension, or should bypass shared caching. A load balancer distributes requests among eligible targets; it does not grant tenant permission. Omitting tenant identity can return another tenant's response and is a release-blocking correctness/security defect.
3. **Containers:** Fargate can reduce host management for compatible tasks; ECS on EC2 can fit host, GPU, daemon, capacity or cost-control needs while adding host operations; EKS fits actual Kubernetes API/ecosystem requirements and adds cluster and node/pod responsibility. Require image identity, task/service configuration, minimum/maximum capacity, startup/readiness, target health, IAM paths, data state, drain behavior and rollback. A Kubernetes-specific controller/operator requirement is evidence for reconsidering EKS; a generic container requirement alone is not.
4. **Global workload:** Edge caching is a direct candidate for eligible static assets and may improve access without duplicating booking writes. Regional reads need a stated staleness tolerance. Regional write cells need a partitioning/authority model; replicated data can lag or conflict. Require routing, identity, quotas, secrets/keys, deployment artifacts, failure and failback evidence plus full regional cost. Extra Regions do not automatically scale a single hot write key.
5. **Serverless:** A short request handler can validate/record a booking and return a meaningful result; non-urgent conversion can run asynchronously from a durable queue. API Gateway/Lambda limits, function duration/concurrency, queue semantics, redrive, idempotency, database connections, observability and retries need coordination. Maximum source concurrency and reserved function concurrency are separate controls; cap the sum of source maxima within the function's safe reserved capacity. Check current documented mode, metrics, quota and charges for the selected configuration.
