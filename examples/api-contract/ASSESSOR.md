# API contract review: assessor reasoning

Authored criteria under fictional assumptions. These six design-case criteria are not live AWS observations or a complete API specification. The separate local lab adds bounded HTTP and SQLite evidence; see its README for scope.

1. The server violates the proposed durable-acceptance promise by issuing its receipt before persistence. HTTP 202 does not prove storage or completion. Verify committed request and dispatch obligation before the promised receipt; define the failure response when that step cannot complete. Do not reinterpret the interface's “safely stored” statement as merely “bytes received.”
2. A fresh key can identify a second operation even though R17 exists. Retry/reconcile using the original key within its documented lifetime and trusted caller scope; return R17's identity and state for the same input. Changed meaning must follow a documented conflict or explicit modification path. Simultaneous retries also require an atomic implementation; the design table alone is not that implementation.
3. An identifier locates a record; it does not authorize the reader. Validate the caller and current ownership/access for each status read, including revoked access. Test a valid reader and another customer against the same existing record through the actual endpoint. Do not return another customer's state merely because the identifier is valid. A chosen non-disclosing error response still requires correct enforcement underneath.
4. The status lookup succeeded, but the business operation was rejected. Render the business state and appropriate next step. Closing the browser ends local interaction; the described contract contains no server cancellation operation. If cancellation is required, define its authority, race with completion, external effects and resulting status separately.
5. The stated one-day mapping cannot establish three-day retry recognition. Define how clients recover the original operation from retained authorized business records, or require investigation when its outcome cannot be established. Do not automatically submit as new while claiming no duplicate risk. Align retention, retry rules and supported offline behavior; state unresolved cases explicitly.
6. AWS's cited comparison lists private API endpoints for REST APIs, not HTTP APIs. Revisit the selected product and design. Then verify intended client reachability, authorization, resource configuration, backend integration, deployment and cost. Selecting the product does not establish the endpoint's actual privacy or business authorization. The scenario does not authorize a cloud deployment.

An acceptable contract gives the client a meaningful next action while stating uncertainty. It separates HTTP outcome, stored-operation state and real-world completion. The local lab demonstrates fixture-based ownership checks, concurrent SQLite acceptance and a controlled lost reply over loopback HTTP. Real authentication, deployed-service behavior, expiry, revocation and measured polling load remain open for a customer-facing API.
