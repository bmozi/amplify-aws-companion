# Assessor notes: distributed and hybrid compute placement

1. **Normalize a web request:** CloudFront Functions are a plausible lightweight option. The learner must preserve correct cache-key behavior and cannot mistake request rewriting for authenticated business authorization.
2. **External policy service:** Lambda@Edge may fit supported network/library needs; regional compute may be simpler if the policy call and user path already require the Region. The learner must identify latency, timeout, fail-closed/open behavior and authoritative policy source. A successful function invocation does not prove an application operation is authorized.
3. **Factory equipment:** Outposts may be a candidate for supported on-premises AWS compute/storage, but its service link to the parent Region, local network, physical readiness and supported services matter. The workload needs an explicit offline requirement. A regional dependency failure may affect control/management or cloud calls; do not claim full disconnected operation without testing the specific services and application. A local non-AWS worker may be a credible alternative.
4. **5G sensor:** Wavelength can bring supported AWS compute/storage closer to carrier 5G users. It adds carrier and location eligibility questions. It is not a generic speed switch and should be compared with the simpler regional path using a measured latency requirement.
5. **Region recovery:** Worldwide users may need latency-aware delivery, but that does not itself require multi-Region writes. A recovery Region needs explicitly replicated state, service/feature compatibility, identity, keys, quotas, DNS/client path and a tested recovery procedure.

A strong answer separates four ideas: where code runs, where data is authoritative, what network must remain available, and which failure promise the design actually meets. Product eligibility and form factors change; verify the target plan against current AWS sources. No cloud evidence is claimed.
