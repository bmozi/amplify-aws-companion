# Assessor: the old device and the new hazard

Read after preserving a first answer to the [changed case](README.md#when-an-old-device-says-the-repair-is-finished). This is authored reasoning for a fictional local fixture, not an independent learner score or a verified repair.

1. A last-arriving close that overwrites the current row would hide the revision-2 hazard and show a repaired machine without inspecting it. The current fixture requires an expected revision at the same local transaction that changes the row. It rejects the revision-1 close after revision 2 exists. That prevents this particular silent overwrite in this file; it does not determine physical safety.
2. `STALE_REVIEW` means the attempted closure did not apply. The order remains open. A responsible, authorized person needs to inspect the new report and actual machine, then decide and record a new action against the current revision. A server receipt for a hazard is not proof of a human response or a completed repair.
3. Rejection of an outdated report must not make a safety-critical observation disappear. Preserve the device draft and its original identity, make the conflict visible to clinic staff and the central owner, and follow the clinic's separately chosen local escalation path. The fixture does not implement that handoff or verify a call. Blindly giving it a fresh ID may create a second incident while failing to reconcile the first; define the business identity and review rule first.
4. A lost reply repeats the same operation ID *and content* to recover the saved outcome. Changed content under the same ID has a different meaning and is rejected. A new action after review needs a new ID and a fresh expected revision; an old rejected decision is not silently turned into success on replay.
5. The invariant depends on all relevant writes reaching one effective authority and enforcing the revision condition there. A second independent file or bypassing writer defeats this local demonstration. A selected cloud design needs real caller/device identity, record ownership, write-path inventory, conditional update semantics, retry/receipt retention, offline-copy protection and a tested conflict route. A working local SQLite transaction cannot prove those cloud controls or a multi-site consistency promise.

**Scoring guidance.** A strong answer separates local saved work, central acceptance, hazard visibility, reviewed closure and actual machine condition. It names the first unsupported claim and a rejecting observation for each. Do not award implementation credit from a diagram or this local test, and do not average away a hidden safety report as a minor rubric point. Ask the reader to change the case to a lost device or an unavailable central authority; an unaided revised answer is separate evidence from this assessor.
