# Reasoning for the fresh capacity cases

Open after saving the first attempt. This is an internal, uncalibrated reasoning guide; alternative designs need their own supporting facts.

1. Each strong read rounds to two 4-KiB blocks: 120 table read units/second. Each write rounds to three 1-KiB blocks: 75 table write units/second. Each new 700-byte index entry costs one index write unit: 25 in its separate pool. Eventual reads reduce this successful-read calculation to 60 units/second, but can violate a required fresh confirmation. Consumption does not establish configured capacity, latency or price.
2. Ten failed conditions against three-block existing items add 30 table write units, bringing the table total to 105. No index change means no additional GSI write here. Concentrated key traffic, contention, quotas, bursts and retry behavior are not proved by the table-wide sum. Different operations need their own accounting.
3. Total I/O is 1,000 operations/second. Bytes are (800 × 64 + 200 × 16) / 1024 = 53.125 MiB/s. Both are below the stated ceilings. At 128 KiB per read, throughput becomes 103.125 MiB/s while IOPS stays 1,000, so throughput exceeds its ceiling. Neither comparison rules out CPU, memory, locks, connection waits or incorrect results.
4. Investigate pool occupancy, all client counts and deployment overlap first. An index might reduce query work but the supplied timing identifies a much larger pool wait; its cause still needs evidence. Reduced overlap changes release and failure capacity. A larger database or proxy does not automatically repair inefficient or pinned sessions. Require customer-level latency and correctness under the selected change.
