# Telemetry design: assessor notes

1. The full combination set is 2 × 3 × 2 = 12 dimension combinations. Two metric names give 24 metric identities in the stipulated namespace and scope. With 1,000 globally unique request IDs and both metrics published for each, the fixture gives 2,000 identities: each request already belongs to its environment/route/outcome combination. Multiplying 2,000 by 12 double-counts combinations that were not observed. Neither number is a dollar bill or a statement about all CloudWatch metric types.
2. Removing request ID from dimensions reduces metric identity growth while allowing controlled log correlation. It does not remove log ingestion/storage/query work or applicable custom-metric charges. Verify the actual dimension sets emitted by the chosen library; multiple sets can publish multiple identities.
3. A route template such as `/customers/{customer_id}/orders/{order_id}` can serve the metric's bounded endpoint question. Do not retain query secrets. Use an allowlisted, purpose-specific event schema, access controls and retention for necessary correlation. Hashing a unique value does not merge it with other requests and is not a universal privacy guarantee.
4. The sampled set's observed failure fraction is 2/10; the complete stipulated counter's fraction is 10/1,000 = 1%. Do not interchange them. A real population estimate needs the selection method, inclusion probabilities where applicable, missingness and uncertainty; error-biased sampling can intentionally overrepresent failures. The fixture's complete counter is an assumption to verify in production.
5. Check telemetry pipeline health with a separately observed heartbeat, controlled synthetic transaction, delivery status or another appropriate independent path. Explain which shared failures remain. A dashboard with no incoming observations must not silently become proof of service health.
6. One-hour retention conflicts with next-day investigation unless another adequate evidence path exists. Reduce unnecessary fields or event volume where the required diagnosis remains possible, price the remaining retention and queries, and assign evidence access/removal responsibility. Sampling or deletion must not erase required security or business records. Do not invent a universal retention period.

7. The 60 observations sum to 600, average to 10 and have maximum 60. The maximum preserves the highest sampled backlog; it does not prove the peak between samples or individual waiting times. Summing queue depth is not counting arrivals: the same waiting jobs can appear repeatedly. Faster display refresh cannot reconstruct unrecorded observations. Select observation frequency, supported metric resolution, period and statistic separately; price publication/API usage, metrics and applicable alarms before selecting a cloud configuration. A complete one-second fixture is a stated assumption here, not a live measurement.

Accept alternatives that preserve the stated observation and explain tradeoffs. Mark answers needing revision when they call missing data zero, infer privacy from hashing, equate EMF with free metrics, or substitute a sampled rate for a complete population without a sampling argument. No live billing, tracing or learner assessment has been performed here.

## DOP-C02 task 4.1 assessor notes

1. **Secure logs:** allowlist necessary fields, omit or mask sensitive payload data at source, and separate writers, readers and deleters. Set CloudWatch retention from the support/security requirement; treat a copied S3 archive as a second controlled dataset. A changed retention rule needs an authorized owner and current cost/risk review, not a default guess.
2. **Metric filter:** a JSON pattern such as `{ $.statusCode >= 500 }` can match new events and publish a value such as 1. It does not backfill historic logs and delivery can be duplicated. A default zero may be published for periods where logs arrived but none matched; it cannot be configured with dimensions, and no events means no evidence that the period was quiet. Do not use a request ID dimension.
3. **Metric Stream:** it exports existing metric updates through a configured delivery route; select necessary namespaces/metrics and verify the Firehose destination role, buffering, errors, format and final S3/partner receipt. Estimate both Metric Streams and Firehose. Raw event records need a log-subscription route, not a metric stream.
4. **Custom host metrics:** the CloudWatch agent can collect supported host metrics and logs. Configure only selected measurements, use the instance's role, permit required service endpoints and observe agent/publish health. A host metric explains machine behavior; a business counter requires application instrumentation or a deliberately chosen event-derived metric. No local test verifies agent behavior.
5. **Lifecycle:** CloudWatch log-group retention controls its stored events; S3 lifecycle applies to objects already delivered to S3. The archive and live search path have separate costs, readers, retention and deletion proof. CloudWatch marks data after its retention point; physical deletion can take up to 72 hours. Owner/legal approval and restore behavior are outside the worksheet.
6. **Subscriptions:** scope the filter, size the destination for expected volume, preserve event identity for idempotent processing, monitor delivery and retries, and exclude logs produced by the delivery workflow to prevent loops. A subscription route does not automatically establish downstream durability or exactly-once side effects.
7. **Search:** use the selected log groups and narrow incident time range; filter, parse, aggregate and limit results. Estimate scanned data. Logs Insights query language is not metric-filter syntax. A larger query can improve context but increases scan volume and should not be left running unnecessarily.
8. **Encryption:** CloudWatch Logs encrypts at rest by default and encrypts in transit. A customer-managed KMS key gives additional key control but adds key policy, service access, availability and recovery obligations. If the key is disabled, retrieval of data encrypted with it fails until access is restored. Test actual authorized read/write paths before relying on the configuration.

These are reasoning criteria tied to current AWS documentation, not proof of implemented settings. Cross-account centralization depends on AWS Organizations and remains design-only here. No AWS behavior, price or learner transfer has been tested.
