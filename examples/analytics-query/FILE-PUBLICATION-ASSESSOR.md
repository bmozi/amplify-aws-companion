# A19 file publication: changed conditions and assessor reasoning

These are fictional, local design questions. Attempt them after the [multi-file drill](README.md#when-one-report-spans-several-files) and before reading the answers. No AWS service or learner attempt is represented here.

## Questions to attempt first

1. V1 is selected at 300 cents. A worker writes only the first v2 part, then exits before writing the second part and manifest. What does the selected reader return? What would a reader of mutable `latest` risk returning?
2. The worker retries with the same run ID but changes `b` to 181 cents rather than the staged 180. Should the partially staged part be overwritten or treated as a conflicting run? What new identity would a genuinely revised source need?
3. V2's selection pointer changes, but the publisher loses its response. It retries with the prior expected generation. Should it publish again, report failure, or read current selection? What if the current selection names a different run?
4. A reader opened v1 immediately before the pointer changed to v2. The cleanup worker removes v1 files as soon as it sees v2 selected. Which customer observation may fail, and what retention decision is needed?
5. Another writer read generation 1 before v2 was selected. It later tries to select a different revision based on that old value. What does this local sequential check reject, and what additional control would a real concurrent object-store design need?
6. The selected manifest's hash matches the part bytes, but the source register omitted a sale from both its records and declared expected-ID list. Is the daily result complete? Which independent source or business reconciliation could reveal the omission?
7. Two complete candidates, v2 at 330 cents and v3 at 340 cents, both expect generation 1. An overlapping local transaction lets v2 win. May v3's worker silently retry with generation 2 because its declared source revision is higher? What must it check first?
8. In the [separate checkout-register drill](README.md#compare-the-report-with-a-separate-checkout-register), a 280¢ candidate passes its own manifest and hash checks. Which evidence holds it? What if the candidate and register both say three receipts and 330¢ but disagree on one ID? What if the register row list omits `late` while its separate closing controls still say three and 330¢?

## Assessor reasoning

1. The pointer still names v1, so the local selected reader returns the complete 300 cents. The incomplete v2 has no manifest and cannot be selected. An in-place mutable folder can expose 280 cents after the corrected first part is written but before the late-sale part arrives. That is a counterexample to equating one file's successful write with a complete dataset.
2. Reject the changed bytes under the same run ID. Retrying an identical input may complete missing parts; silently changing a staged part destroys the meaning of the original run receipt. A new source revision/run ID, with an explicitly reconciled expected row set, is needed for a real correction. The local check does not authenticate the source of either input.
3. Re-read selection first. The local retry returns `already_current` when it finds the same v2 run and validates its files; it must not append rows or advance the generation again. A different selected run requires investigation of its revision and authority, not a blind overwrite. The local example serializes actions; a real design needs a conditional selection update and a retry policy for conflicts.
4. The pinned v1 read can fail even though new readers receive the correct v2 result. Retain old parts for the promised reader lifetime and recovery window, with an owner and removal evidence. “Latest is v2” alone is not a safe garbage-collection rule. The lab deliberately deletes one old part to demonstrate the failure.
5. After v2 selects generation 2, a selection attempt with expected generation 1 is stale in the sequential model. That local check is not a distributed compare-and-swap: two writers could both read generation 1 before either local check completes. A proposed S3 single-pointer design needs an appropriate conditional write such as `If-Match`, tested failure handling, and an explicit catalog/reader protocol. The [S3 conditional-write reference](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) describes the object-level precondition; it does not promise a Glue/Athena transaction.
6. No. The matching hash and ID list show agreement among the supplied inputs, not completeness of the real business source. Reconcile with a separately owned register sequence, settlement total or accepted-event ledger for the same time window, and investigate missing IDs before calling the report final. An AI-generated “complete” label cannot supply that evidence.
7. No blind retry. The [overlapping local drill](README.md#let-two-publishers-reach-the-selection-gate-together) allows exactly one writer to select generation 2, and the other sees `stale_generation`. The losing writer must reread the selected run, its authority, source revision and reconciliation evidence. A larger number supplied by that candidate is not proof that the business approved it or that it includes all source facts. Only after a new decision may it attempt a conditional update against generation 2. The SQLite transaction is a local contention model, not a distributed object-store or catalog transaction.
8. The supplied checkout register lists `late` for 50¢ and separate controls of three receipts and 330¢, so the 280¢ candidate is missing an accepted identity and fails both count and total. A same-count, same-total candidate with `other` in place of `late` still fails exact-ID reconciliation. A register row list that omits `late` conflicts with its own closing controls and must be investigated rather than silently redefining the expected population. The fixture demonstrates an independent **comparison path**, not an authenticated producer or evidence that its register captured every real sale. Without that source, completeness remains unknown.

A strong transfer answer preserves the reporting time definition, exact accepted IDs, source revision, reader-selection contract, concurrent-writer guard, old-reader retention and cost/cleanup plan. It labels the local test, AWS service design and future live observation separately.
