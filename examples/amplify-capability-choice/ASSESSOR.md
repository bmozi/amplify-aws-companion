# Assessor notes: capability choice

Internal answer guidance. Do not present these as independently tested learner responses or deployed AWS behavior. A good answer names the changed promise and refuses to treat a category listing, built artifact or successful UI as a live service test.

1. **Menu.** Hosting alone can deliver the static page; no Cognito or database follows from the menu promise. This repository's Terraform owner would declare Hosting and the manual publisher would deliver an artifact. A public route and deep-link load are positive observations; a stale/wrong revision or a failed deep link is a negative observation. Previews introduce branch/build/possibly backend-environment lifecycle decisions. End them explicitly and inspect build, stored artifact and transfer charges; turning off future builds does not delete a hosted site.
2. **Orders.** Auth, Data, client calls and an interface can remain as categories, but a simple sole-owner rule does not express selected shared readers. Model household membership, revocation and authorization at the API boundary; do not widen all authenticated users. Test both linked and unrelated app identities against a real order read/update, and consider a removed household member. Retained records, API calls and identity usage remain cost/cleanup concerns.
3. **Map and AI.** Geo plus the relevant Amazon Location resource is a candidate; the other categories do not follow from address search. Verify Region/eligibility, permissions, address-data handling, map/search calls and current cost before a run. A later tailored explanation needs an authorized path to each order, a deliberately selected model/service and Region, quality/failure criteria, data-handling review and a token/request budget. The current `inspect` function is not an AI model. Do not call generated text a verified delivery promise.
4. **Campaign.** Do not adopt the Pinpoint-backed tutorial as a new-build lab. AWS's [Amplify migration guide](https://docs.amplify.aws/react/build-a-backend/add-aws-services/pinpoint-migration/) says those backed analytics and push paths stop after October 30, 2026; it names Customer Profiles and Kinesis/Data Firehose replacements by function. Its [current setup guide](https://docs.amplify.aws/react/build-a-backend/add-aws-services/notifications/set-up-notifications/) documents `defineNotifications()` for device/profile registration backed by Customer Profiles, with a default Connect instance/domain and push application. The generated API can allow guest credentials, so signed-in-only registration is a policy to enforce and test, not a default to assume. That setup does not itself establish campaign audience, schedule or measurement. AWS's [Pinpoint service guide](https://docs.aws.amazon.com/pinpoint/latest/userguide/migrate.html) says direct push-sending APIs continue under End User Messaging, but stored Pinpoint endpoints/campaigns do not. It says native push is not currently supported in Connect campaigns; a journey can invoke Lambda with push templates. It also says in-app messaging is unsupported after the deadline and unavailable in Connect Customer. A custom authorized page is a distinct design. A build checks code, not device registration, permission, campaign configuration, consent, message delivery or recipient experience. Estimate all replacement-service meters and cleanup separately.

Across cases, reject a resource with two IaC owners. Before an account experiment, require a fresh account/credit/price check, a whole-run estimate within that owner's chosen ceiling, and a chosen credit reserve. Organization-dependent exercises stay design-only here. These assessments remain partial teaching evidence until an independent learner attempts changed cases and a reviewer checks the reasoning.
