# Choose an Amplify path when the promise changes

This is a paper exercise. Start with the [capability atlas](../../docs/AMPLIFY-CAPABILITY-ATLAS.md) and the [first-app lesson](../../reader/BOOK-LOCATORS.md#book-e8d9fb108293da29). For each case, write: (1) the customer promise, (2) Amplify parts and backing AWS services, (3) infrastructure owner, (4) one positive and one negative observation, (5) cost meters and residual cleanup. Do not create cloud resources. The cases are fictional; the [assessor](ASSESSOR.md) is an author key, not learner evidence.

1. **A menu and a misheard promise.** The bakery owner only wants a public menu and opening hours. A contractor says Amplify requires Cognito and DynamoDB. The menu is a static React build, updated weekly. Choose a path. Now the owner asks for a preview of each proposed menu before public publication. What changes, and what might still cost money after previews stop?
2. **Private orders become shared household orders.** A customer must see only their own order. A year later, two explicitly linked household members may view one order, but an unrelated customer may not. The current notebook's `allow.owner()` rule is offered as the complete solution. Explain which original parts can stay and which authorization/data model promises need redesign. Give an API-level denial test, not just a hidden button.
3. **A real map and a tempting catalog.** Drivers need to search delivery addresses on a map. A teammate proposes adding every Geo, Predictions, Analytics and AI Kit category “so the app can grow.” Select the immediate candidate and identify the evidence needed before a live lab. Then the owner asks for a tailored AI delivery-time explanation using private order data. Name the separate authority, model-quality and cost decisions that appear.
4. **A campaign before a deadline.** Marketing wants push notifications and an in-app offer screen. A tutorial uses Pinpoint-backed Amplify APIs and claims a green build means the campaign is ready. It is October 19, 2026. Decide whether to adopt that tutorial as a new lab. Distinguish continued push *sending* APIs, today's Connect Customer Profiles-backed Amplify registration path, and retiring Pinpoint-backed registration, campaigns and analytics. Explain the stated end state for Pinpoint in-app messaging, the separate custom-page design, and what an actual delivered-notification claim would require. Continue with the [three-route packet](../notification-evidence/ROUTE-CHOICE.md).

Try a second pass with Codex: ask it to defend each proposed box with a source file or current official documentation, an owner, an access test and a charge meter. Challenge any row that cites only a library category or says “free” without account-specific evidence.
