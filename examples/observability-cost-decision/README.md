# When cheaper telemetry cannot explain a failed booking

Maya's repair shop pays to collect logs, retain them, scan them in queries and keep a few custom metrics. Her first proposal moves every record to a cheaper log class and shortens retention. A five-day-old booking complaint then arrives. The graph is cheaper, but the customer-read failure has disappeared, and the alarm path no longer works as drawn. [Follow the illustrated signal and cost path](signal-cost-path.svg), or its [phone-sized version](signal-cost-path-phone.svg), before doing the arithmetic. The accepted booking itself belongs in durable application data; a log record is a diagnostic copy, not the authority that decides whether the booking exists.

**First predict.** Which plan can answer all four questions: Was the booking accepted? Did the customer read fail? Did the worker report an error? Was the source still sending records? Which plan can also show that an operator received an alarm? Write your answer before opening the [assessor](ASSESSOR.md).

The [fictional case](case.json) prices three *declared designs*, not an AWS account. Baseline collects 12 GB in Standard. The cheap plan sends all 12 GB to Infrequent Access, keeps critical records for three days and omits two incident records. The bounded plan keeps 2 GB of critical events in a separate Standard group for seven days, sends 10 GB of verbose diagnostics to a **new** Infrequent Access group and narrows the query scan. All invented prices are in the file so you can change one assumption. From the repository root:

```sh
python3 examples/observability-cost-decision/decide.py
python3 -m unittest discover -s examples/observability-cost-decision -p 'test_*.py' -v
```

Read each cost component before comparing totals. The modeled baseline is USD 7.890, the cheap but blind plan USD 3.685, and the bounded plan USD 4.650. Those amounts are invented and omit any unlisted workload or AWS charges. The checker holds the cheap design even though it has the smallest number. It marks the bounded design's *declared* incident path complete, but always reports `live_path_verified: false`. A plan can promise a log, alarm or operator receipt without producing one.

**Change the case.** Copy `case.json` outside the repository. Remove `source_heartbeat` from the bounded plan's `captured_records`, then run `decide.py` with the copy's path. A quiet error chart with no heartbeat cannot distinguish no errors from no records. Next set `critical_retention_days` equal to the five-day incident age. The model holds that boundary: an incident at the edge of retention has no time margin for investigation. Restore the seven-day value before continuing. This conservative teaching rule does not predict the exact moment AWS deletes a record. Restore the heartbeat and change `metric_filter_source_class` to `INFREQUENT_ACCESS`: the metric-filter path must hold. Restore that, then increase `query_scanned_gb` from `6` to `30`; the modeled cost rises to USD 4.770 while the declared evidence path stays the same. Explain why a query's cheaper scan changes the bill model but does not create an absent customer-read event.

Now restore the original values and set `standard_ingest_gb` to `0`, or separately set `custom_metric_months` to `0`. The model holds both cases: this fictional incident assumes critical records are ingested into Standard and its alert uses a custom metric during the modeled period. Zero usage contradicts those assumptions even if the record and receipt boxes remain checked. These are usage inputs, not billed amounts: a real charge can be zero because of pricing allowances or credits. Nonzero estimates still do not prove that a record arrived or an alarm reached a person.

Restore the case again, then set `stored_gb_month` to `0`. The retained-record promise now conflicts with the assumed storage usage, so the model holds the plan. A GB-month combines quantity and time: keeping 1 GB for half a month is roughly 0.5 GB-month before service-specific measurement and pricing details. For this fictional monthly model, records retained for the incident consume some positive storage-time; zero is not an honest estimate merely because a credit might pay the bill. A positive number alone still does not show that the estimate includes every group or reflects actual retention. Explain how you would estimate each group's average retained size over the period, then separately check pricing, allowances, credits and observed usage. Do not treat this simplified calculation as an AWS quote.

**When the cheaper plan is queried much more often.** Restore the original case, then suppose the bounded design's *total* monthly scanned volume grows from 6 GB to 806 GB because an investigative query is repeated. Leave the baseline's stated 30 GB unchanged for this comparison. Predict the new bounded total before setting `query_scanned_gb` to `806` and running the model. Is it still cheaper than the baseline? Which other assumptions would you need to compare the plans fairly? Keep the four incident records and alert path requirements in the decision. This is a fictional sensitivity test: it does not assert that either design will really scan those quantities, or that the five listed meters are a whole AWS bill.

AWS's [CloudWatch Logs class comparison](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CloudWatch_Logs_Log_Classes.html) says Infrequent Access has a lower ingestion price, but it does **not** support metric filters; the class of an existing log group cannot be changed. It also says storage and Logs Insights charges do not differ between Standard and Infrequent Access solely by class. The bounded design therefore keeps its metric-filter source in Standard and creates a different group for verbose logs. AWS's [Logs Insights guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/monitor-application-activity-by-using-cloudwatch-logs-insights.html) advises narrow time ranges and log-group selection because queries charge for scanned data. [Retention behavior](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CloudWatchLogsConcepts.html) belongs to each log group. Verify current service features and selected Region pricing before a real design; the rates here are not quotes.

**Ask Codex to challenge your first answer.** Have it name one cost meter the fixture omits, one missing signal that could make a green chart misleading, and the AWS feature rule that would reject your preferred class. Check the feature rule against AWS docs, preserve your original answer, and decide again yourself. A production choice also needs approved data minimization, access, retention and test records. No AWS log group, alarm, query, notification or charge was created for this lab. Organization-wide collection stays design-only in this exercise.
