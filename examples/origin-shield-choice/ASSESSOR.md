# Origin Shield assessor: arithmetic is a starting point

Read after attempting the [worksheet](README.md). The public guide has 100,000 fictional viewer requests and 13,000 declared regional misses: `13%` of viewers in this simplified worksheet. Without Shield, 13,000 × USD 1.20 / 1,000 = **USD 15.60** of modeled origin work. With Shield, 3,000 × USD 1.20 / 1,000 = **USD 3.60** of modeled origin work, plus 9,000 × USD 0.05 / 10,000 = **USD 0.045** of invented incremental Shield charges. The modeled total is **USD 3.645**, or **USD 11.955 less** than the no-Shield origin-work amount. Keep the extra decimal until the bill-level rounding rule is known; this is not a forecast to the cent.

The public guide's modeled break-even origin-work rate is USD 0.045 × 1,000 / 10,000 = **USD 0.0045 per 1,000 avoided requests**. The invented USD 1.20 input is above that threshold. This comparison omits transfer, logs, latency, operational work and the real billing rules.

The private invoice has 20,000 requests and no shared cache. Both paths still ask the origin 20,000 times, costing USD 24.00 in invented origin work. The additional 20,000 Shield requests add USD 0.10, so the modeled total becomes **USD 24.10**. More importantly, a person-specific invoice cannot be placed in a shared cache merely to improve this number. The customer's data boundary decides cache eligibility before the price comparison.

Changing the public guide to **13,000 origin requests with Shield** removes the assumed consolidation. Origin work remains USD 15.60 and the declared incremental charge adds USD 0.045. A changed cache key can fragment copies and lower hit opportunity; a missing identity-dependent value can disclose one person's response to another. Neither mistake is fixed by adding a deeper cache. An origin move requires a new Region/latency, traffic and price review; do not preserve the earlier saving as a fact.

If the changed case also assumes **zero billable Shield requests**, the added Shield charge is zero and both modeled totals are USD 15.60. Because neither option avoids origin requests, changing the origin-work rate changes both totals equally: they tie at every rate. The threshold formula divides by zero, so the calculator returns `null` for the threshold and explains the tie separately. With no avoided requests but a positive incremental charge, the Shield option remains more expensive at every rate. Neither scenario establishes the charge for a real distribution.

The real decision needs observed requests at each relevant layer, cache-key and TTL correctness, origin request/byte cost, Shield billable request counts, latency and error distributions, transfer and log meters, security controls and a rollback comparison. AWS notes that Origin Shield can be less suitable for dynamic or infrequently requested content and adds request charges. This fixture measures none of that and makes no deployment choice.

For the gRPC changed case, do not reuse the guide's Shield consolidation assumption. [AWS's Origin Shield documentation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html) says gRPC requests are proxied directly to the gRPC origin without passing through Origin Shield, even when Shield is enabled for the distribution. Estimate and observe that workload's origin requests and capacity separately; the worksheet does not model gRPC behavior, service eligibility, or its whole bill. Other traffic on the same distribution needs its own path and cache analysis.
