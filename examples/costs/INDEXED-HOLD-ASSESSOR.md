# E11 assessor: price the hold, not just the lookup

Read this after writing the E11 ten-hold comparison. It is author reasoning for a fictional workload, not a scored learner attempt or an approved AWS run quote. The source being assessed is the A03 [manual scan and sparse-index implementation](../../architectures/reliable-workflows/README.md).

Imagine ten set-aside slips. The due-hold index is a tray containing a small card for each still-held slip. Asking the tray which slips are due is one activity; adding and removing its cards is another. The table still holds the real slip and the remaining-seat count. A faster lookup does not move the authority into the tray.

| Work in the stated case | Scan discovery | Index-query discovery |
| --- | --- | --- |
| Create ten indexed holds | Base-table transactional work **and** index inserts; retain indexed bytes until each hold ends | The same work; selecting the query later does not create the index writes |
| Find due candidates once | Strong base-table scan reads; each request evaluates at most five items **before** filtering, so unrelated items and empty-result pages can consume reads | Eventually consistent GSI query reads; each request asks for at most five due keys, but follow its cursor and account for lag or stale keys |
| Decide and release | Strongly reread a returned base hold; a conditional transaction may return one seat and remove the index key | The same authoritative read and conditional transaction; an index result alone never releases a seat |
| Repeat and finish | A later pass may find newly due or previously missed holds; include Lambda duration, logs, retries and cleanup | Repeat for index lag, and retain the table scan for older holds missing the index key; include the same operating meters |

Ten successful acquisitions imply ten **logical** index insertions in this source. If all ten holds later leave `HELD`, their terminal updates remove ten index entries. That is not a claim of exactly twenty billed write request units: item size, additional writes, attempts and AWS billing rules still matter. A `KEYS_ONLY` projection saves some projected bytes; it does not make index storage or updates free. [AWS explains GSI write and storage behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html).

For an index-only discovery pass, the worksheet's scan-read increment may be zero. For a scan-only pass, its `due_gsi_reads` quantity may be zero. **Neither choice makes `due_gsi_writes` or `due_gsi_storage` zero when this run creates indexed holds.** If the operator uses both paths to reconcile old records, count both kinds of reads. The scan's filter is applied after DynamoDB reads items, and a page with no matching hold can still have a cursor and a read cost. [AWS Scan behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html).

A sound estimate names the number and size of table and index items, acquisition and terminal transactions, due-discovery pages and repeated passes, base rereads, Lambda invocations/duration, logs and time until resource removal. It also retains the earlier A02 queue-polling workload if this is the same stack/run. Fill the three stable index meter rows in the [worksheet template](worksheet.json), choose its `hold_mode`, verify current regional rates and review every other cost driver. The older [dated subtotal](ohio-core-services-2026-10-18.json) omits the index and selected hold activity; reproducing its arithmetic does not make it a complete run estimate.

The [priced Ohio teaching scenario](ohio-indexed-hold-2026-10-19.json) supplies all eleven listed meter rates and keeps its run review pending. The repository's Decimal estimator returns USD 0.1836716875000 before and USD 0.3673433750000 after its 100% contingency. If the SQS assumption changes from 400,000 to 200,000 requests, those values become USD 0.1036716875000 and USD 0.2073433750000. If the GSI write assumption then changes from 5,000 to 10,000 units while the lower SQS assumption stays, they become USD 0.1067966875000 and USD 0.2135933750000. These are script results for changed *assumptions*, not observed savings or a cap. A learner should identify the SQS and GSI write rows as the only direct arithmetic changes and still challenge item size, retries, backfill and cleanup before using the figure operationally.

The best answer does **not** choose scan or query solely by a dollar total. It considers table size, due-hold density, tolerated index lag, required reconciliation, read/write pressure, one-partition scale limits and the business deadline. The default lab has no scheduler; an opt-in source candidate exists but has no exact real-time release guarantee or live AWS evidence. A later live experiment needs a scoped non-root identity, a complete estimated run within the account owner's chosen limit, an appropriate verified credit reserve and cleanup evidence. This paper exercise verifies none of those account facts.
