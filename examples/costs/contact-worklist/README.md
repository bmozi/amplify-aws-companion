# A02 contact worklist: count the quiet reads

Imagine a clerk walking every shelf to find overdue requests. The shelf walk costs effort even if only one folder matches. The A02 contact worklist currently does this with **manual**, strongly consistent DynamoDB scans. `Limit=20` means at most 20 **evaluated** items per page, before filtering to requests or escalations. An empty result may still have a continuation cursor. This exercise counts the table work that is easy to miss; it is not a deployed schedule or a bill forecast. [AWS Scan guide](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html).

Run from this directory: `python3 lab.py scenario.json`. Change the ten counts in the JSON to represent **the whole intended run**, including repeats after a lost reply and internal transaction-conflict retries. Run `python3 -m unittest test_lab.py` to check the model. The checked-in fictional case counts four first-contact calls, six due-scan pages evaluating 120 items, eight overdue requests and eight transaction attempts, and three worklist pages evaluating 60 items. The worklist returns six escalations, two of them open. The output is **196 modeled** table read request units and **40 modeled** write request units. It is **not** 196 DynamoDB API calls; the result separately lists 16 `GetItem`, nine `Scan`, and 12 `TransactWriteItems` calls.

The combined **196 reads and 40 writes span two different boundaries**. The optional cloud handler exposes only `check_due` and `read_open`: this fixture allocates **188 read and 32 write units** to that candidate. The remaining **8 read and 8 write units** come from four `record_first_contact` calls in the separate local domain exercise. The cloud handler has no contact-record action. Treat the split as an allowance under the assumptions below, not a measured charge or a complete cloud estimate.

Trace those numbers to [`domain.py`](../../../architectures/reliable-workflows/src/domain.py):

| Action | Source calls | Simplified capacity contribution |
| --- | --- | --- |
| Record first contact | Strong request `GetItem`; one-item conditional write transaction; strong contact `GetItem` | Two read units per call and two write units per transaction attempt |
| Check contact due | One strong `Scan` per page; one two-item transaction for **each overdue request returned**, even if an earlier pass already opened it | A teaching allowance of one read unit per evaluated item and four write units per attempted transaction |
| Read open contacts | One strong `Scan` per page; contact `GetItem` for each returned escalation; request `GetItem` if no contact exists | The same scan allowance, one read unit per escalation and one more per open escalation |

The arithmetic assumes each scanned or fetched item is at most 4 KiB and each transaction item at most 1 KiB. For scans, it deliberately allows one unit per evaluated item, or one unit for an empty page; **this is a planning simplification, neither a lower nor an upper bound on AWS's actual page charge**. AWS says read capacity depends on evaluated item sizes, not the number returned after a filter; empty or sparse table scans can also consume capacity. Transactional writes have prepare and commit work, including a canceled conditional attempt. Larger items, more scan work, retries, GSI updates, contention, and pages beyond the supplied counts can increase usage. [AWS read/write operations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html), [transaction capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html#transaction-capacity), [Scan guide](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html).

The optional private `check_due` and `read_open` handler now requests DynamoDB `ReturnConsumedCapacity='TOTAL'` for its scans, follow-up gets and transaction attempts. Each successful handler response includes a `capacity_observations` array with an operation label, outcome, `reported` flag and any returned numeric capacity fields as decimal strings. The array omits table keys, customer request text and item bodies. The separate local `record_first_contact` fixture accepts the same optional trace, but the private cloud handler still does not expose a contact-recording action. An absent `ConsumedCapacity` object remains **unreported**, not zero; a canceled transaction is marked `canceled`, because DynamoDB may consume capacity even when a condition fails. [DynamoDB transaction capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html), [ReturnConsumedCapacity](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html).

For a future authorized run, keep the response for **every page and retry**, including an empty filtered page with a cursor. Sum only returned numeric read and write fields for the same selected table and action path; list every `reported: false` operation separately. A total-only field does not by itself split reads from writes. Do not fill a missing amount with the worksheet estimate or call a partial sum a bill. A failed Lambda invocation may not return a handler receipt at all. Reconcile with DynamoDB metrics, the selected capacity/billing mode, other application calls, and later attributable billing before judging the estimate. A projected scan can omit request text from the response while still reading evaluated items; AWS says a projection does not reduce scan capacity. [AWS Scan guidance](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html). Moto tests prove only the request/trace shape, not actual AWS capacity or charges.

This small script therefore supplies **illustrative demand under stated item-size assumptions**, not a quote or bound. If the worklist grows, consider a purpose-built sparse access path after comparing index write/storage cost and consistency behavior; the current scan is useful for a tiny teaching table but should not silently become a frequent cloud poller.

## Practice reading page receipts without cloud access

Run `python3 reconcile.py synthetic-receipts.json`. The invented file has a two-page due check, a one-page open-worklist read, and a repeated due check after a lost reply. The repeated check is a **new pass** because the table was read again; four handler responses do not mean four complete business requests. The result reports 20 returned read-capacity units and 2 returned write-capacity units. Its 23.5 returned *total* units overlap those read/write fields, so do **not** add 23.5 + 20 + 2. One canceled transaction returned only a 1.5 total and cannot be assigned to read or write from this receipt; another canceled transaction reported no capacity at all. The 2 write units are therefore a **partial observation**, not a whole-run write total.

Try deleting the second due-page invocation but leave the first page's `next_cursor`. `supplied_page_chains_complete` becomes false. Try changing the second page's `requested_cursor`; the script rejects the broken handoff. Add a `failed_no_response` invocation with no `response` to represent a lost Lambda result; that pass stays incomplete. The tests include those changes. The script prints only pass identifiers, action names, counts and numeric sums; it does not print cursor keys or any `customer_text` in a response. Use invented data only. The fixture is a teaching example, **not an AWS receipt**.

Even `supplied_page_chains_complete: true` proves only that each *supplied* pass ends without a cursor. It cannot discover a page, pass, retry or failed invocation missing from the input file. `supplied_numeric_observations_complete` also requires no unreported operation among those supplied. Neither flag reconciles a bill, proves a hard spending limit, or authorizes deployment. A live operator would need an independent invocation log, table identity and time window, DynamoDB/service metrics, the account's billing mode and attributable charges to close the gap. [AWS Scan API](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Scan.html), [DynamoDB transaction capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html#transaction-capacity).

## Put the whole illustrative path beside the small contact subtotal

The [dated Ohio public-price worksheet](../ohio-contact-worklist-2026-10-26-utc.json) connects this fixture to the other A02/A03 meters without making it a live-run ticket. From the repository root, run:

```sh
python3 scripts/estimate-lab-cost.py examples/costs/ohio-contact-worklist-2026-10-26-utc.json
python3 scripts/refresh-contact-worklist-prices.py --check examples/costs/ohio-contact-worklist-2026-10-26-utc.json
```

At the recorded public paid-tier Ohio rates, the **invented** 17-row workload totals USD 0.184434487875 before contingency and USD 0.368868975750 after doubling. The six contact-specific rows contribute only USD 0.000762800375; the base SQS row contributes USD 0.16 because it assumes **400,000 requests**, including a deliberately severe quiet-polling case. A small contact subtotal is not a small *whole system*. The nine contact Lambda invocations, 11.25 GB-seconds and two 0.001-GB log buffers are assumptions, not measurements. The account, full Terraform plan, actual item sizes, operator, repeated runs, data transfer, taxes, shared resources and cleanup are unresolved. The worksheet retains `run_review.status=pending` and every named cost-driver decision as pending; the arithmetic does not establish that any chosen run limit or reserve is satisfied in a real account.

The estimator now prints `review_signal` immediately after the totals. In the checked-in case it lists seven pending drivers and `deployment_permission: not_granted_by_estimator`. For a changed case, copy the JSON outside the repository, mark its status `complete_live_run`, fill a made-up account ID and mark every driver `priced` with a reason. A typed claim is evidence of what the worksheet says, not evidence that an AWS account, Terraform plan or charge was reviewed. Choose a bounded limit and reserve from your own account terms and goals before any real work.
