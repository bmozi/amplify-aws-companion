# Assess the contact-worklist cost decision

Give the learner [`scenario.json`](scenario.json) and ask them to run the offline model. Then change the case: the first due check reply is lost, so the operator repeats the complete check; the table has also grown to 400 small items because old outbox and hold records remain. They must state what to recount before any cloud run, explain why `Limit=20` and the `kind` filter do not make the check cheap, and identify the point at which an indexed discovery path might be justified. A successful answer does **not** promise an exact DynamoDB bill from this script.

Look for these elements:

1. Count every page of both passes, including pages that return no requests; do not count only eight matches or assume a single page. The current `Scan` is not a snapshot of the whole table and needs cursor traversal.
2. Count repeated transaction attempts for overdue requests. A conditional failure or duplicate escalation can still consume transaction capacity. Reconcile any lost reply against the worklist before retrying a business action.
3. Recalculate Lambda invocations, duration, logs, table reads/writes, other A02/A03 work, retries, storage and cleanup. Use the current regional price and verify credits and a reserve for the selected account. Compare the complete estimate with that account's chosen run and reserve limits; a low subtotal alone is insufficient.
4. Compare a sparse index's extra storage and write cost plus eventual consistency and migration with the repeated full-table scan. An index changes the tradeoff; it does not remove the need for a current whole-run estimate or source-level correctness checks.
5. Keep the proposed cloud run pending until a scoped role, exact plan, complete priced review and operator/teardown evidence exist. Local model output is not AWS usage evidence.
6. If handed sample `capacity_observations`, separate returned numeric fields from `reported: false` operations. Keep canceled transactions and lost Lambda replies in the uncertainty list; neither a missing field nor a projection proves zero charge. Explain why one page's receipt cannot stand in for the whole run or the later bill.

7. Run `reconcile.py synthetic-receipts.json`, then break a cursor handoff, omit the last due page, and replace it with `failed_no_response`. The learner should explain why the first change is invalid and the latter two leave an incomplete supplied pass. Ask whether 23.5 total plus 20 read plus 2 write should be added, whether the two canceled operations have known costs, and whether a missing pass can be detected from this file. Expected: no double addition; one canceled attempt has a total-only 1.5 with unknown read/write split, the other has no numeric report; an entirely absent pass is invisible to this file. The two completeness flags are limited to supplied records, and `bill_reconciled` remains false.

8. Separate the optional cloud handler from the local contact-record fixture. The original combined case reports 196 illustrative reads and 40 writes; only 188 reads and 32 writes belong to the handler's due/open actions. Four local `record_first_contact` calls account for the other 8 reads and 8 writes. With ten local contact calls and attempts, the combined result changes to 208/52 while the cloud-handler allowance stays 188/32. A response that copies 196/40 into the six optional-handler worksheet rows has crossed the boundary. The 188/32 split is still incomplete without Lambda duration, logs, base workload and cleanup.

9. Use the dated [Ohio teaching worksheet](../ohio-contact-worklist-2026-10-26-utc.json) and its estimator. The expected fictional subtotal is USD 0.1844344878750, doubled to USD 0.3688689757500 by the stated 100% contingency. The six contact rows add USD 0.0007628003750; the base SQS stress row alone adds USD 0.16. The learner must identify the 400,000-request assumption and at least one omitted or unreviewed whole-run driver before making a cost judgment. The `--check` command confirms recorded public offer identity and authored quantities at the time it runs; it cannot approve credits, account budget, Terraform plan, operator or cleanup. Changing the local contact-record count alone must not change the optional handler's six quantities. Do not accept “under the run ceiling” as a deployment answer while `run_review.status` and driver decisions remain pending.

10. Read the estimator's `review_signal` as a separate claim from its decimal total. The original file has seven pending cost drivers, no filled account field and no deployment permission. A synthetic copy that declares `complete_live_run` and fills every driver still receives `not_granted_by_estimator`: those edits do not verify the account, terms, workload, exact plan or cleanup. A reader's own run needs a spending limit and reserve chosen from that account's current terms.

**Codex prompt for a learner:** “Trace `record_first_contact`, `check_contact_due`, and `read_open_contacts` in `domain.py`. For this changed case, list every DynamoDB call, the assumptions needed to turn calls into request units, and anything the model cannot bound. Challenge any claim that a filter removes read charges. Do not use AWS credentials.” Check Codex's answer against the source and the [AWS Scan](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html) and [transaction-capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html#transaction-capacity) documentation. Agreement with an AI answer is not independent billing evidence.
