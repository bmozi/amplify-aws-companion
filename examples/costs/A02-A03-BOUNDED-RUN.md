# A02/A03: price the quiet queue as well as the busy worker

The later A02 **manual contact worklist** adds strongly consistent table scans and conditional transactions. Use the [cloud-free contact-worklist exercise](contact-worklist/README.md) to count its source-traced read/write demand, then review that allowance in the whole-run worksheet without double counting. The dated examples below predate the contact-worklist path and do not include its usage. The exercise is a planning simplification under small-item assumptions, not a quote or an approved cloud run.

Imagine a clerk checking an empty mailbox. No customer letter arrives, but each check is still work. In the A02/A03 lab, Lambda watches the SQS work queue through an event-source mapping. The mapping's maximum concurrency is two, matching the worker function's reserved concurrency. That bounds simultaneous worker execution. AWS says this maximum-concurrency setting also disables the lowest-traffic polling optimization, so an almost-empty queue can still generate SQS requests. [Lambda SQS scaling](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-scaling.html), [SQS request pricing](https://aws.amazon.com/sqs/pricing/).

## A reviewable component scenario

The [dated Ohio rate worksheet](ohio-core-services-2026-10-18.json) models one two-hour exercise. It assumes 500 Lambda invocations with ten seconds each at 128 MiB, 5,000 DynamoDB write units, 10,000 read units, 400,000 SQS requests including polling, 0.01 GB of ingested logs and small retained data/log quantities. These are **planning quantities, not AWS quotas or measured usage**. The 400,000 SQS calls deliberately stress the estimate; AWS does not promise that this is an upper bound. The rates were recorded from AWS's Price List API for `us-east-2` on October 18, 2026. No Free Tier allowance or account credit is subtracted. Recheck every selected rate, applicable feature and service eligibility before a live run.

Run `python3 scripts/estimate-lab-cost.py examples/costs/ohio-core-services-2026-10-18.json` from the repository root. Decimal arithmetic yields USD **0.1801716875** for the listed service meters and USD **0.3603433750** with the worksheet's 100% contingency. The SQS line alone is USD **0.1600000** in this scenario. A simple 10,000-request guess would have priced that line at USD **0.0040000**. The difference illustrates why “only a few messages” is not the same as “only a few queue API calls.” This is a **core-service subtotal**, not a complete approved USD 5 run estimate or a spending cap.

The **default** Terraform source declares one DynamoDB table **with a sparse `due-holds` global secondary index**, two SQS queues, four Lambda functions, four log groups, one Lambda/SQS mapping and IAM roles/policies. The opt-in scheduled tick adds a dedicated function/log group/role, one schedule group and schedule, two failure queues, one asynchronous failure configuration and four alarms. Neither mode has a VPC, NAT gateway, load balancer, public API or provisioned Lambda concurrency; A02 dispatch remains manual. The earlier core subtotal predates the index and is not a quote for this revised stack. Include index storage, query reads and extra writes plus any applicable data transfer, tax, existing shared-resource usage, additional retries, extra runs, storage after the exercise and cleanup time in the real run record. If any meter cannot be priced or bounded for the selected account and Region, leave the live decision pending; do not fill the gap with zero. AWS says SQS traffic between resources in the same Region has no SQS data-transfer charge, but a changed route or service combination needs its own review. [SQS pricing](https://aws.amazon.com/sqs/pricing/).

The current A02 sender does not set `MessageGroupId`, so this worksheet's SQS line models ordinary standard-queue requests, including polling. Do not transfer that line unchanged to the [A10 SQS fair-queue design](../tenant-fairness/SQS-DECISIONS.md). AWS says grouped-message actions on a standard queue can incur both standard and fair-queue request charges; select and price the additional fair-queue meter before any such live experiment. A `MessageGroupId` would also be a tenant label to derive from verified authority, not a substitute for it. [AWS SQS fair-queue pricing](https://aws.amazon.com/sqs/pricing/), [fair-queue behavior](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html).

**Optional A03 hold sweep changes the run workload.** The new private `sweep_due` action strongly scans up to five *evaluated* table items per invocation, then may run one conditional three-item release transaction per due hold. A filter that returns zero holds still consumes reads; a continuation cursor means more pages and more requests. The checked-in worksheet was built for the original immediate-reservation live harness and does **not** price an authorized hold-sweep trial. Before including this action in a live run, revise read/write quantities, Lambda invocations and duration, retries, log volume, retained terminal records and the number of complete passes. Price the whole intended run including the existing queue workload and cleanup, and review the changed plan and role permissions. For the author's personal trial account, the standing limits are an estimate at or below USD 5 and at least USD 100 verified reserve; readers must choose limits appropriate to their own account. Neither limit is an automatic spending cap. No schedule creates background sweep calls. [DynamoDB scan capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Scan.html).

The optional `query_due` path queries at most five due entries per page from the new GSI and then strongly reads each returned base record before the same release transaction. That can reduce unrelated table reads, but index queries are eventually consistent and the index adds storage and write work even when no operator runs `query_due`. A newly due item may be missed on one pass; a stale terminal item may be returned. The old scan remains a migration/reconciliation path. Price index creation/backfill if applying to an existing table, index bytes and write/request units, query pages, base reads, transactions, repeated passes, logs and cleanup. The generic template keeps unpriced GSI rows, and the older dated core-service worksheet omits them. The priced teaching example below still lacks a completed live-run review; none of these files approves deployment. [AWS GSI behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html).

The manually invoked `query_due_tick` can read three five-entry index pages in one Lambda call. A 16-hold test needs a second call; a failed second page can leave earlier releases committed. The [schedule decision packet](../reservation-cloud-transition/SCHEDULE-DESIGN.md) compares two future recurring routes and lists separate Scheduler delivery and Lambda execution failure records. **The default plan has no schedule or tick-failure queues.** Its manual worksheet has no Scheduler, new SQS, alarm or recurrence meters. The opt-in [scheduled worksheet](scheduled-due-tick-worksheet.json) adds those rows, and the runner matches `schedule_mode` to the Terraform flag before plan/apply. Do not select `query_due` in a manual worksheet and infer that a scheduled run has been priced. A two-hour once-per-minute planning ceiling with both boundaries counted is 121 occurrences and 363 index pages before retries; this is scenario arithmetic, not a service or billing cap.

### Seven decisions before changing `pending`

The source can narrow a question without answering it for the selected account. Use this ledger alongside the worksheet rather than copying `not_applicable` into every field:

| Worksheet driver | Source-grounded observation | Evidence still needed for this run |
| --- | --- | --- |
| Data transfer | Current Terraform declares no VPC/NAT or public ingress; SQS documents no SQS transfer charge for same-Region resources. | Inspect the exact plan and harness route for added endpoints, cross-Region or internet egress; price any changed path. |
| Tax | The public offer rates do not include an account tax decision. | Verify the account's billing/tax treatment for the selected purchase context; record the method or amount. |
| Shared resources | This source declares its named table, queues, functions and logs. | Inspect current account inventory and the exact plan for shared bootstrap, preexisting resources or other active meters. |
| Retries | The 500 Lambda calls and 400,000 SQS requests are invented stress quantities, not limits. | Bound selected harness attempts, queue retry/redrive behavior and a stop condition; revise all affected meters. |
| Repeat runs | The worksheet models one two-hour exercise. | Decide how many attempts the operator may perform and price each, including failed/restarted plans. |
| Retained storage | Queue retention, one-day log retention and on-demand table/GSI storage can outlast handler expiry. | Name the deletion owner/deadline and price the time until verified removal, including failed cleanup. |
| Cleanup delay | `expires_at_epoch` stops handler work; it does not run Terraform destroy. | Record the actual destroy procedure and deadline, then verify resources and later billing after execution. |

Every row remains **pending** for a live run. A realistic scenario and a 100% arithmetic contingency do not turn unbounded usage or an unknown credit balance into a guaranteed cost.

The table and GSI source each set on-demand maxima of 20 read and 20 write request units per second. AWS calls these [best-effort throughput targets](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/on-demand-capacity-mode-max-throughput.html); bursts can exceed them. They do not cap total requests over a two-hour run or replace the USD 5/credit-reserve gate.

## Which tradeoff are we making?

We keep the mapping's maximum concurrency of two for this candidate because the worker also reserves two concurrent executions. Removing the mapping cap may allow AWS's quieter polling behavior, but it can let the poller seek more concurrent work than the function can run, creating throttling and retries. This is an **inference from the configured limits and AWS's scaling behavior**, not a measured AWS result. Compare both configurations only in a separately authorized, bounded experiment, with queue-request counts, throttles, delayed work, failed messages and customer-level completion recorded. Do not change the limit merely because one line of a model looks high.

## Stop, remove and reconcile

The intended exercise has no public entry point and uses only synthetic requests. Before plan/apply, record the selected non-root role, current account-plan and credit terms, exact Region, rate date, complete estimate, account-specific run ceiling and reserve, operator, and cleanup deadline. The author's account retains its USD 5 estimate ceiling and USD 100 reserve; these are not universal reader defaults. The runner refuses a handler expiry more than two hours away and checks that this planned work end precedes the reported plan expiration. **Handler expiry does not delete anything.**

Stop on an unrecognized resource, unexpected invocation/polling growth, failed verification or inability to complete cleanup. Do not repeat the live harness simply to get green checks without updating the estimate. After the exercise, run the specific Terraform destroy path, inspect state **and** query the exact table, queues, functions, mapping, log groups and roles; for a scheduled run also check the schedule group/schedule, both failure queues, four alarms and async invoke configuration. Record retained resources and their owner. Refresh credits and later reconcile attributed pre-credit usage after billing catches up. A small immediate net bill is not proof that the run was free.
