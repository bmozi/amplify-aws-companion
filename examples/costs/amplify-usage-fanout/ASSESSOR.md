# Assessor notes for the fictional visit fanout

1. With 80,000 visits and 500,000 hosted bytes per visit, the model calculates 40 GB of Hosting transfer, so both the older 5 GB worksheet and the separately revised 0.15 GB smoke scenario fail as forecasts. The same multiplication increases note lists, saves, uploads, inspections, API responses, new storage and logs. Leaving 25 distinct signed-in users unchanged deserves a challenge; a different audience or repeat-visit pattern could change Cognito's relevant count. The run could still incur retained backend and Hosting costs before and after these visits.
2. Doubling `lists_per_visit` from 2 to 4 at 100 visits makes 400 lists, 435 assumed AppSync operations and 400 assumed DynamoDB read units. Saves, uploads, inspector invocations, live connection minutes, delivered updates, hosting bytes and distinct-user input do not change in this *model*. More API response transfer is calculated because the model multiplies all AppSync operations by one assumed response size. A real app could issue different calls, page results, retry or cache; those require observation.
3. Removing `log_bytes_per_inspection` makes the plan incomplete and the local calculator refuses it. Setting it to zero would be a **claim** that this run produces no charged log bytes, not evidence. Inspect actual log configuration, retention and measured volume before reviewing a live cost record.

The original plan and `lab.py` are quantity teaching tools. They do not compute AWS dollars, measure the current account, decide whether a free allowance applies, authorize publication or prove the reader can transfer the idea. The publisher's positive backend subtotal and seven reviewed component statuses are a separate preflight; even a passing record remains a human forecast, not a spending cap. Use [AWS's service pricing pages](README.md) and actual resource/configuration evidence when converting these quantities into a bounded real run.

5. The bundle exercise measures the exact local entry HTML and directly referenced script/style files, then counts the complete local static file set separately. Adding a linked file changes the entry total and adds its digest. An unlinked file leaves the *entry* total alone but increases the all-file raw total; a later page may fetch it. An external CDN reference moves bytes outside this local build and requires a separate transfer/source review; treating it as free would be a false estimate. Local gzip is one possible encoding, not an observed Hosting response. The older 500,000-byte smoke guess was below the current complete 1,344,387-byte raw set. The revised 1,500,000-byte input exceeds that local set, and the publisher preflight checks it against the exact built ZIP's raw byte count. That still cannot cap visits, retries or backend work, or establish a whole-run budget pass. A browser network trace, served compression headers, route/cache behavior and backend calls would provide stronger evidence.

6. The local Chrome probe is a bounded browser trace, not a cloud measurement. A linked stylesheet adds a request and positive first-visit response-body bytes; a same-tab reload can reuse cached CSS while revalidating the page. The October 25 static entry transferred 284,455 local response-body bytes on first load, compared with 1,344,387 raw bytes across all static files. Zero body bytes on the repeat is **not** zero network bytes: the `304` response has headers. The publisher's all-file ZIP check is a conservative human-review rule, not a factual minimum per visitor. Do not lower the pending planning input from this trace alone: it omits Amplify's actual response encoding/cache rules, other routes, signed-in API calls, visitor variation, retained resources and a hard audience cap. An actual branch trace, bounded use scenario and billing reconciliation would answer different parts of the question.
