# Assessor: multi-cluster container recovery

1. **Stale data:** A running target cluster cannot meet the five-minute confirmed-work-loss promise with a known 12-minute-old checkpoint. Hold or obtain explicit business authorization for a degraded promise; never silently turn a stale replica into authoritative booking data. Measure the actual confirmed-write boundary, not a generic replication heartbeat.
2. **Sleeping capacity:** Start the timer at the defined failure/detection boundary and stop it at a correct customer response. Include operator decision, scaling, image retrieval, dependency readiness, key/secret access, routing and client cache behavior. A cluster API reporting ready is an intermediate receipt. Warm capacity trades recurring expense for a faster candidate path.
3. **Returning writer:** Require an authoritative epoch/lease/fence or equivalent business write gate that every booking effect checks. A DNS change affects some new client routing but does not necessarily stop existing connections, queue consumers or background workers. Failback must re-establish one writer and reconcile effects made during recovery.
4. **Image and key:** Compare the exact reviewed image digest and relevant configuration in both Regions. A health endpoint may miss application data and decryption. Test one permitted booking read/write through the target identity and one denied neighboring customer record; verify the intended key grant and audit evidence without exposing key material.
5. **Per-app shift:** Application-specific health and routing may keep the healthy photo path in its original Region. Check shared identity, data, network, ingress and control dependencies before assuming the applications are isolated. [AWS EKS routing example](https://aws.amazon.com/blogs/containers/implementing-granular-failover-in-multi-region-amazon-eks/).
6. **Location and cost:** The prohibited Region is out regardless of its warm capacity. A permitted target or slower recovery option needs a new measured customer promise and full-life estimate. A backup of cluster resources and persistent volumes can support a restore pattern, but it is not a live tested booking path. [AWS EKS backup/restore example](https://aws.amazon.com/blogs/containers/cross-region-disaster-recovery-for-amazon-eks-using-aws-backup/).
