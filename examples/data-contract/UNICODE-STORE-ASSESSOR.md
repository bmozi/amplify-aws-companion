# Assessor: the durable label boundary

The learner should predict two rows in the raw-only table. Its `UNIQUE` rule compares the raw strings, and the composed and decomposed spellings are different. Both separate connections can see an empty canonical-key lookup before any insert. That observation does not reserve a key. The first insert into the second table succeeds; the second reaches the same `label_key` and SQLite rejects it. Only supplier A survives. A lookup with B's spelling resolves the label key to A, but never authorizes B to impersonate A.

A strong changed-case answer distinguishes three responsibilities: the business defines whether this *label* uses NFC; each write path computes or validates the key; the database enforces uniqueness at the write. If an old table has both spellings, adding a unique canonical-key index will encounter a collision. The owner must decide whether these are duplicate labels for one supplier or two real suppliers that need different labels. An automated merge could transfer data or authority incorrectly. A changed Unicode-version or field rule also calls for inventory and migration before switching keys.

For a bypassing writer that inserts a raw label with an unrelated `label_key`, the current table can no longer guarantee the intended raw-to-key relationship. The demo deliberately leaves this as a production-design issue: centralize key generation in a trusted write path or use a database-supported deterministic rule, constrain who can write, and test migration and direct-write behavior for the selected service. This SQLite drill does not test real simultaneous requests, distributed databases, every Unicode version, AWS permissions, or learner performance.
