# Assessor reasoning: owner and revision are different gates

Use this after the learner predicts and runs [the loopback exercise](README.md#two-authorized-clients-one-http-record). The script's successful local request path is evidence about this one fixture, not an AWS or production security result.

The missing token is 401; Lee's recognized but nonowner token is 403. A correct part ID or current ETag does not turn Lee into Maya. A missing ETag is rejected with 428 by this fixture; a weak or malformed tag is rejected with 400 because the exercise accepts only one quoted strong revision. A boolean price is also 400 under the earlier data contract. These statuses are outputs of the included narrow service, not claims that every real API must use exactly this error mapping.

Two Maya clients start from GET's ETag `"1"`. The barrier causes both accepted requests to reach the update edge. The one-statement SQLite predicate allows one row change; the second sees zero matching rows and receives 412. Which edit wins is not fixed. The later GET returns ETag `"2"`, and an explicit new update combines the independent missing change into revision 3. The SQL's owner condition is defense in depth alongside the preceding owner read. The fixture has no external writer and makes no distributed-transaction claim.

The handler constructs an update from its initial read, so it must also reject a supplied tag that differs from that read's revision. Otherwise a guessed future tag could become current after a concurrent write, allowing a conditional update to apply values derived from the older read. Matching the initial read is necessary but not sufficient: the conditional SQL is still required to detect a change after that check. The controlled future-tag hook tests this ordering locally; it does not establish the behavior of an AWS datastore or other writers.

If both clients select different prices, an automatic retry would choose a winner without business review. Show the current and proposed values to an authorized person. If a reply is lost, a 412 on retry proves only that the presented ETag is stale; the original PUT might have succeeded, or another write might have advanced the record. A separate request record can help resolve that question if the system binds a stable request ID to the caller, operation and request contents and records the outcome consistently with the mutation. Reusing an ID for different contents must not silently return an unrelated result. If the record is missing, expired, or its consistency with the update is unknown, the outcome can remain unknown; absence alone is not proof of failure. The fixture does not implement this request record or lost-response recovery. An out-of-band write that does not increment the revision makes the strong ETag cease to represent the current body; delete/recreate at revision 1 risks an ABA-style false match. The local fixture does not implement either path.

Strong learner work explains all three independent questions: **Who is the caller? May that caller edit this part? Is this still the revision the caller saw?** It also states that fixture tokens do not prove real identity and a localhost SQLite race does not verify AWS IAM, network exposure, cloud database isolation, true load, lost-reply recovery or customer behavior. No independent learner attempt has been recorded.
