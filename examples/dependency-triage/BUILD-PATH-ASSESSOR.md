# Assessor: follow the build path

1. **No proven customer-request path.** The trace establishes a development dependency, while the published browser files are built from `app/frontend-publisher/` with a separate lock. Check that lock and the emitted files for imports or bundled copies. A clean production audit narrows the question but does not establish every browser byte or future release.
2. **Installation is not execution.** The current typecheck job only runs `tsc --noEmit`; this scenario does not prove that it calls the glob package or passes the proposed pattern to it. A later generator that accepts contributor-controlled patterns could create that input path, making a development-tool denial of service more relevant. The job's lack of AWS credentials would limit one consequence, but not job failure. Review who can submit the source, when that generator runs, resource/time limits and the exact glob caller before claiming reachability.
3. **A build tool can influence the parcel.** `--omit=dev` describes a filtered dependency inventory; it does not inspect the credential-free generation job's code. Separating its AWS authority from the publisher reduces credential exposure, but a compromised builder could still emit altered files that the publisher accepts. Review the emitted artifact, dependency provenance and workflow before enabling publication.
4. **Do not collapse lock, install and audit into one claim.** Four old lock records and an unchanged full audit contradict a claim that the audited graph is repaired; physically resolved newer copies narrow a particular execution observation. A candidate needs a coherent `npm ci` lock, installed-version inspection, relevant audit change, affected backend-generation behavior, browser build comparison and permission review. The conflicting metadata may need an upstream bundle or npm resolution fix. A clean install alone is insufficient.
5. **Advisory context matters.** The remote gateway exploit described upstream is not evidence that this static site offers such a gateway. The old development copies still merit dependency and build-input review; their presence is neither proof of remote exploitation nor proof of safety. Adding a federated gateway with customer-controlled aliases would create the advisory's stated input and process conditions, requiring a patched compatible runtime and direct changed-query testing before serving traffic.
6. **The digest proves byte identity after hashing.** It can detect later ZIP changes. It does not prove that the build script produced approved content when the script itself is inside the trusted main-branch boundary. A reviewed source change, protected workflow/branch, independent artifact-content comparison or equivalent provenance control addresses that distinct question. The current private-plan branch-protection limit remains a release-design constraint.
7. **An advisory withdrawal changes the finding, not the installed tree.** The October 23 registry audit no longer reported `braces`, and the upstream notice says it was withdrawn as not practically exploitable. The dependency path and lockfile did not change. Keeping the generator still calls for ordinary source-input and job-permission review; it does not need a forced version change to address this withdrawn notice. Replacing it for another demonstrated reason needs backend-generation and output compatibility tests. Stopping it removes a learning/build capability and needs a documented replacement or scope change. The two URLs remaining **at that checkpoint** needed their own investigation; a later audit added a Zod root finding. A lower count alone proves neither a package patch nor general build safety.

A strong answer names the exact input, process and authority for each claim. It separates the upstream advisory's scenario from this project's observed path, and a proposed containment from a demonstrated repair. These answers have not been calibrated with independent learners.
