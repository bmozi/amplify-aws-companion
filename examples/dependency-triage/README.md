# An advisory count is not a risk count

Imagine a workshop with three defective tools used by many other tools. A defect report can name every affected parent. Counting those names does not tell you how many independent defects exist, which tools actually run, or whether the finished website contains them.

Run the cloud-free fictional fixture from the repository root:

```sh
python3 examples/dependency-triage/lab.py examples/dependency-triage/fixture.json
python3 -m unittest discover -s examples/dependency-triage -p 'test_*.py' -v
```

It reports three affected package entries but one root advisory URL. `parent-tool` is a direct dependency with an inherited finding; `nested-library` carries the root advisory. The script groups only advisory objects present in `via`. It does not guess which advisory caused each inherited parent when several causes overlap. It rejects an incomplete/error report and a metadata count that disagrees with the entries.

For the actual app, run `npm audit --json` from `app/` and save the JSON outside tracked source, then supply that path to the script. Run `npm audit --omit=dev --json` separately to see the production-only view. npm can return a nonzero exit because it found vulnerabilities; a registry/network failure is a different event. Do not present a missing or failed query as a clean audit. The October 19 full report had **44 affected entries and three advisory URLs**; an October 23 report had **21 entries and two URLs**. On October 25, the committed lock's full audit reported **40 affected package entries under three root advisory URLs**, while the production-only view reported zero. The exact full JSON is saved locally outside tracked source at `artifacts/dependency-audit-2026-10-25.json`; the committed lock SHA-256 is `60fa17770afec86d38a46e2daf1379f8201aa47f3315dec50e3a100dd608f8a2`. These dated reports are not a risk trend or release approval.

The [braces stack-exhaustion notice](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) was **withdrawn October 23** as not practically exploitable. Its removal from the audit did not update the package. The October 25 root URLs are [GraphQL Tools `mergeDeep` prototype pollution](https://github.com/advisories/GHSA-7mx3-vvmw-hjmv), [OpenTelemetry baggage allocation](https://github.com/advisories/GHSA-8988-4f7v-96qf), and [Zod oversized constrained collection validation](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). Their listed patched versions are `@graphql-tools/utils` 12.0.1, `@opentelemetry/core` 2.8.0 and `zod` 4.6.6. The installed Amplify generation tree includes older GraphQL Tools majors and declares a Zod 3.25.17 peer. Forcing those copies to a newer major is a compatibility decision, not a routine patch. Some OpenTelemetry 2.0.0 paths remain in the lockfile even though the installed top-level copy is newer; investigate the exact installed path before claiming remediation.

## Changed cases before the assessor

Cases 6–10 replay dated override and audit observations. Case 11 uses the October 25 Zod finding. Keep each historical baseline separate from today's registry result when answering it.

1. A new audit reports 50 affected package entries but still three root URLs. Did security improve or worsen? What additional version, path and execution evidence would settle the question?
2. A production-only audit is clear, but a GitHub build job runs generation with a deployment role. Which process and authority need review? Does a browser-only scan answer it?
3. An upstream fix is available only in a new major version. Compare a scoped, tested upgrade; restricting untrusted input/credentials while waiting; and disabling the dependent feature. Which evidence is needed before each choice?
4. A lockfile records a vulnerable nested package but clean installation does not create that nested path. Which two observations should be recorded? Why would deleting the lock entry by hand be weak evidence?
5. The registry query fails before returning a report. What should the release gate say?
6. A clean install exits zero after an operator adds a patched-version override. Four vulnerable nested versions remain in the lockfile, the full audit count is unchanged and `npm ls` calls two installed copies invalid under the override. Which evidence contradicts the claim that the patch landed? What would have to be retested before accepting a broader replacement of the nested family?
7. An operator widens the override to `core`, `resources` and `sdk-trace-base` at 2.12.0. Lockfile-only installation exits zero, but four nested `core@2.0.0` entries remain under Amplify construct bundles and the audit still reports 44 affected entries. Is the override now a repair? What is the earliest failed acceptance check, and what evidence would an upstream bundle update need before the publisher could rely on it?
8. An [upstream npm issue](https://github.com/npm/cli/issues/9821) reproduces a bundled lockfile round-trip failure with Amplify construct versions 1.17.7 and 1.22.2. Our lockfile uses 1.17.8 and 1.22.3 but still records four nested `core@2.0.0` paths. Which parts of the upstream report explain a plausible mechanism, and which facts must you check locally before claiming our version is fixed? Draft a release decision that distinguishes a clean install, physical installed versions, the full audit, and backend generation behavior.
9. A teammate runs `npm install` and commits a shorter lockfile. Before saying it is cleaner, run `python3 scripts/check-amplify-bundled-lock.py`. The local guard checks four exact dependency requirements in two Amplify construct bundles and refuses missing nested lock records. Its three negative-control tests include a pruned record and a changed requirement. Why does a pass protect one `npm ci` precondition while leaving the OpenTelemetry advisory unresolved? What further installed-tree, audit and backend-generation evidence would a genuine repair need?
10. Npm's audit JSON says `fixAvailable` for a direct Amplify package and names version 1.8.0, while the registry's current version and our declared dependency are 1.25.1. A dry-run `npm audit fix --ignore-scripts` proposes several package changes but still reports the same 44 affected entries. Is the advertised version a safe upgrade? What does the dry run establish, and what would you demand before changing the committed lockfile?
11. The October 25 audit reports Zod 3.25.17 through the Amplify backend CLI and output schemas. Its advisory lists 4.6.6 as patched. A teammate adds a package-wide `zod: 4.6.6` override and calls the builder repaired before running it. Which declared peer constraint did the teammate cross? What generation, CLI, output-schema and browser-build behavior must be checked in a disposable tree? Does the development-only location prove that an untrusted oversized collection reaches this parser?

Ask Codex to trace one root advisory to the app's direct dependency using the actual lockfile and `npm explain`. Require it to name the process that handles attacker-controlled input, its permissions and a test for the proposed repair. Check the trace yourself. Three URLs do not mean only three reachable exploits, and 40 affected entries do not mean 40 independent attacks.
