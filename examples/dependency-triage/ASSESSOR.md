# Dependency audit assessor

1. Neither count direction proves risk changed. Compare the exact advisory set, affected versions, package paths, changed inputs and execution context. One new parent may raise the entry count without a new root; a repaired root could coexist with newly affected parents elsewhere.
2. Review the build/generation process and its role, inputs and dependency versions. The production-only audit omits development dependencies but the build may run them with powerful credentials. The proposed publisher separates build and AWS role jobs; verify that actual workflow boundary before enabling it.
3. A major override can break internal APIs. Test the affected generator and deployed outputs in a suitable bounded environment, not only the Vite build. While waiting, restrict untrusted inputs and deployment authority, document owner and revisit when upstream changes. Disabling a feature needs proof that no required lab capability was silently removed.
4. Record the lock entry and the physical installed tree from a fresh `npm ci`; also record the npm version and exact command. Hand-editing the lock can make `npm ci` fail or hide the discrepancy without changing the installed code. Investigate the upstream resolution behavior.
5. Fail closed or mark the audit unavailable. A query error is not an all-clear. Preserve the previous dated result as history but do not call it current.

A broader replacement must produce a coherent lock and installed tree, lower the relevant advisory exposure, preserve supported dependency constraints, and pass the affected backend generation path plus frontend build and security-boundary checks. Do not count a lower console summary or an edited version string as proof of that whole result.

Inspect the lock and a clean installed tree for every relevant Zod copy and peer warning.
