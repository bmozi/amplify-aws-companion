# Assessor notes: assistance is not evidence

1. A useful test fails when the booking rule is deliberately broken and passes against the intended implementation. Check an allowed booking as well as a denied one, so an implementation that always refuses cannot pass. Generated tests require human review for assertions, fixtures, scope and sensitive-data handling; a test count is not coverage of the business promise.
2. Tie any review to the exact artifact and environment, not just a branch name. Record who has authority to approve and deploy, and verify the customer path and rollback conditions. AWS documents DevOps Agent release management as preview; this paper case does not configure it or demonstrate automated approvals. [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent.html).
3. A denied request could involve the wrong principal, an absent allow, or an applicable explicit deny, among other causes. Actual identity, action, resource, policy and request-context evidence are needed before changing anything. Amazon Q's answer is a hypothesis, not a complete IAM evaluation or authority to widen access. [AWS console error diagnosis](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/diagnose-console-errors.html).
4. Compare a documented baseline and the changed implementation under representative conditions. Test invalidation and competing updates; include stale results, correctness and total cost as well as speed. An AI suggestion or a local toy benchmark cannot establish a production optimization.

To demonstrate one of these AWS-specific skills, a reader would need an authorized, current, appropriately scoped tool session and a recorded independent check. This exercise establishes only an approach to planning that work; it provides no result from Amazon Q Developer or AWS DevOps Agent.
