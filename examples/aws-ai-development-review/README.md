# Ask an AWS AI tool, then check the evidence

Maya's team has a test gap, a risky release, an error and a slow request. An assistant can suggest where to look, but a confident answer does not run a valid test, approve a release, establish a root cause or measure an improvement by itself. Start by writing what would count as evidence before choosing a tool.

AWS's Developer Associate guide includes skills involving **AWS AI tools**. Codex can help rehearse general reasoning, but using Codex is not evidence that you have used an AWS tool. AWS documentation describes Amazon Q Developer options for generating tests, explaining or fixing code, and suggesting optimizations. It separately describes AWS DevOps Agent release-management and incident-investigation capabilities; release management is documented as a **preview** in the linked guide. Availability, permissions, supported environments, pricing, data handling and features can change. Check the current documentation for the selected account and Region. [Amazon Q Developer code actions](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/explain-update-code.html); [AWS DevOps Agent workflow](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent.html).

This exercise is a **paper rehearsal**. It does not install an extension, enable an agent, call a model, create a pipeline, or verify that either AWS tool is available to you. It is not an official AWS practice question.

## Four decisions

1. **Generate a test.** Maya's appointment function must not confirm a booking without a free slot. Before asking for a generated test, write one allowed case, one denied case and a controlled defect that the test should catch. If a generated test only checks the implementation's current output, how could a broken rule still pass? Specify the test command, expected failure under the defect and evidence that the unmodified code passes.
2. **Review a release.** A proposed pipeline will ship a booking change after an AI review labels it low risk. Identify the exact commit, built artifact, test environment, reviewer or policy that can approve release, and the customer outcome to check afterward. Which evidence would invalidate the approval? A release-readiness suggestion is not the authority to deploy.
3. **Investigate an error.** A fictional AWS console message says access was denied. Write two different hypotheses and the evidence that would distinguish them. AWS describes Amazon Q Developer's console error diagnosis for supported cases; a suggested permission change still needs inspection of the actual principal, requested action, resource and applicable policies. Never resolve uncertainty by automatically granting broad permissions. [AWS console error diagnosis](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/diagnose-console-errors.html).
4. **Propose an optimization.** A generated suggestion caches appointment availability. State the correctness promise, a representative workload and a baseline measurement first. Design a changed-data case that can reveal a stale answer. Compare customer-visible latency, errors, cost and freshness after the change; an unmeasured code suggestion is not a performance result.

For each decision, record the original evidence, the suggestion, your independent check, the result, remaining uncertainty and the person who owns the action. The [assessor notes](ASSESSOR.md) give one possible path. Use synthetic data; do not paste credentials, state files, customer data, private URLs or account identifiers into an assistant. Confirm the selected service's data-handling terms before providing even sanitized organizational material.

If you later choose to use an AWS tool, independently confirm its current setup, access controls and costs, then define a whole-run estimate, spending limit and credit reserve, stop condition and cleanup owner. A preview feature or agent may need additional account setup and resources. The paper cases need none.
