# Security finding review: assessor notes

1. Inspector is the vulnerability context, GuardDuty the suspicious-activity context, and Macie the S3 sensitive-data discovery context. Security Hub can correlate supported signals; it is not proof that these three fictional reports share a cause. Require account, Region, exact resources/artifacts, actor relationships and relevant observation intervals before joining them.
2. The missing evidence is what the running workload actually uses and whether the relevant assessment covers that artifact. A repaired source and tested image D do not show that deployed image A was replaced. Also preserve the distinction between addressing a package condition and investigating earlier behavior.
3. Accept: “The filtered result contains no findings for the ten recently covered resources; coverage for two intended resources remains unknown.” Inspect filters, target account/Region, supported resource types and coverage freshness. Do not silently change the denominator from ten to twelve or treat unknown coverage as a clean assessment.
4. Bucket inventory and representative object analysis are different scopes. Review selected objects, eligibility, discovery interval and job/sampling configuration. The observation does not establish that all content is nonsensitive, nor that any specific unexamined object contains sensitive data. A factual coverage statement is preferable to an invented severity label.
5. Distinguish event time from report arrival. Candidate explanations include earlier workload misuse versus expected authorized activity, but both require actor/action context and corroboration. The 13:00 deployment cannot explain an earlier event merely because its report arrived later. Resolve the other report's Region and resource identity before correlation; similar names are insufficient. Exposure and attack-sequence context should be examined when available, not flattened into a simple finding count.
6. Evidence supports the stated reassessment of the replacement artifact and its tested application behavior within the observed scope. It does not resolve the earlier activity investigation or prove that every workload is free of vulnerabilities. Record the investigation owner and next discriminating observation separately from repair verification.

7. Cognito user-pool authentication establishes an application identity and supplies tokens for the configured flow. The receiving API/application must validate the intended identity and enforce the record's access rule; the notebook example uses an owner rule. GuardDuty threat observations and Macie sensitive-data discovery answer other questions and do not grant the requested record read. Identity pools are a separate credentials mechanism, not automatically required for every user-pool-backed API. Require a permitted-owner case and another-user denial as proposed evidence, without claiming they were performed in this exercise.

Transfer: preserve the original finding/resource identity and observed interval, identify the replacement using current read-only inventory, and report the mismatch. A resource name reused after replacement is not sufficient identity. A duplicate notification is not new authorization, and a proposed response is not a completed action.

Require revision when an answer equates a vulnerability with exploitation, source repair with deployed repair, no returned findings with complete coverage, or passed application checks with incident closure. Sufficient answers name the missing evidence and remain useful without pretending it exists. No actual service configuration, incident response or learner mastery has been verified here.
