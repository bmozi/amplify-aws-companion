# Assessor: whose authority survives in a queued job?

Answer before opening this page. The fixture has two deliberately different promises; neither is a universal SaaS rule.

1. **Alice loses Shop A membership after submitting both jobs.** The `personal_report` job stops because `execute` requires the same active membership revision recorded at acceptance. The `repair_followup` job may continue because this fictional Shop A policy says acceptance transferred the job to tenant-owned work. The server's fixed action map, rather than a caller-supplied authority label, chooses that distinction. Both were authorized at submission; only their later authority differs.
2. **A preview passed immediately before revocation.** It is a stale observation. The local effect is written only after `execute` starts a SQLite `BEGIN IMMEDIATE` transaction and rechecks the relevant tenant and membership state. Removing that later check would create a check-to-effect gap.
3. **Shop A closes before either pending job runs.** Both stop. Acceptance does not override tenant closure. A duplicate call for a job already marked done returns its earlier local result; closure cannot undo a prior effect.
4. **Alice sends `shop-b` with a note ID also used there, or a stored job's authority is relabeled.** Submission is denied because the synthetic membership lookup includes actor and tenant. The note key and effect row also carry tenant. A relabeled row fails the server action-map check at execution. Matching record IDs and caller-controlled labels do not grant cross-tenant or continuing authority.
5. **The effect is an email rather than a SQLite row.** This lab no longer proves one effect. A database transaction cannot atomically commit an email provider's action. The design needs provider idempotency or a queryable receipt and a reconciliation/stop path for unknown replies. It also needs a clear rule for revocation that occurs after a send begins.
6. **Alice leaves and later rejoins Shop A.** A new membership revision must not silently reauthorize an old delegated job. The local equality check rejects it. A real service needs a trustworthy version or equivalent authorization decision, retention rules and an explicit replay policy.

The seven local tests cover these selected SQLite conditions, not authenticated membership, distributed worker timing, cloud authorization, external effects or learner competence.
