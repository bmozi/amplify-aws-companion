# Assessor notes: the stand-in API

1. A prepared response can show how this client behaves when it receives the chosen status, headers and body. It establishes no live scheduler, reservation, persistence, identity enforcement or customer notification. Check the UI and network observation separately from the eventual business result.
2. In AWS's documented REST mock example, the integration request mapping produces a `statusCode` used in the configured response setup. Configure and inspect the corresponding integration response and method response, including body and headers, then deploy the change to the intended stage before testing that stage. The mapping result is not proof that a real backend ran. [Mock integration overview](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-mock-integration.html); [console setup](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-mock-integration-console.html).
3. Choose an explicitly configured failure case and verify the client shows an appropriate failure state, does not report a confirmed booking, and offers a safe recovery path. Avoid assuming every error is retryable or that a retry is safe. A passing simulated failure does not establish how the live scheduler fails.
4. The browser may block JavaScript access to a response when the applicable cross-origin rules are not satisfied; inspect the request, response and preflight where applicable. For a REST non-proxy integration, AWS documents configuring relevant method and integration response headers. Check the selected method, response, origin and deployed stage; CORS is a browser access rule, not authorization or proof a backend is healthy. [CORS for REST APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-cors.html).
5. Name the shared schema and owner, version it, and validate representative success and error responses. A contract test against the actual scheduler should expose the string/number mismatch; a mock that is never updated can continue to pass. Do not promise the test is sufficient for authentication, performance or failure recovery.

A strong answer separates a configured stand-in, an observed response, the client result and a verified business effect. These are distinct evidence boundaries. No case here establishes actual API Gateway behavior in an account.
