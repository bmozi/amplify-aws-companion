# Remote Terraform state assessor notes

These are authored reasoning criteria, not a validated learner rubric or live backend test.

1. **One key:** a supported backend can lock state around a write operation. Both runs must use the same backend and state key for that coordination to apply. Do not disable locking to bypass contention. A lock is not a lock on every AWS resource in the account.
   The local lab supplies a concrete negative control: a second normal plan is refused during the first apply, but `-lock=false` can propose creation from a stale view. It never applies that proposal. After release, the normal plan is a no-op. If teams use different state keys for one object, each key can be locked successfully while ownership still conflicts. Choose one manager or make a deliberate, reviewed transfer; a lock on each separate record cannot solve duplicate ownership.
2. **Workspace access:** a workspace affects the state path, but its name is not IAM authorization. Separate object-key permissions and roles are needed to isolate production writers from development. Limit bucket listing to necessary prefixes as well as scoping object and lock permissions.
3. **Uncertain writer:** confirm the originating process/session has ended through run records and operator confirmation. If a writer may still be active, stop. Force-unlocking a live writer permits concurrent updates and can corrupt the record. Remove only the lock known to belong to the stopped operation, following the backend's supported procedure.
4. **Old state:** versioning provides earlier state objects but no service rollback. Compare lineage, serial, recorded addresses, operation history and actual resources. A stale state can omit later objects or contain deleted ones. Reconcile ownership and produce a fresh plan; do not use force to override lineage/serial protections as a shortcut.
5. **Migration:** do not apply against an unexpectedly empty backend. Preserve the old state securely, confirm the exact destination and workspace, perform an intentional backend migration, then verify that the expected resource addresses remain in the remote state and a fresh plan is a no-op or otherwise understood. A no-op plan still is not business acceptance.
6. **Console drift:** the S3 lock coordinates Terraform writers only. Record the observed setting and incident intent. Update configuration if the emergency fix should remain; otherwise plan a reviewed reversion. The lock cannot prevent a different controller or console action from changing AWS.

For the current S3 backend, HashiCorp documents native lockfile support via `use_lockfile`; its DynamoDB locking option is deprecated. The S3 backend needs object access to the state and lock paths, with `DeleteObject` on the lock object; the state itself is not deleted during ordinary writes. Do not infer that Terraform provider permissions are the same as backend permissions.
