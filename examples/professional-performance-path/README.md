# Professional performance: follow the bottleneck

This fictional review packet follows [Unit 21's read-path lesson](../../reader/BOOK-LOCATORS.md#book-b2320aadd4a275a7), [Unit 02's compute lesson](../../reader/BOOK-LOCATORS.md#book-98320f6e3107b9a6) and [E07](../../curriculum/EXERCISES.md#e07). Answer each changed case before consulting the [assessor reasoning](ASSESSOR.md). The supplied rates and times are invented; the packet makes no AWS performance or price claim.

Maya reports that repair searches are slow during weekday openings, booking writes occasionally time out, and overnight photos miss their deadline. The platform has an application fleet, a database, an optional cache, object storage and a queue-backed photo worker. For every case record: customer success and p50/p95/p99 latency; arrival and completion rates; errors and retries; first limiting resource or wait; data freshness/correctness requirement; candidate change and rejected alternative; peak/failure headroom; cost per successful operation; rollback; and a bounded test that could disprove the choice.

1. **Averages hide the queue.** Average CPU is 28%, but booking p99 rises from 300 ms to 4 seconds. Database connection wait and error counts rise while application CPU remains flat. Compare adding app workers with a connection/query investigation. Change the observation so CPU is sustained at 92% and database wait stays low. Which additional profiling fact and workload test would support a compute-family/size experiment?
2. **The cold-cache opening.** Eight same-key readers arrive while a cache entry is absent. Run the [local concurrent burst](../cold-cache-burst/README.md), then change the system to six separate application processes with a source concurrency allowance of four. State what process-local coalescing proves, what it cannot bound across the fleet, and how source admission, timeouts and customer responses might change. The requested value becomes tenant-private; decide where authorization and freshness belong.
3. **A replica returns the wrong moment.** A read replica relieves the primary but is 12 seconds behind while a customer expects to see a just-confirmed booking. Choose which reads may use the replica and which require an authoritative path. Change the incident to a bad write copied to the replica. Explain why neither a cache nor a replica is a historical recovery point.
4. **Buffer the work that may wait.** Photo jobs arrive at 12/s, workers can transform 20/s and the result store can accept 8/s. Compute the steady backlog growth. The store is improved to 16/s while the backlog is 1,440 jobs; compute the ideal drain time with arrivals continuing. Then add a 20-minute worker outage and a customer report deadline. Use the [local scaling model](../scaling-policy-model/README.md) and list the real service-time, retry, queue-age and storage evidence missing from its arithmetic.
5. **The storage interface changes.** Repair photos are immutable downloads, a legacy processor writes a shared POSIX path, and a database needs low-latency random updates. Compare object, shared-file and block interfaces before comparing capacity and price. Change the processor so it can write objects directly and state what interface and consistency tests would justify removing the shared filesystem.
6. **Purpose-built does not mean automatically faster.** Bookings require conditional admission for the last available slot, reports scan large historical events, and support searches repair notes. Compare one general-purpose database with separate transactional, analytical or search-oriented paths. Define the authoritative record, synchronization lag, permission scope and added failure/cost surfaces. Do not route last-slot writes to an eventually updated search index.
7. **Right-size after an experiment.** A worker's representative profile shows high memory working set and low CPU, but the current instance also has high network and disk wait. Compare a memory-focused family, a storage/network change and a query/application fix. Define a bounded A/B workload with equal inputs, warm-up, peak, one-AZ failure margin, p95/p99, errors, cost per successful job and an exact rollback. A larger instance is a hypothesis, not the conclusion.
8. **A slow customer is far from the origin.** A global repair portal has a 900 ms p95 in one distant region. One representative 900 ms slow request spends 550 ms on repeated image and script transfers, 220 ms on an uncached booking API call, and the remainder on other work. One trace does not establish the p95's cause, so collect a representative sample before changing the path. Compare CloudFront for cacheable web assets, CloudFront with a deliberately configured dynamic HTTP path, and Global Accelerator for a separately proposed TCP/UDP service. Which measurement would show that each option improved the relevant path? Change the trace so database wait dominates the API call. Explain why an edge service cannot repair that wait. State cache keys, private-data handling, invalidation, regional endpoint health, transfer/request charges, and rollback before a trial.
9. **Close-together machines solve a different problem.** A batch simulation exchanges large intermediate results between tightly coupled EC2 nodes; measured node-to-node network wait dominates. Compare a cluster placement group, a larger independent instance, and more application replicas. State the single-AZ and capacity-placement consequences of the cluster choice, then design a test with the same job and instance configuration. Change the workload to ordinary independent web requests spread across failure zones. Explain why a cluster placement group loses its rationale, and how a partition or spread strategy would answer a different failure-isolation question.

For one case, turn a business promise into a measurable objective before choosing the technology: “95% of completed searches return within two seconds during the weekday opening.” Define the population, measurement window, exclusions and correctness check. Distinguish that application KPI and target from any selected AWS service's contractual SLA. A provider commitment is evidence about its service under its terms; it does not promise the end-to-end portal result. Compare baseline and trial on the same traffic mix, report sample count and uncertainty, and reject a faster result if it makes successful or correct outcomes worse. Record how to roll back.
