# Does Maya need a dedicated key room?

Maya's repair company encrypts customer records. An auditor writes, “Use an HSM.” The architect starts drawing a CloudHSM cluster. Before anyone spends money, Maya asks what control the auditor actually needs: a protected key, a customer-owned **KMS key policy**, customer-supplied key material, or a dedicated single-tenant HSM under her team's operational control? These are different requirements. The answer changes who must keep the keys available when customers need their records.

![Three key-store choices are separated from a customer request: standard KMS, a CloudHSM-backed KMS custom store, and direct CloudHSM integration. The custom path adds cluster capacity, backup and reconnection obligations; a fresh decrypt stops if the store is disconnected.](figure.svg)

This cloud-free lab deepens [Chapter 31's dedicated-HSM lesson](../../reader/BOOK-LOCATORS.md#book-aa4f22aba2f8c74a) for [SAP-C03 skill 2.2.3](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-professional-03/solutions-architect-professional-03-domain2.html). It is a design exercise, not legal or auditor approval. Do not create an HSM, custom key store, KMS key, VPC or bill to complete it.

## Three doors, three operating jobs

**Standard KMS key store.** AWS KMS already protects KMS key material in HSMs. A customer-managed KMS key gives Maya control of its policy and lifecycle. This is the ordinary starting point when the requirement is to authorize a supported AWS service to encrypt records. A dedicated HSM does not follow just from the word “HSM.” [AWS key-store choices](https://docs.aws.amazon.com/kms/latest/developerguide/key-store-overview.html).

**CloudHSM-backed KMS custom key store.** Maya operates a CloudHSM cluster, while AWS KMS manages supported *symmetric* KMS keys whose material is in that cluster. This keeps a KMS API integration for supported services, but adds a cluster, private connectivity, crypto-user administration, HSM-hour charges, backup/restore and availability responsibility. A disconnected custom store makes its keys unavailable for fresh KMS cryptographic operations. Custom stores do not support every standard KMS feature, including automatic rotation and multi-Region keys; AWS warns that this route has lower throughput and higher latency, and is unsuitable for high-volume S3 or DynamoDB request patterns. The selected application and service integration still need proof. [KMS custom-store overview](https://docs.aws.amazon.com/kms/latest/developerguide/key-store-overview.html), [CloudHSM key store](https://docs.aws.amazon.com/kms/latest/developerguide/keystore-cloudhsm.html).

**Direct CloudHSM integration.** A custom application can use supported CloudHSM client software and cryptographic interfaces directly. That is a separate application and operations design; ordinary AWS service encryption does not automatically use an application-managed CloudHSM key. Specify the cryptographic operation, client library, network path, user ownership, rotation, monitoring and recovery before comparing it with KMS. [CloudHSM cluster architecture](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cluster-architecture.html).

## Make seven decisions before the assessor

For every case, write **the exact requirement, selected key path and rejected path, operational owner, useful allowed and failure observation, cost driver, and remaining proof**. Read [the assessor](ASSESSOR.md) only after writing your answer.

1. **What did the auditor mean?** The written requirement says only “HSM-backed encryption and a customer-controlled access policy.” Choose a starting design and state what additional exact language or reviewed interpretation would justify a dedicated single-tenant cluster. Do not invent a regulatory mandate.
2. **Single-tenant custody becomes explicit.** A signed requirement now says Maya's team must operate dedicated single-tenant HSM capacity while a supported AWS service continues to call KMS. Compare a CloudHSM-backed KMS key store with direct CloudHSM use. State the key type and supported service checks that can defeat the first proposal.
3. **One Availability Zone fails.** A fictional cluster has three HSMs, two in zone A and one in zone B. The team measured **40 invented operations per second per HSM**, and promised **70 per second** at peak. Does a single HSM failure differ from losing zone A? Show the arithmetic and identify the real load, client and network tests still needed. AWS recommends different-zone placement and additional redundancy; this exercise's capacity number is not an AWS benchmark. [CloudHSM availability](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cluster-high-availability-load-balancing.html), [cluster best practices](https://docs.aws.amazon.com/cloudhsm/latest/userguide/bp-cluster-management.html).
4. **The key store disconnects.** A new customer tries to read an encrypted record. A previously running worker might hold a usable plaintext data key. Which fresh KMS operations fail, and why might the old worker's immediate behavior differ? Do not promise that every service stops instantly or keeps running; test the selected service and its data-key use. [KMS custom-store troubleshooting](https://docs.aws.amazon.com/kms/latest/developerguide/fix-keystore.html), [unusable keys and data keys](https://docs.aws.amazon.com/kms/latest/developerguide/unusable-kms-keys.html).
5. **Backup age exceeds the promise.** Maya promises an RPO of 12 hours, but the latest *known* cluster backup is 27 hours old. Can the backup alone prove the promise? Write the most recent acceptable recovery point, backup retention owner, restore action, and an authorized customer decrypt test. AWS makes periodic CloudHSM backups at least once every 24 hours; that cadence alone does not prove a 12-hour RPO. [CloudHSM backups](https://docs.aws.amazon.com/cloudhsm/latest/userguide/manage-backups.html), [restore guidance](https://docs.aws.amazon.com/cloudhsm/latest/userguide/backups-using.html).
6. **The request pattern changes.** A proposed high-volume S3 object workflow would invoke a CloudHSM-backed KMS key on a hot path. Revisit the custom-store choice, consider a supported ordinary KMS design if the requirement permits it, and specify a workload measurement and cost estimate. Do not solve a throughput problem by silently relaxing custody requirements. [Key-store performance limits](https://docs.aws.amazon.com/kms/latest/developerguide/key-store-overview.html).
7. **A new Region is required.** The product owner asks for recovery in another Region. A CloudHSM-backed custom store does not provide multi-Region KMS keys. Outline a separately reviewed destination cluster, backup copy or other compliant design; identify key mapping, data migration, permissions, timing and customer read proof. A copied backup and an available application are separate claims. [Custom-store feature limits](https://docs.aws.amazon.com/kms/latest/developerguide/key-store-overview.html), [CloudHSM backup copy](https://docs.aws.amazon.com/cloudhsm/latest/userguide/copy-backup-to-region.html).

## Run the fictional promise audit

From the repository root, run `python3 examples/dedicated-hsm-decision/lab.py` and `python3 -m unittest discover -s examples/dedicated-hsm-decision -p 'test_*.py' -v`. The model checks **only** supplied HSM counts, zones, invented capacity, backup age and declared store state. Change the fixture to three zones with one HSM each, then change the backup age to four hours. Explain which warnings disappear and what remains unproven. A passing arithmetic worksheet is not a CloudHSM benchmark, backup restore, KMS behavior test or auditor acceptance.

Ask Codex to critique your answer as both the custody owner and the on-call operator. Require it to name one incorrect shortcut (“KMS does not use HSMs,” “three HSMs means every AZ outage is safe,” or “backup exists, so RPO is met”), cite current AWS documentation, and separate an asserted service behavior from a testable observation. Verify the citations. Do not paste private key material, crypto-user passwords, account identifiers or actual audit documents.

For a future authorized implementation, calculate at least HSM-hours across the whole cluster, supported KMS key/request charges, network/client capacity, backups, monitoring and recovery test resources using current Region prices. Name the stop and cleanup owner and reconcile post-run charges. This high-cost exercise stays on paper; it authorizes no CloudHSM spend.
