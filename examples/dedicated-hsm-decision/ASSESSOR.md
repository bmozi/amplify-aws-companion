# Assessor: dedicated HSM decision

Credit an answer when it states the actual custody requirement and matches it to a supported integration and recovery promise. “Use CloudHSM for security” without a named control, owner and failure test is incomplete.

1. **Ambiguous audit sentence.** Standard KMS is already HSM-backed. A customer-managed KMS key with reviewed policy is a defensible starting proposal for the stated words. Ask the auditor or control owner whether the requirement truly demands dedicated single-tenant capacity or customer control of key material; do not declare compliance from a paraphrase.
2. **Explicit custody.** A CloudHSM-backed KMS custom store preserves a supported symmetric KMS path for selected service integrations, at additional cluster responsibility. Direct CloudHSM needs application/client integration and does not make every AWS service consume that key. Confirm key type, service, Region, throughput, network and control-owner acceptance.
3. **Failure arithmetic.** Three HSMs at 40 invented operations per second each offer 120 in the undisturbed toy model. Losing one leaves 80, above the promised 70. Losing zone A leaves one HSM and 40, below 70. A three-zone one-HSM-each arrangement leaves 80 after any single-zone loss in this toy model. None proves measured CloudHSM capacity, network behavior, KMS custom-store throughput or a complete AZ-failure recovery.
4. **Disconnect.** AWS KMS cannot perform fresh cryptographic operations with keys in a disconnected CloudHSM-backed custom store. A component already holding a usable data key may continue until it needs KMS again; exact service behavior must be observed. Diagnose connection, HSMs, network, KMS key state and a selected fresh decrypt separately.
5. **RPO.** A 27-hour-old latest known backup does not prove a 12-hour recovery point. CloudHSM's periodic backup cadence is not an application RPO guarantee. Restore a chosen backup into the designed cluster path, check expected keys and crypto users, reconnect the key store if applicable, and verify an authorized application read without losing current data. Retention and cross-Region copy need named owners.
6. **Hot path.** AWS warns that CloudHSM-backed KMS stores have low TPS and are not suitable for high-volume S3/DynamoDB patterns. If a single-tenant mandate is real, redesign the workload or obtain a reviewed exception, rather than treating standard KMS as an automatic substitute. Gather actual operation volume and selected-service behavior before a cost/performance claim.
7. **New Region.** Custom-store KMS keys are not multi-Region keys. A separate destination cluster and copied backup may be one component of a compliant recovery design, but key identity, ciphertext migration, policies, restore time and customer use are additional checks. Never call a backup copy a tested recovery.

**Changed-case challenge:** A diagram shows three HSMs in three zones and a four-hour backup. A reviewer declares the service ready, but the `kmsuser` connection cannot be established after a credential change. The count and backup do not prove current KMS key usability. Require connection-state diagnosis, an intended allowed operation, a meaningful denied operation and a customer-path restore result before accepting readiness.

The local model proves only its own arithmetic and warning logic. No auditor, independent learner, AWS cluster, custom store, service integration, bill or restore was observed.
