# A04 two-gate review assessor notes

Use these explanations after [the nine changed-condition cases](REVIEW-PATH.md). The two-gate fixture establishes SQLite transitions; the visitor extension also exercises a loopback HTTP route. Accept another design if it preserves the stated access and review promise with testable boundaries.

1. The approval must identify the same immutable upload/version and bytes that were checked. A reused key without version binding can point at V2 while the verdict refers to V1. A digest helps detect change; it neither authenticates the scanner nor proves content safety. Test a replacement before and after the verdict and inspect what the owner actually receives.
2. `UNSUPPORTED`, `ACCESS_DENIED` and `FAILED` are not clean outcomes. Keep owner access denied, retain a bounded diagnostic status and assign retry/manual-investigation ownership. Even `NO_THREATS_FOUND` is a scanner observation, not the school's final approval or a universal safety guarantee. The local `inconclusive` path models unavailability, not GuardDuty behavior.
3. Derive identity from a trusted login or equivalent verified context and check reviewer eligibility at decision time. Bind the decision and any callback capability to upload ID, version, action and expiry; protect token delivery and replay. A body field is a claim. Reviewer read permission can be a separate controlled path that does not authorize customer download.
4. Under the fixture's first-committed-decision rule, either eligible reviewer can win. Exactly one review row and a matching terminal object status should persist; the loser receives a conflict, not a second effect. A two-reviewer policy needs distinct identities, an explicit quorum/revision/expiry rule and new contention tests. Local SQLite locking is not an AWS result.
5. Keep a tombstone or equivalent durable identity so late events cannot make withdrawn bytes available. Deny or mark callbacks too late, preserve necessary audit evidence, inventory retained object versions and use a new ID for a replacement. The local NULL payload does not establish physical erasure or S3 version deletion.
6. Step Functions Standard is a credible candidate for an externally visible multi-service path with a callback and explicit timeout; a Lambda durable function is a code-first candidate for Lambda-centered steps and waits. Both need stable start identity, authorized callback, version binding, failure ownership and cost review. AWS documents that S3 event notifications are at least once and do not directly target durable Lambda functions. Changing team and integration requirements can change the choice; neither orchestrator replaces the application acceptance rule.
7. A scanner tag alone cannot stand in for human approval. Any direct storage read or valid presigned URL that bypasses current approval violates the promise. Conversely, a failed tag update may leave a tag-dependent policy denying an approved document; keep the customer state honest and investigate the mismatch. Verify the chosen policy and all direct/indirect read paths with negative tests before calling it enforced.
8. A complete trial estimate includes all chosen active and retained meters, not just stored bytes. Use dated selected-region pricing, a short workload, scoped identity, a stop condition, cleanup inventory and later billing reconciliation. Choose limits for the selected account; planning gates do not prove that a bill cannot exceed them. No live price, credit balance or budget delivery was checked by this packet.
9. The local second-door negative control returns 200 from its independent bearer-link copy while the original application route returns 404 before approval and after withdrawal. That is an observed **local privacy failure**, not measured S3 behavior. A 404 from `/raw/...` in the original toy server cannot rule out a different host or URL. Withhold any real download capability until both decisions or make the read route re-evaluate current approval and owner authority at use time; account for link lifetime and withdrawal behavior. Verify actual bucket/object policy, issued URL behavior before/after approval and withdrawal, retained versions and every application/CDN read route. Pending review should show a truthful processing state without returning bytes. The local 410 after explicitly retiring the second copy does not revoke previously saved bytes or prove physical erasure.
