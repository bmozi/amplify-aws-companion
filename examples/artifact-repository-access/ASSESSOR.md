# Assessor notes: give every release job the right repository key

These notes are a reasoning guide, not policy JSON. The desired answer names caller, action, resource, owner and all missing evidence. Do not reward a policy that merely removes the error by adding `*`.

1. **Dependency reader:** use a build identity that can obtain only the package inputs needed from the selected domain/repository. CodeArtifact authorization can involve `sts:GetServiceBearerToken` with the `sts:AWSServiceName` set to `codeartifact.amazonaws.com`, `codeartifact:GetAuthorizationToken`, repository read access and package-manager metadata actions. Exact operations depend on the client and package format. The intended negative is publishing, deleting a package or changing repository policy. Confirm the actual resource types in the current permissions reference rather than guessing from API names.
2. **Publisher:** separate publishing from administration. `codeartifact:PublishPackageVersion` is associated with package resources; some formats/clients also need metadata or repository operations. Restrict the destination to the selected package/repository as the service supports. Do not infer that a repository-level wildcard gives package-level scoping; consult current service documentation. The publisher generally should not administer the domain, change resource policies or delete unrelated packages.
3. **Cross-account consumer:** for CodeArtifact, cross-account access needs an allow in the consumer's identity-based path and in a producer-side resource policy. Token acquisition also needs its service permission; the domain policy may need to authorize token use. A resource policy naming an entire account can admit more principals than intended, so prefer the specific trusted role when supported. Check explicit denies and any boundary, session and organization controls. See the current CodeArtifact repository-policy and IAM documentation before implementation.
4. **Compromised build:** split untrusted PR validation from trusted package publishing. Untrusted input should not run with the trusted publisher or production role. Protect changes to workflow definitions, role trust/permissions, environment approvals and repository policy. A control in the build YAML is not a security boundary if an untrusted contributor can edit that YAML and the job already holds production credentials. Review the full delegation path.
5. **Different service:** ECR uses image/repository authorization and may use repository resource policies; S3 separates bucket-level and object-level actions and policies. These are not CodeArtifact's `ReadFromRepository` and package-ARN rules. Use each service's current official permissions and cross-account docs, then test the expected pull/push and a meaningful denial against the intended repository. A successful authentication token alone is not evidence that the artifact action is authorized.
6. **AccessDenied:** obtain the exact AWS request/action and target, caller account and assumed-role session, Region, resource owner, timestamp/request ID and relevant CloudTrail event where applicable. Inspect attached identity policies, resource policies, trust/session context, permissions boundary, session policy, Organizations controls, endpoint policy, KMS key policy if encrypted and the service's own authorization requirements. A screenshot omits most of that context. Begin with read-only policy/configuration inspection and a simulation whose inputs are listed; confirm behavior with a safe request only in an authorized disposable environment.

The strongest answer distinguishes **authentication** (who made the request), **authorization** (why this action on this resource was allowed or denied), and **workflow integrity** (whether untrusted code can obtain a trusted publisher or deployer role). It names one legitimate read/publish/deploy action and one valid out-of-scope action using the same service and compatible resource type. It does not claim a local simulation or role-name guard proves live AWS behavior.

This exercise makes no AWS call, publishes no package and edits no account policy.
