# Platform transfer assessor reasoning

Read after making the [one-page decision](README.md#make-the-decision-then-change-one-fact). This is a fictional design assessment. The exercise does not operate an AWS platform.

**Base case.** First remove or externalize the worker-memory receipt cache; it can disappear or disagree after replacement on *any* replicated platform. An EC2/Auto Scaling move may be the lowest application-change investigation because the program is already a VM process, but it needs reproducible host setup, safe replacement, load balancing, database capacity and a real restore path. ECS/Fargate is a bounded alternative after container compatibility is proven; it moves host management away from this team, not application-release, network, identity, database or recovery work. A single API with no Kubernetes-specific requirement gives no positive reason for EKS yet. None of these statements proves that a candidate meets the customer promise in AWS. The [A06 local path](../three-tier-boundary/README.md) proves only selected loopback behaviors.

1. A tested container and no host-patching capacity make ECS/Fargate a stronger candidate. Check valid task sizing, image provenance, startup/readiness, task versus execution authority, ingress, protected data, shutdown and complete cost. A healthy task can still return the wrong repair. The stated local tests should be actually observed before calling containerization proven; this packet merely supplies the changed fact.
2. Yes, the controller/API requirement and existing staffed platform make EKS worth evaluating. Inspect whether the controller, ingress/storage/security integrations and selected Kubernetes version work under the chosen EKS mode. EKS Auto Mode expands AWS infrastructure management, but the team still owns application containers and cluster/VPC configuration. Keep the same customer checks and include cluster, compute, Auto Mode and surrounding services in the price. [AWS EKS Auto Mode scope](https://docs.aws.amazon.com/eks/latest/userguide/automode.html).
3. No. A required host feature can rule out a particular Fargate task configuration; check the exact current capability rather than generalizing to every container path. ECS with EC2 capacity, ECS Managed Instances or EKS compute are distinct candidates with different host and operating ownership. [AWS ECS capacity choices](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/capacity-launch-type-comparison.html). Do not assume the team must own EC2 just because Fargate fails one requirement.
4. A rollout that makes old workers unable to read the new schema breaks the overlap/rollback promise. Test the actual old/new coexistence and customer operation, define a compatible migration or forward-repair plan, and decide whether traffic can safely move. A platform's control-plane health is narrower than correct durable business data.
5. New app replicas can consume more database connections or SQL work. Compare admission, connection wait, query/lock time, error rate and correct customer completions before and after the change. A green process endpoint and a larger desired count are not evidence that the shared store has more capacity. The [A06 loopback slot](../three-tier-boundary/README.md) is a tiny counterexample, not an RDS benchmark.
6. Inventory the cluster lifetime, managed compute/nodes, Auto Mode charges if chosen, ingress, storage, logs, addresses, data movement, retained images and backups. AWS's [EKS price page](https://aws.amazon.com/eks/pricing/) includes a cluster-hour meter; a zero-Pod state is not a deletion receipt. Check actual resource lists, configured billing visibility and later attributable charges before reporting cleanup.

The [fictional estimator](whole_run_lab.py) reports full totals with contingency and rejects missing meters; it does not convert invented rates into current regional AWS prices. At 12 hours the EC2 case happens to be below the case's USD 5 limit arithmetically, yet it may still be the wrong service decision or an incomplete real estimate. The Fargate and EKS cases exceeding that fixture limit suggest shortening/simplifying a proposed exercise *before* any live work, not spending credits to make the report look safe. Raising the offline limit to USD 6 changes Fargate's comparison to true but changes no cost line, workload requirement or real authorization. Credits affect payment, not resource consumption or the validity of an estimate. A reserve must be chosen and checked against current applicable account credits separately; the case's USD 100 is not a reader default.

**Strong answer criteria:** one identical customer promise; explicit current versus invented facts; two bounded choices; runtime/state, identity, network, store, replacement and recovery ownership; complete meter/lifetime estimate; a reversal condition; and a testable business result. A candidate cannot be called deployed, cheaper in reality, safer or certification-ready from this packet alone.
