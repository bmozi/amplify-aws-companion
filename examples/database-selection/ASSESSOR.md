# Assessor reasoning — database selection

1. Evaluate Aurora PostgreSQL as a candidate and RDS for PostgreSQL as an alternative for the stated migration. Check exact versions, extension support, procedures, drivers and operating requirements. SQL syntax familiarity does not establish engine compatibility. A move to MySQL needs a separate conversion rationale and behavior tests. No cloud benchmark here establishes either candidate as cheaper or faster.
2. The original specified key-based workload supports evaluating DynamoDB. A relational primary is an alternative when flexible relationship queries become central. Revisit access patterns and measured costs before deciding whether to change the primary design; do not treat unbounded repeated scans as evidence that the initial design still fits. The case does not establish an actual traffic distribution or latency guarantee.
3. The invariant alone cannot select an engine. DynamoDB has transactional operations, so categorical rejection is unsound. Compare the atomic boundary, conditional updates, retries and concurrency tests for each candidate. A transaction in either candidate does not automatically include an external payment or notification.
4. The benchmark omits concentrated access. Repeat with the skewed workload and inspect per-key/customer behavior, contention, throttling and correctness. Neither an average request rate nor an evenly distributed test proves the hot customer's path will work. Adding capacity may not remove a serialized business decision.
5. Start with the simplest design satisfying measured requirements. Identify authority and freshness first. A separate cache/reporting system adds copies, synchronization and recovery obligations. A justified separation could follow a measured bottleneck or reporting requirement, but service count alone is not evidence of scalability.
6. Reject migration acceptance on this evidence. Row counts can match while business meaning changes. Build expected ordered results and exact monetary outcomes, investigate types/collation/rounding, and test corrected behavior before comparing performance. Counts remain one reconciliation check, not the acceptance criterion.

Do not score a service name alone as correct. Look for requirements, a defensible candidate, a credible alternative, explicit reversal conditions and evidence limits. No independent review of this rubric has been conducted.

## In-memory authority and recovery

7. The appointment ledger remains authoritative; a lost display cache may be refilled only from an authorized, sufficiently fresh ledger read. Confirming a booking still requires the ledger's atomic admission rule. A cold cache can send the full read demand back to the ledger, so measure source capacity and bound miss traffic. Improving the source query is a credible alternative before adding a continuing service. A local cache experiment can show a mechanism but cannot measure ElastiCache failover or the real busiest hour.
8. R17 is absent from the stated snapshot, so restoring only that snapshot contradicts the already-issued customer confirmation. The current ordinary-cache design cannot support the stated promise without another authoritative record or a proven recovery path. An eligible node-based ElastiCache for Valkey configuration with synchronous durability is a candidate because its acknowledgment waits for the Multi-AZ log; it is not proof that this app's authentication, last-slot rule, backups, regional availability, or whole customer path work. Test a confirmed R17 write, controlled failure, recovery, authorized read and duplicate-prevention rule; price running nodes, the selected durability/recovery features, network, monitoring, backups and retained time from current regional information.
9. The asynchronous configuration cannot support the stated zero-loss promise: AWS says recent acknowledged writes may be lost before log persistence. Synchronous durability is a candidate for one-Region acknowledgment; MemoryDB is another durable primary candidate, subject to the same application correctness and recovery tests. A MemoryDB replica read may lag its primary, so the just-written read promise needs explicit routing and observation. A two-Region write requirement changes the design: compare documented multi-Region write support, replication/conflict semantics, client routing, recovery and current full cost. Do not claim that a single-Region synchronous log or a cross-Region read replica provides two-Region active-active correctness.

These are source-based design judgments and changed-case prompts, not observed AWS performance or a completed certification objective.
