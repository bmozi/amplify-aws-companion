# Assessor notes: recovery controller

These are author-created decision criteria, not a measured cloud run or a calibrated learner assessment. Several implementations could satisfy a real workload once service eligibility, costs and effective permissions are checked.

The answer should keep five jobs distinct. Resilience Hub assesses a published application's configuration against a policy and recommends improvements; it does not measure Maya's actual customer restoration here. FIS tests a selected failure and can stop on a CloudWatch alarm; stopping injection is not application recovery. ARC routing control changes the Route 53 traffic path for a configured multi-Region design; it does not replicate data, fence writers or erase cached DNS answers. Systems Manager Automation can run ordered steps and pause for approval; the runbook and its caller/role still need the specific permissions and business preconditions. The decision owner may use these tools but remains accountable for the booking promise.

Assessment and fault-injection testing belong to reviewed preparation, before the active incident in this scenario. During the outage, use recorded results and current observations to decide whether to recover; do not launch FIS merely because the diagram lists it before the decision row.

The linked local-gate exercise should print `NO_GO` three times. Missing reconciliation blocks both the initial case and the case with approval; replacing the receipt while removing capacity evidence still blocks cutover. This proves only the deterministic local policy's behavior for supplied flags. The learner must separately explain who would verify B-8417, how the standby's capacity is measured, and what customer-safe degraded operation would mean.

A defensible order holds broad traffic until the old writer is fenced or otherwise made unable to accept conflicting writes, B-8417 is reconciled against an authoritative record, the ninety-second lag is evaluated against the agreed data-loss tolerance, and the standby has a credible quota/capacity or explicit degraded-service plan. It records who may execute each step and who approves the customer-affecting change. After the route change, it measures correct reads and new booking completion, observes clients using old routes, and preserves a separate failback plan. HTTP 200 and a green Automation status are insufficient business evidence.

For changed condition 1, [AWS says ARC readiness check is no longer open to new customers](https://docs.aws.amazon.com/r53recovery/latest/dg/recovery-readiness.html). A valid answer removes it from the new-account plan and uses documented resource/quota inspection, route observations and an appropriate controlled application probe instead. It must not pretend that an existing-customer readiness signal is a disaster health trigger.

For condition 2, a triggered [FIS stop condition](https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html) establishes that the configured alarm reached its threshold and the experiment stopped. It does not establish that any already-started application effect was reversed. The backlog and uncertain booking still require reconciliation, recovery and observation; expansion is held.

For condition 3, deny approval while the old writer may be active and the executor's permissions are unresolved. The team must specify a scoped role for the exact runbook actions and a demonstrable writer-fencing step before approval. [Systems Manager approval](https://docs.aws.amazon.com/systems-manager/latest/userguide/running-automations-require-approvals.html) pauses a workflow for a decision; it is not evidence that these prerequisites passed. Do not award credit for a broad-admin shortcut. No real role, runbook, routing control, second Region or account budget was evaluated in this packet.
