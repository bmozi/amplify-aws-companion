# Network selection assessor notes

These notes support the [six entry-point cases and three A21 extension packets](README.md). They are internal teaching criteria, not independent learner validation or an AWS implementation test. Service references and limitations are in [the lesson](../../reader/BOOK-LOCATORS.md#book-6948135871204c55).

1. **DNS canary:** DNS decisions and HTTP requests are different units. Cached answers and reused connections break the claimed per-request ratio. Measure actual candidate traffic and business outcomes over an appropriate population. If precise request-level selection is needed, investigate a suitable request-routing controller; do not infer its behavior from DNS weights. Reject a promise of an exact short-run distribution.
2. **Private cache:** The same URL can represent different authorized records. Shared reuse without a demonstrated isolation policy can disclose one customer's invoice to another. Initially keep private invoice responses out of shared caching and enforce authorization at the application. Public content can have a separately reviewed caching policy. Merely adding a customer-supplied identifier to a key does not authenticate the customer. Require warm-cache cross-customer denial checks before accepting a later private-cache design.
3. **Two web services:** ALB host/path listener rules are directly relevant to this HTTP routing requirement. NLB transport routing does not itself implement the requested HTTP path decision. The services still authenticate callers and enforce record ownership. Other application routing approaches may be acceptable if justified; the rubric rewards the boundary explanation, not memorizing one architecture.
4. **Capacity:** One surviving worker provides 40 requests per second against demand of 60, a deficit of 20. The hypothetical starting capacity is 80. Redistribution alone cannot meet the stated surviving-load objective. Require measured recovery behavior, realistic headroom and startup time if scaling is proposed. A queue changes waiting time and may not satisfy a synchronous response deadline.
5. **Equipment traffic:** Investigate standard Global Accelerator with a supported regional endpoint, potentially an NLB serving TCP targets. Verify protocol/port support, endpoint and regional availability, encryption boundaries, connection recovery, health behavior and full cost. Compare against a regional NLB alone if global entry addresses cease to be required. No evidence here establishes lower latency, transparent session migration or a reason to add a CDN.
6. **Second Region:** Endpoint reachability does not establish safe booking writes. Define acceptable data loss and recovery time, replication behavior, writer ownership, fencing and idempotency. A useful isolated test would interrupt the active path during a booking, retry through the recovery path and reconcile the accepted requests against durable appointments. Include incomplete replication and conflicting writes. This is a proposed test; no failure injection or reconciliation was executed.

Assess each answer as supported, partly supported or needing revision. Record requirement reasoning, alternatives, limits and proposed evidence separately. If a learner identifies a valid different design, evaluate it against the requirements rather than forcing these candidate choices. A completed worksheet proves only a bounded design discussion, not operational proficiency.

## A21 extension criteria

7. **Cached success:** A retained public page proves that this request could be served from cache, not that its origin or booking service is working. Separate cache-hit observations, origin-dependent reads and the relevant authorized business path. A safe synthetic journey needs its own isolated records, permissions, bounded requests and cleanup. A global average dominated by popular cached pages can conceal an unavailable write path.

8. **Unknown client outcome:** A committed appointment and a lost response are compatible. B's absence of the record is explicitly stale evidence, not proof of nonacceptance. The same request ID cannot prevent duplicate effects if independent authorities each treat it as new. Seek an authoritative result lookup and a demonstrated coordination/recovery design before accepting another write. A reasonable customer message says the request is being checked and avoids claiming either confirmation or failure; it should provide a stable reference and explain the next status path. Merely displaying “pending” is not a resolution mechanism. Require a bounded escalation path and a defined authority for final status. Do not invent an available ledger, successful fencing or synchronous replication.

9. **Method-specific boundary:** The proposed CloudFront `POST` failover is unsupported by the cited feature. Allowed-method configuration does not expand the origin-failover method set. A public read's fallback cannot establish write recovery, and moving a mutation into `GET` is not a valid repair. Accept a justified separate application recovery design if it names authority, uncertain outcomes, duplicate handling, tested access, capacity and customer acceptance. No particular database or multi-region product is mandated by these facts.

For the two architecture options, require an explicit decision about the unapproved confirmed-write loss window. Favoring a simpler regional design can be reasonable when its outage behavior meets the agreed requirement; it cannot silently discard a requirement. Adding another Region can be justified only with the additional state, access, recovery and cost work made explicit. No latency improvement, cost estimate, live failover or learner result has been measured by these design cases.
