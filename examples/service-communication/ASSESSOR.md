# Service-communication reasoning

Internal criteria for the [six cases](README.md), grounded in the primary references linked from unit 15. Accept alternatives that meet the stated requirements and preserve the access boundaries.

1. Service Connect names belong to its configured communication arrangement. An office client is a different caller environment and needs a supported discovery/connectivity path. Inspect actual resolver results and intended entry point; widening invoice permissions does not make the short name resolve.
2. Transport protection does not establish the reporter's business authority. Identify both workload-level permission and customer/record authorization. A useful test allows the intended aggregate operation while rejecting the invoice read, with evidence of which component made each decision.
3. Auth type and policy content are separate. An anonymous allow defeats the diagram's universal authentication claim. Inspect the effective policy path, require the intended principal scope, and test unsigned and wrong-principal calls alongside the authorized signed request. This is a proposed test, not an instruction to change a live policy.
4. Service/service-network auth policies do not apply to resource configurations. Trace the database resource's actual connectivity, sharing and authentication/authorization mechanisms. Do not infer either security or exposure without that review; the known fact is that the claimed service-policy coverage is unsupported.
5. A working protected route proves only that route. Inventory direct addresses, listeners, routes and traffic controls. Demonstrate the intended backend restriction using a harmless denied request from the excluded caller, while preserving the allowed path. A drawing that omits the bypass is insufficient.
6. Retry layers can repeat an operation or amplify work. Identify the durable business request, carry its stable identity through applicable retries, and reconcile the uncertain outcome. Do not assume an intermediary's transport behavior supplies application idempotency. State which retry policy is owned by which component.

Evaluate the reasoning and missing evidence, not the number of product names used. A local HTTP denial elsewhere in the companion does not validate Lattice policies, Service Connect TLS, direct-route isolation or a distributed retry path. Independent learner attempts and service-specific configuration remain pending.

## Loopback fixture reasoning

The [local HTTP run](proxy_bypass_lab.py) should produce 200/403 pairs as shown in the learner table. In the entry-only version, the proxy blocks an invalid workload key, but the invoice backend accepts a direct request and ignores the stored customer owner. The two 200 responses are observable defects **in the deliberately weak fixture**. They are not observations about an AWS service.

In the guarded version, a valid booking request still returns 200. A wrong customer reaches the backend but fails its stored-owner check; a direct request without the proxy receipt fails before invoice data is returned. These are local control-path observations, not evidence of effective IAM, a closed subnet route, a signed AWS request or TLS. The copied valid receipt returns 200 even in the guarded version. It exposes replay and direct reachability that the toy has not solved. Do not grade the guarded version as production-secure or describe the HMAC header as a replacement for AWS authorization.

For the partner change, a strong answer keeps the partner's aggregate operation distinct from invoice retrieval, names the intended private or public entry and real identity mechanism, and tests both the allowed summary and denied invoice/direct paths. It prices the complete candidate path only after Region, runtime, traffic and certificate choices are known. The figure and five local statuses make the reasoning inspectable; they do not establish a live service-network policy, a learner result or a cost quote.

## Two-backend replay reasoning

The [follow-up HTTP run](replay_boundary_lab.py) sends a signed nonce through the entry to backend A. A's own ledger rejects a copy, but independently started backend B returns 200 for the same copied headers because it has no record of the first use. That 200 is an observable defect **in the deliberately separate-ledger fixture**, not an AWS observation. When both handlers use one lock-protected in-memory ledger, B returns 403. The concurrent-claim test establishes one winner for that one local object, not durable or distributed atomicity.

The copied headers come from test instrumentation, not an HTTP response to the caller. Neither version closes direct reachability. A fresh signed nonce produces another 200 and says nothing about duplicate payment or another external effect. A strong changed-case answer carries a stable business operation ID to the payment boundary, reconciles provider receipts after an uncertain reply, and does not label a timeout as either charged or uncharged without evidence. It distinguishes a token replay check from authorization, route isolation and business idempotency. A shared ledger would need explicit durability, availability, expiry and failure semantics in a real design; this fixture supplies none.

## Process replacement and uncertain result

The [process lab](process_replay_lab.py) uses separate backend processes and one same-machine SQLite file with a unique nonce key. A first signed request returns 200; copied headers return 403 at A, B and a newly started B. A new valid signature still returns 200 after replacement. In the local two-process race, exactly one of 32 copies claims the nonce. Those observations support a **single-host, persisted claim** under these conditions, beyond the prior in-memory object. They do not establish a distributed claim store or a secure network boundary.

The injected failure happens after the nonce insert commits and before the normal invoice response. Its 503 followed by a 403 on retry is not contradictory: the receipt was consumed, while the response was unavailable. The fixture performs no payment or other business effect. For a changed payment case, a strong answer refuses both “charged” and “not charged” without a trusted provider result. It proposes one stable business operation ID, an outcome record and a provider lookup or matching receipt; it also describes how retry and reconciliation avoid a second effect. A replay ledger is not a payment outcome ledger. The direct backend port, temporary HMAC keys and same-host database remain exercise limitations. No AWS behavior or learner result was observed.

## Isolated claim copies

The [split-state case](process_replay_lab.py) sends one correctly signed receipt to two separate processes with separate empty SQLite files. Both first calls return 200; both local repeats return 403. The files' claim-set union has one distinct nonce although two responses were accepted. This defeats the inference that a later merged set proves only one earlier acceptance. The fixture models isolated state by construction; it does not create a network partition, synchronize replicas or cause a business effect.

A defensible design answer states the customer promise before choosing a mechanism. If duplicate action is unacceptable, one authoritative claim decision must remain available or the operation must pause when it cannot be consulted. If the business chooses isolated availability, the answer must name the possible duplicate, stable operation identity, recorded outcomes, reconciliation owner and customer remedy. Neither choice is universally best, and this local GET fixture cannot establish the behavior or cost of a selected AWS service. A learner should distinguish first and repeated calls, two accepted responses versus one distinct merged key, and replay claims versus business results; no learner performance has been measured.
