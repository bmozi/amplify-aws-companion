# Environment destination review assessor reasoning

Original author reasoning for the fictional [exercise](README.md), not independent learner or cloud evidence.

1. Preview and practice match the supplied plan, but they are deliberately **shared** on all four inventoried paths. A preview write can affect practice data and users subject to the actual service permissions. The local program cannot prove those permissions, but it must not call the preview isolated. Different hosting URLs do not create different backend resources.
2. Practice's copied Auth, Data and Storage destinations and invented notification target all disagree with its approved values and collide with live. Its practice URL and banner do not repair any of those connections. A future deployment review would block publication and inspect the actual built artifact plus configuration source; it would not “fix” the output file by guessing identifiers.
3. A mixed bundle can sign in through practice and upload to practice storage while reading or writing the live Data endpoint. The exact effect depends on authorization at that endpoint, which this fixture does not test. Review all connection paths, including custom integrations outside generated outputs. The negative control fails on `data` even though other fields still match.

Missing fields and unexpected frontend names are review findings, not invitations to assume defaults. The approved map is a trusted **teaching input**. In real work, establish its owner and revision, inspect the built browser configuration and test both allowed and denied operations with synthetic identities against selected resources. A deny result at one screen is narrower than full isolation; direct API and file paths remain part of acceptance. Branch sharing may be intentional, but shared data, credentials, costs, cleanup and change ownership must be recorded.

The built-browser continuation demonstrates why a fingerprint is necessary but insufficient. Its practice build with copied live configuration has a valid hash and different site bytes, yet fails the supplied practice plan. The same live-configured bytes pass the supplied live plan. The local scan observes only two invented host markers in JavaScript; it does not authenticate an approval, enumerate every runtime destination, exercise backend authorization or prove that a real browser request reaches the expected AWS resource.

For the served-entry changed case, the whole-folder scan is green because approved strings exist in an unused file. The loopback page references a different module entry, so the new check correctly reports those selected values missing from the returned entry response. If the server returns changed bytes for that entry, the byte comparison fails even if its strings still look plausible. This establishes only the local index-to-entry response path. An imported chunk, runtime fetch, service worker or hosted branch can still change what a browser uses. The learner should ask for an approved artifact identity, inspect remaining destination channels and plan a scoped allowed/denied request before claiming isolation.

The read-only outputs inspector adds actual-file evidence without printing selected resource identifiers. If only Data differs, Auth may still be shared; the comparison must be read field by field. Matching selected fields do not establish that two websites came from the same branch, that either file was deployed, or that all custom/runtime destinations match. A mixed Region is a review prompt, not an automatic error: intentional cross-Region architecture needs an owner, latency/cost and permission rationale. A SHA-256 mismatch against a separately approved file stops the proposed release; a self-created digest proves only that the operator hashed some bytes. The local October 19 file parsed as version 1.5 with Auth, Data and Storage in one Region and unauthenticated identities disabled. That is a configuration observation, not current AWS resource, backend rule or customer-access evidence.

The local built-output audit adds one more arrow: this project's current JavaScript build contains the selected values from the ignored local outputs file, and its report withholds those values. A missing selected Data literal could mean the wrong outputs file was built, an omitted field, or a build transformation; stop and inspect rather than asserting which cause. A distinct value from a separately reviewed protected file is a stronger local warning, but a shared value may be intentional and is never called forbidden by that comparison. A false pass is possible if the correct literal sits in dead code or an unused asset while another runtime/custom value controls requests. A source map alone does not satisfy the scan. Neither this scan nor its synthetic tests prove what the hosted branch serves or whether effective authorization separates data.
