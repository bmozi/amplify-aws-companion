# Hybrid exercise: reasoning to look for

These are model-authored review notes for fictional cases, not observations from AWS or an independently validated rubric. Allow alternatives that satisfy the stated constraints and identify their own assumptions.

1. **Ambiguous addressing.** A single destination prefix does not identify which site's identically addressed host was intended. Ask for the addressing and translation/proxy plan, including each boundary's view. Renumbering, deliberate translation or scoped application access have different operational consequences. A hub or DNS alias alone is not sufficient evidence of a fix.
2. **Name-resolution path.** The constrained successful HTTPS test is evidence about that destination and hostname, while the failed lookup points to a separate DNS path. Inspect the client's resolver, forwarding rule, destination endpoint, returned error and authoritative namespace. Do not disable TLS verification or immediately broaden application access. A correct answer distinguishes timeout, negative answer and wrong answer rather than collapsing them into one cause.
3. **Return-path uncertainty.** An incoming request does not prove that the application sent a response or that the response reached the client. First correlate server completion and response evidence, then inspect return routing and traffic controls. Do not assert a missing route solely from a timeout; dependency delay remains a competing explanation until distinguished.
4. **Shared failure point.** Two tunnels do not remove the single router, provider or power dependency. Inventory independent device, access and recovery paths. A revised design still needs a test: a redundant diagram is not measured failover. Record which failures remain shared rather than claiming universal availability.
5. **Capacity under failover.** Probe success establishes limited connectivity, not full workload capacity. Measure arrival/completion rates, backlog age, latency and path capacity during a bounded representative load. Compare adding capacity with prioritizing/degrading noncritical work. Do not promise the primary link's performance from a small probe.
6. **Authorization or another HTTP-layer control.** The correlated 403 and successful peer request suggest an actor-specific path worth investigating. Confirm which component produced the response and inspect the actor's intended permission. A 403 alone does not prove the app itself denied it. Preserve the denial if access is not part of the employee's job; network reachability is not a reason to grant it.

A strong final design shows application and DNS directions separately, resolves overlap, states encryption scope, inventories shared dependencies and defines a customer-level recovery check. It accounts for idle resources and deletion, not only traffic charges. It does not create an Organization or assume that a small experiment allowance can fund an arbitrary hybrid implementation.

For an oral variation, remove the office identity provider or change the second office's requirement to one read-only API. Ask which assumptions break. Record unaided reasoning separately from AI-assisted drafting. Technical review and real learner attempts remain pending.

## Network-evidence reasoning

The healthy tunnel reports a connection state, not a completed booking. The 13:55 DNS answer may be cached or stale by 14:02. The Flow Log row is not yet correlated to the client's translated address, port and time, so its `ACCEPT` cannot be assigned to this request. Even a correlated accept is an IP-flow observation, not application authorization or business success. Reachability Analyzer models the specified AWS configuration and does not send the customer's packets; the office and application layers remain outside that result.

First ask for the actual 403 response's request ID, issuing component and intended employee authorization. This directly tests a plausible application or edge denial while preserving the denial if correct. Next correlate the affected client's source/translated address, destination, port and timestamp with the relevant network record and return-path observations. A different component, missing request record or inconsistent address would redirect the investigation. An absent Flow Log row could reflect logging scope, skipped records or traffic excluded from capture; it does not by itself identify a drop. Avoid changing security rules before identifying the failed boundary.

In the changed case, HTTP 200 establishes that one request was accepted by a responding component, not that the booking was committed or confirmed. Ask for a booking identifier and durable write result, worker/event status and confirmation-delivery record. State what remains unknown if any one is missing. The fictional packet assesses reasoning only; no AWS diagnostic source or learner performance has been validated.

## Multi-VPC topology reasoning

These are authored criteria for a fictional design, not an AWS test or a unique complete answer.

1. **Two VPCs:** Their CIDRs do not overlap. Direct peering is a plausible smaller design for a specific A↔B path. It still needs active peering, source/destination subnet routes, return route, traffic rules, DNS behavior and application authentication/authorization. Transit Gateway can also connect them, but the prompt gives no scaling or segmentation need that justifies its additional attachment and processing costs. A diagram line alone is not packet or API evidence.
2. **Third VPC:** VPC peering is non-transitive. A↔B and A↔C do not imply B↔C. If B truly needs C, evaluate an explicit B↔C peer or a hub with intended route-table association and propagation. A future large topology may favor a hub, but a hub's shared table can create accidental development reachability. Require business permission before making the route.
3. **Same office addresses:** The two `10.20.0.0/16` destinations cannot be distinguished by one ordinary route. Compare migration pain of renumbering with translation's mapping/observability burden and service-scoped access's protocol and authorization limits. DNS names can differ while answers still land in overlapping ranges. Neither peering nor Transit Gateway gives addresses new meaning.
4. **Co-location:** One read-only lookup does not justify broad routed access by itself. A permitted public HTTPS API may be simplest; otherwise compare VPN or provider-arranged Direct Connect to reach private AWS prefixes and a narrowly exposed service when supported. Direct Connect is not encrypted by default. A PrivateLink interface endpoint is inside a consumer VPC; a client in the facility still needs a route to it. Endpoint connection permission and application record permission differ. The design needs current regional/provider cost and failure evidence before selecting a paid connection.
5. **Region and zone:** The supplied facts do not establish which Region has better customer experience or meets data-location constraints. Measure representative whole requests, office calls, volumes and failure needs, then check services and cost. Two AZs can reduce dependence on one AZ for correctly distributed components; they do not remove the single writer, router or identity dependency. A Region choice is not a cross-Region recovery design.

For the ECS change, require the actual task networking mode/interface, subnet route, traffic rule, DNS answer and task identity/service authorization. Accept a different justified design that satisfies the flows, permission and failure constraints. Mark live routing, pricing, independent technical review and learner transfer as pending.

## Connection-selection reasoning

For the additional briefs: A can use the public application endpoint over HTTPS and does not need a private VPC circuit based only on the facts supplied. B supports evaluating Site-to-Site VPN as an expedient private-prefix path, with actual device configuration, tunnel/route behavior and internet-provider failure risks still to validate. C justifies evaluating Direct Connect alongside resilient route design, provider diversity, encryption and a measurable test plan; the prompt does not provide enough data to declare a design adequate or cheaper. D has no evidence that Direct Connect is needed or that its physical path supplies encryption or redundancy; ask for workload and provider evidence before recommending a circuit. An internet path can use TLS, and a VPN still depends on the internet underneath it. Treat the business's acceptance of variation and interruption as supplied requirements, not measured service guarantees.

1. VPN is a plausible starting candidate from the supplied device/connectivity facts, subject to actual configuration and requirements. Direct Connect requires a justified dedicated-connectivity arrangement, provisioning plan and encryption decision. Neither product name establishes capacity or resilience. A stronger throughput or variation requirement could motivate further dedicated-path evaluation; it does not prove a particular design meets it.
2. The supplier operates the consumer endpoint; Maya operates the exposed endpoint service, load balancer and API in this design. Connection permission/acceptance and employee authorization are different checks. Compare the supported protocol and DNS arrangement before selecting the pattern. Broad routed connectivity is not required solely to ask this one API question.
3. Private endpoint addresses must be reachable from the office. Retain or design the appropriate VPN/Direct Connect path and DNS resolution. The two mechanisms serve different portions of the request. A consumer already inside its VPC has a different starting point from an office client.
4. Replies to consumer-initiated requests do not demonstrate a fresh provider-initiated callback route. Polling can retain consumer initiation but changes timeliness and request volume. A callback needs its own reachability, identity, retries and duplicate-handling design. Evaluate those requirements instead of inventing bidirectional network access from the original diagram.
5. Inspect the actual resolver, authoritative namespace, forwarding/private DNS settings, answer and TTL. Preserve the intended hostname and certificate validation. Endpoint existence and a successful raw-IP probe cannot establish the complete named application path. Do not modify DNS before identifying the owner and expected answer.
6. Endpoint placement does not remove a shared provider dependency. Trace the entire successful operation after crossing out the affected zone. Provisioned endpoint hours and other retained components can still cost money with no client traffic. Inventory each charge and deletion owner; no price or successful failover is implied by this exercise.

Accept justified alternatives that meet the stated boundaries. Require the reader to separate service selection from verified implementation. The case set supports a partial conceptual assessment, not a deployed VPN, Direct Connect circuit, PrivateLink service, outage test or independent learning result.

## Storage-extension reasoning

1. One cache hit establishes one read under the observed client/identity conditions. It does not prove full working-set coverage. An uncached read adds the source retrieval path; do not promise it during disconnection.
2. The local acknowledgement is not cloud upload evidence. Treat AWS availability as unknown until the intended content/version is verified there. Do not assume either successful upload or total loss from the facts provided.
3. The allowance fills in eight hours; the threshold is reached in six. Eighteen GiB drains in nine hours at net 2 GiB/hour. At upload 3 the backlog stays constant; at upload 2 it grows by 1 GiB/hour. These constant-rate inputs omit overhead and bursts and are not service performance measurements.
4. Single-writer ownership reduces conflicts but limits offline editing. Explicit review preserves alternatives at an operational cost. Last-write-wins may discard a valid business change; timestamps alone cannot resolve meaning. Do not describe a gateway refresh or scheduled transfer as an automatic merge.
5. Test authorized fresh sign-in and access after restart under the scoped outage. An established session may hide the identity dependency. The design must specify supported degraded operation or a controlled stop, preserving access restrictions.

A complete design response distinguishes local durability, cloud availability, content freshness, authorization and conflict handling. These authored criteria extend the exercise; actual learner responses and deployed gateway/transfer behavior remain untested.

## Subnet and return-path reasoning

- **Baseline:** All conditions represented by this small model are present. `modeled_conditions_present` is not a claim that AWS, TLS or the customer operation works.
- **Wrong B table:** `source_subnet_route_missing`. The worker's subnet is associated with `b-main`; a peer route in the unassociated `b-peer` table is irrelevant to this packet. DNS can still return the intended API address.
- **Wrong A table:** `destination_subnet_return_route_missing`. The API receives the request in the scenario but its subnet's chosen table cannot send a reply toward B. A forward route is only half the design.
- **API security group:** `destination_security_group_inbound_denied`. The direct peer and both routes still exist; routing is not permission. For an ordinary tracked request, a separate reverse security-group rule is not required for the reply, but the request still needs its appropriate outbound/inbound rules.
- **API ACL reply:** `destination_nacl_reply_denied`. An ACL is stateless, so the reply direction needs an outbound rule for the worker's client port even when the request entered on 443.
- **Worker ACL reply:** `source_nacl_reply_denied`. The other subnet also needs an inbound return rule; fixing only A's ACL cannot deliver the reply.
- **Application denial:** `application_denied`. Network delivery does not assign the worker permission to read a booking. Require a correlated API authorization result before attributing the outcome to a route.

For the changed case, expect `source_security_group_outbound_denied`, `destination_nacl_reply_denied` and `source_nacl_reply_denied` together. A broader route does not change any of these independent checks. Strong answers also identify the actual subnet association and both directions of the flow, rather than naming one useful-looking route table. The Python model does not establish live AWS rule evaluation or TLS success.

## Two-direction DNS reasoning

The office-side forwarder asks the private authority for `booking.aws.test`; the VPC-side forwarder asks the office authority for `parts.office.test`. These are separate conceptual inbound and outbound AWS directions, represented by local UDP processes rather than AWS endpoints. A name outside the office-side `.aws.test.` rule is refused by this fixture. After the private record changes at synthetic second 5, the office-side cache still gives the first address and does not ask upstream again. At second 31 it obtains the changed answer. With its rule disabled and cache expired at second 62, this fixture returns `NXDOMAIN` despite the record existing at the authority. Do not generalize that exact error code or TTL to Route 53 configuration.

The changed subnet case has a correct DNS answer and a missing route for the later request. A correct answer is not packet delivery, TLS hostname validation, application authorization or a booking receipt. A strong incident answer records the affected client's resolver, answer, TTL and time, then checks the separate data path and actual operation. A design with a forwarding loop needs correction before deployment; the fixture does not implement recursion or test AWS's loop prevention. Resolver query logs may omit a lookup answered from VPC Resolver's cache, so an absent entry is not conclusive by itself. Require current selected-endpoint cost and effective configuration evidence before any AWS claim. No independent learner attempt has been assessed.
