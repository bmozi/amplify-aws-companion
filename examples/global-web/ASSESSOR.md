# Assessor notes for the global web path

Use these explanations to review your decisions; they do not test CloudFront.

The unsafe fixture's URL-only shared invoice cache gives Bob Alice's bytes after Alice warms `/invoice/current`. The safe local path keeps private responses out of that shared cache, so recognized fixture actor strings select distinct invoice bytes and an unrecognized string gets 403. The actor header is supplied by the caller; it is not authentication. A real design needs verified identity and origin-side record authorization, plus a separate reviewed cache policy for any private response.

When the simulated origin goes down, the warmed public guide still returns 200 while an uncached guide, private invoice and booking request return 503. This shows why a popular cached read cannot be the only availability measure for the origin or booking journey. The lab does not emulate CloudFront cache keys, TTL, invalidation, origin failover, DNS or a committed write with a lost response. The separate lost-response drill addresses the last case under one local SQLite authority.

For the changed guide, a customer name requires a new classification and sharing decision before reuse. A strong answer may keep it private and uncached initially; any private cache design needs a trusted principal, a key and policy that prevent cross-customer reuse, a warm-cache denial test, controlled origin access, expiry/withdrawal expectations and cost review. A correct actor-supplied key does not authenticate the actor. If the reader gives a different design, assess its evidence and bypass paths rather than a service-name match.

For the failback case, Alice's first-location receipt is present at both stores before the second accepts Bob. A route back before reverse copy returns a healthy-looking location that lacks Bob. `NO_GO_WRITER_OPEN` is right while the second toy writer could still change; `READY` follows closure, copy and exact comparison of the accepted rows. The first writer opens only after that check. The missing-receipt and same-slot controls must stop rather than overwrite or silently choose a winner. The fixture's `INSERT` and local uniqueness rules do not settle a real distributed conflict.

If the first location is unreachable, a second store cannot infer the complete set of accepted-but-unreplicated receipts from its own rows. A zero-loss promise needs a separate durable, accessible evidence path or a controlled pause until the old outcome can be reconciled. If a stale client can still write the first location, the Python flag is not a fence; identify every client, worker, queue consumer and credential path that could bypass the selected route. If both stores confirmed different customers for 09:00, do not describe last-writer-wins convergence as a valid booking resolution. Preserve both receipts, stop new confirmations for that slot, investigate ownership and customer remedy, then define a deterministic business resolution. The lab is a local explanation and test, not an AWS failover result.

## Two-writer conflict extension

1. Both customers received a confirmation for one scarce slot. A later visible row can name only one of them; the other acknowledged receipt still needs investigation and a customer remedy. Data convergence and business correctness are different checks.
2. Switching the invented winner changes who disappears from the visible row. It never changes the fact that two confirmations were issued. The program's selected winner is deliberately **not** a DynamoDB timestamp model.
3. A real single-writer transfer must identify and stop every earlier writer, retain accepted and ambiguous receipts, reconcile the destination against that evidence, and check permissions, routing, capacity and the customer path before opening new confirmations. If the source is unreachable, its unseen final writes are unknown. State the recovery-point limit or pause; do not invent a zero-loss claim from a green destination.
4. A single writable Region can simplify the business authority but introduces write-pause/fencing and recovery work. DynamoDB MREC accepts local writes and asynchronously replicates; conflicting same-item writes can converge by last writer wins, and transactions are local to their originating Region. MRSC offers latest-item conditional checks and strongly consistent reads in supported three-Region arrangements, but has cross-Region latency/quorum and feature limits, including no transaction APIs. It cannot repair a schema that represents one scarce slot under multiple unrelated keys or supply authentic identity, external-effect reconciliation and a customer-facing decision. Confirm the chosen Region set, feature support and full cost against [current AWS guidance](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-global-table-design.html) before any implementation.
5. A timeout is an unknown outcome. Keep Bob's stable request identity, ask the authoritative store for its recorded result and show a bounded checking status until verified. A fresh ID can create a second logical booking; declaring failure can contradict an accepted 10:00 receipt. The local fixture does not implement the lost-reply path; use the separate network-selection drill for that behavior.
6. Two conditional writes on two different keys do not enforce uniqueness for one shared slot. Put the slot's admission decision under one authoritative key and operation, or design an equally explicit coordinator; then test concurrency, retries and each deployment path. A real MRSC result for one item would still need a whole-application verification.

Score the explanation, security, recovery, cost and evidence scope separately using the [exercise rubric](../../curriculum/EXERCISES.md). An answer that says “the replicas agree, so both bookings are safe” misses the central defect. These are internal author criteria; no learner response or AWS trial was assessed.

## Late old writer and local epoch guard

The flag-only case accepts `r-old` and `r-new` in separate files for the same 09:00 slot. The early-check case observes epoch 1 before ownership moves to epoch 2, yet the old file still accepts `r-late` afterward. A correct observation at time A does not constrain a separate effect at time B. The guarded case places the epoch check and booking insert in one SQLite transaction and rejects the old generation both before and after the new receipt; it accepts only `r-new`. Its uniqueness rule also refuses a second same-slot insert under the current generation. Five added local tests cover these outcomes, stale transfer, same-slot conflict and invalid owner input.

For the changed cases: (1) only a check enforced at the same write boundary refuses the delayed old effect; (2) an unreachable shared authority calls for a pause or explicitly weaker promise, not a guessed confirmation; (3) a bypassing queue writer defeats a web-only guard; (4) an epoch change cannot reveal an uninspected confirmed receipt; and (5) a real transfer requires trusted operator/workload identity, scoped permission, review or emergency procedure, and an audit trail. The fixture's strings and sequential operations establish none of those controls. Do not call this a regional fence or zero-loss failover. Assess whether the learner locates *every* effect path and states the availability cost of a single authority.
