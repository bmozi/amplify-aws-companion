# Professional reliability: survive the changed requirement

This fictional architecture packet follows [Unit 07's DNS and reliability lesson](../../reader/BOOK-LOCATORS.md#book-0dc111ce46a7729c), [Unit 22's quota lesson](../../reader/BOOK-LOCATORS.md#book-98530e7b95042c56) and [E05](../../curriculum/EXERCISES.md#e05). It builds on the existing [resilience-switches illustration](../../book/figures/resilience-switches.svg). No service, DNS record, queue, replica or second Region is created. Answer before consulting the [assessor reasoning](ASSESSOR.md).

Maya's repair company confirms bookings and processes photos. Customers need correct bookings through one Availability Zone loss; photo analysis may wait up to 30 minutes. The weekday peak is a **fictional** 600 booking requests/s. For each case, draw the serving path and the recovery-control path. Record the exact customer promise, AZ/Region boundary, data and writer authority, surviving capacity, applied quota versus available capacity, DNS policy and TTL/cached-client behavior, status/queue contract, failover/failback action, customer-level probe, cost and cleanup. Keep supplied numbers separate from measurements and defaults separate from account-applied limits.

1. **Two zones, too little survivor.** Each of two AZs has assumed useful booking capacity of 400 requests/s; the shared database is assumed limited to 700. One AZ fails at the 600-request/s peak. Calculate surviving application and database ceilings. Compare a third 400-capacity zone with keeping only two zones but 700 capacity in each. State the extra failure boundaries, warm-up and cost evidence that arithmetic omits.
2. **The scaling request that cannot finish.** An Auto Scaling target requests four new workers after an AZ loss. The account's *supplied* regional quota would permit four, but only two compatible workers are presently available in the requested AZ; a role permission is also missing for the image. A dashboard says “desired capacity reached.” Separate quota, actual capacity, permission, registered/ready target and completed booking evidence. What exactly must be checked before traffic is increased?
3. **Buffered photos, urgent bookings.** The photo analyzer is unavailable for 20 minutes. Compare directly blocking a booking on the analyzer with accepting a booking and recording a separate durable photo task. State the acceptance/status contract, retry identity, message age, poison-work handling and deadline. Change the queue itself to unavailable at acceptance time. Does a client retry create a second booking? Use the [local queue recovery drill](../queue-recovery/README.md) for its bounded behavior only.
4. **The copied wrong value.** A booking amount is corrupted and appears in a read replica and a second-Region copy; a historical backup predates legitimate later bookings. Compare online replication with point-in-time recovery and an independent confirmation journal. Decide when reads can resume and which legitimate effects need replay or customer reconciliation. Explain why an apparently healthy managed data service cannot answer that business question alone.
5. **The tempting DNS choice.** A teammate chooses latency routing between two Regions for “automatic recovery.” The second Region has lower latency for some users but a 90-second lag and half the booking capacity. Compare simple, failover, weighted, latency and geolocation policies against the actual stated objective. State which policy, if any, is a candidate after data, capacity and writer controls are ready, and what a cached primary answer can still do.
6. **A geographic rule changes the promise.** Maya must present country-specific content, but travelers and unresolved IP locations also need a valid default. The content requirement does not say where bookings should be written. Design separate content-location and transaction-authority decisions. Change the requirement so a whole Region is lost while some clients retain its old DNS answer. Identify the safe client response, route observation and reconciliation path.
7. **Managed components still need an operator.** A managed database reports failover complete, an ALB has no healthy targets, and the on-call operator cannot reach the normal identity provider. Decide what each managed component has actually done, how ALB fail-open changes the route risk, which independent operator path is needed, and what customer transaction would close the incident. Name the continuing cost and rehearsal work.
8. **Growth uses up the failover reserve.** Complete the [local growth screen](../reliability-growth/README.md) before changing its inputs. Four fictional weekly peaks rise from 420 to 600 correct bookings/s. A supplied 660 next-week planning case and 10% extra retry attempts require 726 booking-equivalent attempts/s. Two 700-capacity zones leave 700 after either AZ fails; the shared data path has a 750-attempt/s ceiling. Compare the modeled result with three 450-capacity zones, then reduce the shared data ceiling to 700. State which growth assumption might be wrong, when to review it, and what live customer and service observations a small arithmetic model cannot supply.
9. **A feature switch is not a recovery receipt.** The team proposes enabling load-balancer health replacement, more Auto Scaling capacity and a second data copy in one change. The launch fixture has quota room for four workers but compatible placement for only two; its image role permission is unverified. Separate deployment gates, ready targets and correct bookings. Change the data copy to 90 seconds behind and the former writer to still accepting traffic. Design a staged, reversible rollout of health behavior, application elasticity and supported replication. Show the negative test that stops promotion and the customer transaction that permits reopening. Do not present a copy, an Auto Scaling setting or a green target check as a complete recovery result.

Have Codex challenge your first design with a hidden shared dependency and an alternate DNS answer that is technically valid but wrong for customer data. Require it to give a falsifying test and to distinguish official service behavior, fictional inputs and unobserved account state. The [regional recovery](../regional-recovery/README.md), [recovery gate](../recovery-automation/README.md), [scaling model](../scaling-policy-model/README.md) and [resilience path review](../resilience-path-review/README.md) provide bounded local or paper exercises; none implements this full AWS architecture.

A live experiment would first need scoped non-root access, current Region/service/pricing eligibility, a small stop condition and cleanup. Choose whole-run spending and reserve limits for the account you will use. A continuously running multi-Region system may exceed those limits and remains design-only here.
