# Assessor: photo P-42 service selection

Use this after attempting the [learner packet](README.md). Accept a different choice when its assumptions, operating plan and reversal evidence are coherent. The exercise does not demonstrate AWS behavior or learner mastery by itself.

For the four opening cases:

- **Partner file exchange:** Transfer Family is a candidate for managed SFTP/FTPS/AS2 file access backed by S3 or EFS, subject to the required protocol, identity, endpoint and file workflow. It does not validate the business contents or publish a file before downstream checks. A self-managed server shifts patching, scaling, availability and protocol operations to its owner.
- **Background work:** SQS can hold work for independently running consumers, but the application still defines idempotent effects, retry/dead-letter handling, status, ordering and downstream capacity. A queue table can be appropriate under specific consistency and operating requirements; a homegrown durable queue is not automatically equivalent.
- **Database credential:** Secrets Manager provides managed secret storage and integration options. The workload still needs a narrow execution role, compatible rotation and safe retrieval/logging. A static value may work technically while creating avoidable exposure and rotation burden; assess the full delivery path.
- **Name confusion:** Transfer Family is for managed file transfer, not general task scheduling. Match a product to its service contract, then test the business outcome.

1. **Backlog and promise.** At forty arrivals and ten supplier completions per minute, the backlog grows by thirty per minute: **300 requests after ten minutes**, assuming constant rates, no initial backlog and no failures. The one-minute API status can be “accepted, awaiting processing,” provided acceptance really is durable. It cannot promise a completed photo or a one-minute completion. After arrivals stop, clearing 300 requests at ten per minute takes another **30 minutes** under those assumptions. Actual tail latency needs a measured arrival and service distribution.
2. **Starting choice.** A defensible provisional choice is A: the application transaction records P-42 and dispatch intent together, the dispatcher sends the stable ID, SQS holds the successfully sent message, and bounded workers process it. SQS operates the queue service; Maya owns the outbox, IAM design, worker repeat safety, status, poison-work response and supplier reconciliation. B may be simpler when the existing database has measured spare capacity and the team can implement leases and recovery safely; queue reads/writes then compete with the booking path. C needs a concrete protocol or behavior need and an operations team able to own patching, high availability, backup and restoration. Neither B nor C automatically solves supplier ambiguity.
3. **Lost responses.** After a lost send response, the dispatcher retries P-42; it does not mint a new business operation. The worker can see another delivery even if the first send succeeded. After a lost supplier reply, the worker records an *unknown* outcome and uses the supplier's idempotency or status lookup, plus its own durable result record, to reconcile before repeating a non-idempotent effect. If the supplier has neither safe repeat nor query, human review may be necessary. Deleting the queue message or moving it to a dead-letter queue alone does not prove business completion.
4. **Changed facts.** A hard broker-protocol requirement can make C, or a managed broker supporting that exact protocol, worth evaluating; protocol compatibility, migration effort and operations still require proof. Database contention weakens B and makes A more attractive only if the outbox and booking writes remain affordable. Long, ordered, multi-consumer replay describes an event-log requirement; evaluate a stream/event-store path and per-consumer position, retention and ordering scope instead of asserting that SQS Standard, SQS FIFO or a dead-letter queue provides arbitrary replay. Reassess the integration and costs with each changed requirement.
5. **Cost and reversal.** Count SQS requests and payload units, worker runtime, dead-letter retention/inspection, KMS use where configured, data transfer and observability; compare database polling/index/backup load or broker infrastructure and operator time. The estimate needs a named Region, traffic distribution and price date. Reverse A if required behavior is unsupported, observed backlog misses the customer deadline despite safe capacity, or complete measured cost and operational burden favors another path. Do not set a universal USD threshold for the reader.

The [local queue-recovery lab](../queue-recovery/README.md) can show a duplicate external effect when operation identity changes and a safe repeat when it is stable. It does not run SQS, validate IAM, prove supplier idempotency, measure production load, or settle the selected service's cost.
