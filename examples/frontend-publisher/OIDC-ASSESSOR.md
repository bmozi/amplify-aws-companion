# Assessor notes: workflow gate, OIDC trust and Amplify authority

Use these after attempting [E28](../../curriculum/EXERCISES.md#e28). Most changed cases are hypothetical. The role is installed, and a [dated manual GitHub probe](../../reader/GITHUB-PUBLISHER-EVIDENCE-CASE.md) assumed it and completed two account reads. Neither that run nor this answer guide establishes an Amplify publication or visitor result.

1. **Documentation push, gate false:** The workflow has only `workflow_dispatch`, so the push does not start it. The variable also prevents its jobs if someone manually dispatches while it is false. No token, role session or deployment follows from this push. Confirm with a workflow-run listing, not merely by inspecting the YAML. This says nothing about a different release controller.
2. **Manual yes, role absent:** The source gates would allow build and publish jobs to start if the other required repository settings exist, but an absent role cannot be assumed. A build artifact can still be produced before the failed credential step. Inspect the exact run and AWS role inventory; neither an attempted run nor a built ZIP proves publication. Avoid claiming every action succeeds just because the gate is open.
3. **Second workflow:** At the dated probe, the installed trust tested the token's audience and repository/branch subject, not the workflow filename or `AMPLIFY_PUBLISH_ENABLED`. The separate read-only probe on `main` [assumed the exact role](../../reader/GITHUB-PUBLISHER-EVIDENCE-CASE.md) while the flag was false, then completed two reads. The newer Terraform source proposes a publisher-name and called-reusable-path condition for the publisher role, plus a separate read-only probe role with its own name condition. A direct copied-name job lacks the required called-path claim; another trusted-branch caller can invoke the approved reusable file and may match the fictional publisher trust. Its internal release gates and repository write review remain necessary. The historical probe does not prove either candidate role change is installed. Another workflow's AWS operations still depend on complete effective permissions. The variable is no IAM deny. Restrict and review writers and workflows, then inspect actual trust and attachments.
4. **Old subject:** The installed trust uses exact `StringEquals` for the immutable-ID subject. An old name-only subject does not match that value. Check the actual token claim format for this repository before changing the trust; do not loosen it to a wildcard to make a copied example pass. [GitHub subject formats](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims).
5. **Other branch:** Under the stated no-other-grant assumption, the installed policy's exact branch ARN does not allow `StartDeployment` on a different branch. A successful STS role session proves trust, not publication authority. Validate the complete effective role and use a harmless compatible out-of-scope request in an authorized fixture; do not test a risky action merely because a denial is expected. [Amplify action/resource types](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amplify.html).
6. **Gate turned off during work:** The variable blocks new jobs evaluated afterward; it does not recall credentials already issued or cancel a running job. Inspect and cancel that run if the intent is to stop it, then verify its final status. The last hosted page and backend remain until their own lifecycle actions are taken. Inspect resources and later billing separately.
7. **Successful job and spending-cap claim:** Check the deployed revision and actual browser behavior. A reviewed estimate is a planning gate, not a hard AWS spend cap. A budget alert is delayed detection, not universal prevention. Hosting, retained backend resources, retries/logs and GitHub Actions use need separate accounting. Reconcile attributable AWS usage after billing arrives and preserve the account’s chosen credit reserve. [AWS budget timing](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html).
8. **Traffic changes before publication:** At the [listed Amplify transfer rate](https://aws.amazon.com/amplify/pricing/), 40 GB served would be USD 6 on an outside-free-allowance basis before storage or other meters. Do not subtract a free allowance or credit without current account evidence. The USD 1 worksheet's 5 GB premise is invalid, and this expected workload no longer fits the selected small-audience estimate; leave the GitHub gate off and re-scope the audience or experiment. GitHub's two runner jobs and retained artifact are metered against the owner's [Actions plan](https://docs.github.com/en/billing/concepts/product-billing/github-actions), not AWS credits. Confirm the actual branch configuration and current rates before any future run; a paper calculation proves no charge.
9. **Installer script and build job:** In the current workflow, `npm ci --ignore-scripts` runs before the outputs file is written, so the dependency's installer lifecycle script does not run there and that file is not yet present. This is a narrower claim than “the dependency cannot affect the output”: its imported code or build plugin may still run during `npm run build` after the configuration is written. The build job has no AWS OIDC permission; the later publisher job has `id-token: write` and assumes the proposed role only after the gated build. A clean macOS local build tests source/tool compatibility but does not prove the Ubuntu job, AWS trust or hosted visitor result.
10. **Build step changes bytes before hashing:** The publisher compares its downloaded ZIP to the digest supplied by the same build job and checks that the marker names the expected commit and run. Both can pass for content changed inside that build. The [local drill](BUILD-TRUST.md) exercises the actual verifier with fictional ZIPs; its separate approved-content comparison catches the changed page. A hosted marker would support served commit/run metadata, not the trustworthiness of every served byte or a working private API. Do not call this an observed malicious package or live workflow run.
11. **Scenario choice and credit check:** With a 40 GB forecast, leave `review_needed` selected; all three jobs skip before installation or OIDC. Selecting `static_smoke_100_visit_1d` while the checked-in smoke record is pending lets build jobs run only if the other gates are on, but the publish job rejects the record before role assumption. An older `app/` tree also stops there. In a separate arithmetic-only fixture, a 100-visit Hosting estimate of USD 0.02273 and invented USD 0.01 backend subtotal give a USD 0.03273 base; USD 0.25 contingency makes USD 0.28273. A Free-plan read of USD 100.10 leaves USD 99.81727 after that estimate, below the USD 100 reserve, so publication stops before `CreateDeployment`. A denied Free-plan read also stops. With otherwise sufficient credits, one other active run or a ledger check older than one hour stops the estimate before OIDC. A zero count is an observation, not an atomic reservation. A reviewer cannot turn a known 40 GB audience into a 100-visit run by marking the record reviewed. The older 5 GB worksheet is a separate teaching counterexample and is not a live workflow option. Keep the release flag off and re-scope or reprice. Local passing checks are not an AWS publication, traffic cap or GitHub billing proof. See the [estimate tests](../../scripts/tests/test_publisher_run_estimate.py) and [credit tests](../../scripts/tests/test_credit_check_cli.py).
12. **Browser configuration changes:** The build writes the new configuration digest into the ZIP, but the reviewed run record names the previous `AMPLIFY_OUTPUTS_JSON` digest. The publish job's estimate verifier rejects that mismatch before OIDC credentials are requested. An unchanged configuration digest says only that those bytes stayed the same; it does not verify that the backend behind those addresses remained unchanged, the audience forecast is accurate or a customer can sign in. Recheck the actual backend identity, cost inputs and behavior separately.
13. **Old policy receipt:** The zero-finding receipt belongs to the prior two-statement policy hash, so it cannot validate the installed four-statement role's Free-plan and budget reads. The offline checker now rejects missing/changed statement shapes and compares the review snapshot's branch and budget to the private Terraform-selected targets. The October 23 four-statement bytes were checked with Access Analyzer and IAM simulation, then the installed role trust and policy were read back. A separate real GitHub OIDC session proved role assumption and those two reads. Amplify publication, unrelated-target denial under that session and customer behavior remain untested. Terraform source and simulation alone would not establish them.
14. **Second hosting route:** The false variable gates only the checked-in manual Amplify Hosting workflow. A different external CI job or preview self-managed CodePipeline has its own trigger and role path; it is not governed by that variable unless specifically designed and verified to be. The self-managed preview guide says no-scope `ampx deploy` deploys backend and frontend stacks, while `--frontend` addresses only hosting for an already deployed backend. Those stacks would introduce customer-owned S3/CloudFront and any selected compute, logging, alarm, WAF and CI resources with distinct costs and cleanup. AWS labels the route preview and does not recommend it for production. Before a live run, establish a scoped identity, current credit evidence and a complete estimate against the account owner's chosen limit. Keep it design-only; the existing false flag is not an account-wide off switch.
15. **Self-managed cost inventory:** The [fictional worksheet and separate assessor](../costs/self-managed-hosting/README.md) require S3/CloudFront, documented default alarms/SNS and each selected feature's meter. Missing alarms, an enabled but unpriced WAF and a copied managed Hosting subtotal fail the local scope check. Its invented USD 2.24 pass is not an account estimate or deployment approval; current generated resources, rates, credits, scoped identity and cleanup remain open.
16. **Redirected marker:** A matching JSON body at the redirect destination does not prove the original branch URL served it. The publisher's direct-marker check rejects the 302, and the local loopback test includes a matching destination as a negative control. A direct marker establishes only that the requested URL served that commit/run JSON at that observation; custom-domain routing, all page assets, Auth/Data denial and customer behavior require their own tests. No live Amplify response was inspected here.

20. **One audience, two cost paths:** At 1,500,000 hosted bytes each, the selectable smoke record models 100 visits as 0.15 GB. 21. **Stopping publication is not removing resources:** A false GitHub variable stops new jobs of this workflow but leaves hosted bytes and backend resources. The estimate rejects an undecided lifecycle, missing owner or stop/verification method, and missing later billing time before OIDC. Retaining either resource group needs a removal deadline no more than 30 days after the planned end and a positive pre-allowance estimate; the billing recheck follows cleanup within 45 days. The invented smoke arithmetic is USD 0.03273 + USD 0.10 + USD 0.30 = **USD 0.43273**, below the USD 5 planning limit and above the 25% contingency minimum. The later removal deadline goes to the Free-plan credit gate. This is not a live forecast. The operator must still inventory and remove or re-budget each actual resource and reconcile later usage. A valid record does not enforce cleanup or limit demand.

24. **Do not turn a local visit into a bill:** The first local Chrome entry visit fetched HTML, CSS and JavaScript with 284,455 response-body bytes under the probe's gzip policy. On a same-tab reload the page returned `304` and the two assets came from browser cache, giving zero *response-body* bytes but still transferring response headers. The 1,344,387-byte raw all-file set is a conservative publisher-review threshold, not a visitor minimum; an added linked stylesheet raises the first-visit total in a copied build. None of these observations bounds later routes, signed-in API calls, public traffic or Amplify's actual cache and transfer meters. The pending 1,500,000-byte input remains a forecast requiring artifact, audience, backend, account and cleanup review; no local measurement changes the `review_needed` status.

A strong response uses five labels consistently: **workflow trigger**, **role trust**, **effective AWS permission**, **hosted observation**, and **cost/resource lifecycle**. It does not assume that an input in one layer enforces the others. It also names the difference between the Terraform source, a deployed role and an observed AWS request. Ask a follow-up: “What changes if this private repository gains a new writer who can edit workflows but cannot change the AWS Terraform state?” The answer must account for the dated installed branch trust and the current source candidate's called-path limit and different-caller case without inventing a live breach.
