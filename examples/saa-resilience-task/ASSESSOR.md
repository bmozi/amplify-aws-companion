# Assessor notes for eight resilience decisions

Use these notes after the reader has recorded a first decision and changed-fact revision from [the packet](README.md). The cards paraphrase the eight applied skills in [current SAA-C03 task 2.2](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-associate-03/solutions-architect-associate-03-domain2.html#solutions-architect-associate-03-domain2-task2). This is an internal authored rubric. It has not been calibrated against AWS exam items or independent learners. Score a bounded reason and a rejecting observation, not a list of service names.

| Card | Evidence of a defensible answer | First tempting failure to challenge |
| --- | --- | --- |
| 1 — controlled automation | Distinguishes source definition, Terraform state and running resources; diagnoses the console change and database-policy delta before a reviewed plan; protects state ownership/locking and partial-apply recovery. A state file from another environment is a stop condition, not a reason to import or overwrite blindly. | Applying the old plan because it is automated, or treating a drift report as authority to change the customer system. |
| 2 — failure locations | One of two 400-capacity zones leaves 400 against 600 demand; the 700 database ceiling is not the first limit in that failure. Three 400 zones leave 800 after one loss if the shared path and other requirements truly support it; two 700 zones leave 700. A failed shared database invalidates either app-only survivor claim. Require cost, warm-up, routing and data evidence. | Adding normal capacity across zones and calling the sum available after a zone loss. |
| 3 — business metrics | Separates correctly completed 400, definite refusals 100 and unresolved 100 against the stated 600 attempts; reports a customer-completion ratio and an unresolved/deadline measure with explicit denominator and time window. Zero arrivals cannot by itself prove health; verify observer coverage and expected traffic before interpreting no data. | Using 100% healthy targets as booking availability or silently dropping uncertain attempts from the denominator. |
| 4 — single points | Draws an operator/control path as well as the serving path; removes office-server dependence for authorized login, instructions and trusted journal through a suitable independently tested arrangement. If the journal remains unavailable, a green login is insufficient to declare confirmed work reconciled or reopen full writes. | Counting two fleets as end-to-end redundancy while recovery control and data evidence still share one office. |
| 5 — data durability | Rejects row count as content proof; checks booking IDs and amounts against an independent trustworthy confirmation source, identifies legitimate later effects and a controlled replay, then tests application reads and writer authority. A completed copy without usable destination-key permission is not a usable restore. | Choosing newest data because it has more rows, or treating backup completion as customer recovery. |
| 6 — DR strategy | Sequential pilot-light path is 33 minutes and misses 30; warm preparation gives 19 minutes under the stated assumptions. Neither arithmetic result proves actual RTO or the five-minute RPO. Replicated corruption requires a clean point and legitimate-write reconciliation; a warm copy can be fast and wrong. Include standby/rehearsal cost and failback. | Calling a faster traffic switch recovery when it exposes corrupted or missing confirmed work. |
| 7 — constrained legacy app | A healthy second instance can answer `/health` while lacking the old session and uploaded file. Sticky routing does not transfer vanished state; a vendor-supported shared-state design needs compatibility, authorization, performance and failure tests. AWS documents ALB fail-open when all registered targets are unhealthy across enabled zones, so the application still needs an explicit customer-safe response. The [local session drill](../legacy-session-failover/README.md) supports only a tiny proxy contrast. | Treating target health, stickiness or a copied file as full session/customer recovery. |
| 8 — purpose-built services | Assigns routing, backup scheduling and connection management only to features whose documented contracts fit; keeps idempotent booking authority, lost-reply reconciliation, old-writer control and customer acceptance in the application/system design. Separates urgent bookings from deferrable photo work and compares recurring, request, storage, transfer, monitoring and rehearsal costs. | Claiming managed infrastructure implements duplicate-free business effects or one policy fits work with different deadlines. |

An acceptable alternative can choose a different service or topology if it preserves the stated promise, explains what changes, gives disconfirming evidence and accounts for the full operating boundary. Do not score a fictional arithmetic result as a measured AWS result. An independent learner attempt, current service/Region verification and any authorized cloud test would each be separate evidence. Organization-dependent multi-account or multi-region implementations remain design-only in this exercise.

Service-behavior checks for these notes: [ALB target-health routing](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html) and [AWS Backup encryption and key access](https://docs.aws.amazon.com/aws-backup/latest/devguide/encryption.html). Recheck the relevant service documentation for the chosen Region and configuration before a live exercise.
