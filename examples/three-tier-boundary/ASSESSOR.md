# A06 two-worker assessor notes

Use after your first predictions. The lab demonstrates loopback HTTP and SQLite behavior only; it does not emulate ALB, Auto Scaling, RDS or a real identity system.

Alice's repair is stored in the shared database and only in worker A's local receipt dictionary. The next request reaches B, where `/local/{id}` returns 404. A shared read through B succeeds. This is a structural weakness in the local-memory design, not evidence that every application needs a separate database service. Bob receives 404 for Alice's ID and for a missing ID under the fixture's ownership query; the public actor string does not prove real sign-in. A separate human/identity assessment would be needed.

With one unhealthy worker, the toy router skips it. With both unhealthy, the toy router returns 503; **actual ALB target groups can fail open when every registered target is unhealthy**, so the AWS design must not be inferred from the toy result. Configure and test both target-group health and the Auto Scaling group's selected health-check type. A passing shallow `/health` response still cannot prove that a customer can store or retrieve a repair. [AWS ALB health behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html), [Auto Scaling health-check overview](https://docs.aws.amazon.com/autoscaling/ec2/userguide/health-checks-overview.html).

Holding the one-slot local dependency makes a new submission return 503 even with two healthy app workers. This is a controlled semaphore result, not a measured RDS limit. Diagnose a real system using application request/error/latency evidence, connection wait and database metrics, actual query work, and the route/target state. More front-end capacity is not a remedy for every shared-store bottleneck; a proxy may improve connection reuse under suitable session behavior but does not make an expensive transaction free.

For the two-branch change, a worker failure may leave the other worker able to serve if it has enough capacity and a healthy shared dependency. A database outage can stop operations that require authoritative state even if the web tier answers a health URL. A defensible recovery claim needs an actual accepted submission or authorized status read, not just a replaced process. The selected option must be justified by measured business requirements and complete current price inputs; no AWS resource was created by this packet.

For the new outage sequence, `/health/live` returning 200 establishes only that the toy HTTP process answered. `/health/ready` returns 503 because its shallow shared-store probe cannot run; Alice's authorized repair read also returns 503. Adding or rerouting workers cannot repair this common dependency. After the fixture switch is restored, the same authorized read returns 200 with the original issue. That is stronger local customer evidence than either health response, but still does not prove a database restore, real failover, correct behavior under concurrency or a timed recovery target. If the shallow probe succeeds while an expected repair is absent or another customer's data appears, the business check must fail even though readiness is green. A strong answer names the exact missing dependency or invariant before prescribing capacity or routing changes.
