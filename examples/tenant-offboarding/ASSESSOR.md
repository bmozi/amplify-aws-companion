# A10 tenant offboarding assessor notes

Use these after the learner writes a prediction. Credit precise boundaries and changed-condition reasoning, not a confident claim that one function satisfies an entire deletion request.

1. `read` resolves the synthetic member's tenant and checks `ACTIVE` before returning a cache hit. One process's eviction does not invalidate other workers, browser caches or previously issued links. A deployed system needs a distributed invalidation/access policy appropriate to each path.
2. A pending local row becomes `CANCELLED`. A row already marked `DONE` contributes to `already_completed_jobs_to_review`; the fixture has no external effects. A real worker may have completed an effect before its response or status update, so inspect downstream evidence and reconcile under that integration's contract.
3. The active record key and delete predicate both include tenant. Deleting solely by the shared ID could remove Shop B's note. The test's Shop B read and job after Shop A closes are the local negative control.
4. `ADMINS.get(operator) != tenant` denies the wrong fixture string. This is not AWS IAM, a signed identity, delegated support access or proof that every administrative route is protected.
5. The receipt may say Shop A's active rows were removed from the named table and access through the tested local methods stopped. It cannot claim backup/object/search erasure. Inventory each copy, owner, retention clock, restore behavior and evidence before stating a broader completion status.
6. Reusing a tenant ID could collide with old receipts, queued messages, backup data or external references. Choose an explicit reactivation/new-tenant policy and preserve enough tombstone or history to distinguish old work. The fixture does not implement reactivation.
7. Restoring only the older app snapshot puts Shop A's note and pending job back in raw SQLite rows **and replaces Shop B's newer note with its older value**. The separately preserved newer closure decision denies guarded A reads and jobs; B remains authorized but its recovered data is stale. Reconciliation removes A's restored active row and cancels its pending job; it cannot recreate B's lost edit. If closure authority is missing, both tenants fail closed in this fixture. Restoring the old authority too reverts A to `ACTIVE` and exposes the note/job: this is the required negative control. A production answer must preserve the closure decision across restoration, prove the request/worker gate applies it before serving, and reconcile other tenants' newer data. The two-file sequential fixture does not prove atomic denial during a concurrent closure, distributed cache invalidation, legal erasure or a cloud restore.
8. The split-file check sees `ACTIVE`, closure commits, and the later data read still returns `private note`: an observable stale-decision leak. The joined SQLite read holds a `BEGIN IMMEDIATE` transaction, so the competing closure write is refused until that read completes. Closure can commit afterward and the next read is denied. This demonstrates one-host database ordering, including a heavy write reservation on a read. It does not establish distributed linearizability, cache or worker denial, restored-file authority, throughput suitability or AWS behavior. A strong changed-case answer names the bypass and the decision point it would have to consult.

A strong architecture answer separates access revocation, active-store cleanup, queued/in-flight work and retained-copy expiry. It names an authorization source, idempotent workflow identity, copy inventory, measurable completion evidence and customer wording for partial completion. It does not use a regulatory or legal claim without an applicable reviewed requirement. Four original tests cover warm-cache denial, pending-job cancellation, unaffected Shop B, repeat closure, wrong-operator denial and completed-job accounting. Five restore-boundary tests cover local old-snapshot resurrection, guarded denial, reconciliation, missing authority and the unsafe co-restore counterexample. Three ordering tests cover the stale check, local serialization and receipt. They do not test distributed races, real credentials, files, search or AWS backup behavior.
