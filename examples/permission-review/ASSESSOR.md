# Effective-permission review: assessor reasoning

Authored reasoning under the case assumptions, not an AWS test receipt. The [lesson](../../reader/BOOK-LOCATORS.md#book-47726780fac09ca7) links current primary policy-evaluation, boundary, role-passing and simulator guidance.

1. With A alone, writing is implicitly denied. B supplies the matching identity grant, so writing becomes allowed under the stated exclusions. The omission in A was not an explicit deny. An applicable explicit deny or restricting control could change the result. Review all effective attachments rather than treating one narrow file as the role's permanent maximum.
2. Reading is allowed and writing denied through the stipulated identity-policy path. Removing A leaves no identity grant, so the boundary alone does not authorize reading. This case is not a conclusion about resource-policy grant paths.
3. The direct role-ARN grant is limited by the boundary's implicit denial. The direct exact-session grant is not limited by that implicit denial under the stipulated same-account rules. Adding an applicable explicit deny causes denial. Do not generalize to arbitrary principal wildcards, other accounts or omitted service controls. This case teaches why principal type must be recorded, not how to bypass the intended boundary.
4. The result establishes only what the supplied simulation inputs produced. The live-role conclusion has insufficient evidence. Obtain the actual caller/session context, applicable policy documents and versions, exact action/resource and relevant service restrictions; record omissions. Use appropriate diagnostics and a reviewed harmless real request when prerequisites permit. A simulator did not execute the service operation or verify sign-in/trust.
5. The direct denial is insufficient. The configured service can operate using the passed role, and the deployer controls code running with that authority. Review permitted workload mutations, passable roles, service trust, execution permissions and possible data destinations together. Narrowing only the deployer's direct read actions misses this delegation path. No actual exploit or cloud access is performed by this design case.
6. An incompatible resource type can fail without exercising a meaningful target restriction. Deleting a valuable app risks harm if the expected denial is wrong. Prefer static/simulation review first, then an authorized harmless job-metadata read against an existing disposable out-of-scope fixture with a valid action/resource pairing and the intended caller. Verify that any denial is actually authorization-related rather than a missing target, invalid request or unrelated failure. If a suitable fixture or identity is unavailable, record the live check as pending.

Do not award a demonstration claim for a correct explanation. Actual role bootstrap, effective-policy inspection, non-root sign-in and allowed/denied service evidence remain separate gates. Organizational examples remain design-only in this exercise.
