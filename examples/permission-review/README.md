# Follow the permission, not just the role name

Original design-only cases for the [identity lesson](../../reader/BOOK-LOCATORS.md#book-47726780fac09ca7). These are descriptive rule cards, not deployable policies or an IAM emulator. No AWS calls, account changes or tests are performed. Read the [assessor reasoning](ASSESSOR.md) after answering.

For cases 1–4, assume an already authenticated role session in one fictional account. The object is an existing plain S3 object. All stated grants match its exact object ARN and request conditions. There is no KMS authorization dependency, additional service-level restriction, cross-account access, organization policy, endpoint restriction or other unstated grant or deny. These exclusions make the cases solvable; a real review must investigate them rather than assume them away. Each case is independent unless it explicitly builds on another.

For each case, identify **allowed, denied or insufficient evidence**, explain the policy path and state what would change your conclusion.

1. **One document, two attachments.** Identity policy A permits `s3:GetObject`. It omits `s3:PutObject`. There is no boundary or session policy. First evaluate a write with A alone. Then attach identity policy B permitting `s3:PutObject` to the same object. Has A's omission prevented the new write?
2. **A ceiling without a grant.** Identity policy A permits both read and write. The boundary permits only `s3:GetObject`. Evaluate each operation through this identity-policy path. Now remove A entirely and evaluate reading with the boundary alone. No resource policy grants either operation in this case.
3. **Role versus session.** No identity policy grants object reading. The boundary omits it. Compare two separate resource-policy variants: one grants `s3:GetObject` directly to the role ARN; the other grants it directly to the exact requesting role-session ARN. No explicit deny applies. Explain why the variants differ under the documented same-account rules. Then add an applicable explicit deny and reconsider the second variant.
4. **A review with an omitted input.** A standalone simulation used only A from case 1 and returned an implicit denial for writing. Someone presents that output as evidence that a live role cannot write. Its full attachments, resource policies and session context have not been inspected. What is actually known? What must the reviewer collect before making the live-role claim?
5. **The service has another badge.** A deployer cannot directly read a confidential dataset. It can configure a workload and pass an approved execution role to the service. That execution role can read the dataset, and the service can assume it. The deployer controls the workload code. Does the deployer's direct read denial establish that it cannot cause the data to be read? Identify the authority chain and the design question before suggesting any policy edit.
6. **The wrong negative test.** A publisher must be denied access to a different application's job metadata. The test instead simulates a job-reading action against an unrelated IAM-role ARN. A second proposed test attempts to delete a valuable application because the operator expects denial. Explain why neither is satisfactory evidence for the intended read boundary, and outline a safer meaningful check.

Close with a review record listing intended action, forbidden action, caller, target, policy inputs, missing facts and next safe evidence. Ask Codex to critique the record without generating or attaching permissions. Explain the changed case without copying its rationale. These cases have no independent learner or live authorization results.
