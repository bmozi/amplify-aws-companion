# Automate an existing resource only inside its approved fence

Read [the upkeep-versus-event lesson](../../reader/BOOK-LOCATORS.md#book-cd6b5ef15e723d8f) and [the staged fleet lesson](../../reader/BOOK-LOCATORS.md#book-b139eca792554b54). These six fictional cases assess the two CloudOps Domain 3 task 3.2 skills: operational-process automation and event-driven automation. Write a first answer before the [assessor reasoning](ASSESSOR.md).

For each case, name the existing resource and its owner, trigger, exact target/version identity, controller, authority/approval, duplicate or stale-input behavior, cost and stop rule, and separate business verification. Compare one credible alternative. A matching event or a successful runbook step is not the complete result.

| Case | Changed condition | Decide |
| --- | --- | --- |
| 1. Monthly patch ring | 240 managed nodes are eligible only after a fresh inventory and approved baseline. The team wants 5% concurrency and zero tolerated errors; one canary fails its application check. | Design the Systems Manager maintenance/runbook boundary and target proof. How many targets are in the planned concurrent upper bound? Which work may already be running when expansion stops? |
| 2. A new matching node | A node receives the fleet tag after the approved target list was frozen. The selector finds 241 nodes, but approval names 240 IDs. | Does a tag grant permission to patch the new one? How should a repeated operation ID behave? Distinguish inventory from authority. |
| 3. An object arrives twice | S3 emits two notifications for the same intake object version. A converter writes a derived object to the same bucket. | Select direct S3 notification or EventBridge routing for the stated needs; define duplicate identity and a prefix/bucket rule that prevents a self-triggered loop. Which destination permission is needed? |
| 4. A stale Config finding | Config reports one production rule violation from 42 minutes ago; Terraform source now specifies a different intended value. | What fresh checks and source-of-truth change precede a Systems Manager remediation? When does a human review remain necessary? |
| 5. An alarm and an agent proposal | A network alarm fires; AWS DevOps Agent proposes a broad security-group change to improve response. One customer operation is failing, but the target path is unconfirmed. | Separate investigation suggestion, action authorization and measured customer recovery. Which least-privilege read-only step narrows the cause? |
| 6. “Succeeded” without proof | An Automation execution reports success, but two intended nodes were never selected and the patched nodes' application health is unknown. | What per-target receipt, source inventory and customer test are needed? Should the next ring start? Estimate action/log/runtime and cleanup costs before a live repeat. |

Run [the staged fleet decision model](../fleet-maintenance/README.md) for cases 1–2 and 6, [the local event/control lab](../monitoring-automation/README.md) for cases 3–5, and [the configuration-owner model](../configuration-change-control/README.md) for case 4. They use fictional state and make no AWS calls. Ask Codex to produce near-match events and a target omitted by a tag; verify expected IDs yourself. Do not supply credentials or customer records.

Before any AWS run, verify a scoped non-root role, selected account/Region and exact resources, current service price and plan eligibility, a complete estimate against spending and reserve limits chosen for that account, a stop rule, cleanup and delayed billing. Systems Manager Automation can incur charges, and a budget alert is not an enforced cap. Organization-wide patching remains design-only in this packet. It enables no service or agent.
