# Assessor reasoning: existing-resource automation

Read after an independent attempt. The cases are fictional; no AWS runbook, event route, agent or learner was tested.

1. **Patch ring:** Five percent of 240 is 12 planned concurrent targets. Compare the fresh selected IDs with the approved inventory and pin the baseline/document version before dispatch. A failed application canary stops later rings. An error threshold can stop sending new work while already-running actions finish; it cannot undo a patch. Verify each node and the billing application separately.
2. **New node:** The tag is a selection clue, not approval for a broader target list. Stop or send the new ID through review; do not silently patch 241. A stable operation ID should return the recorded result on replay in the local model, but a live external effect still needs observed-state reconciliation.
3. **Object twice:** S3 notifications are at least once. Use the exact bucket/key/version or another sound object identity for duplicate control and publish an effect receipt. Filter to incoming objects and write elsewhere, or use a separate bucket, to avoid a loop. Direct S3 notifications can be sufficient for one known source/destination; EventBridge is a candidate when content routing or several targets justify it. Validate destination resource policy and the worker's read/write role separately.
4. **Stale Config:** Check the exact resource/account/Region, evaluation time and current configuration. Find the reviewed owner of desired state; change Terraform source if that owns the value, rather than making a competing manual fix. Review disruptive effects and the runbook's role/parameters/stop rule before any mutation. A stale finding cannot authorize a blind action.
5. **Alarm and agent:** The alarm is a scoped metric state, and the agent output is an investigation/recommendation. Neither proves the failing request's route or authorizes a broad security-group change. Join a safe request identifier, destination, related logs and current rule state first; then propose a bounded owner-reviewed change with allowed/denied and customer checks.
6. **Succeeded:** A top-level execution status does not include omitted intended nodes or unknown application health. Compare the approved target manifest to per-node outcomes and exceptions, then check the real customer path. Do not expand while targets or health are unknown. Price runbook steps, underlying compute/patch resources, log ingestion/retention, retries and cleanup for a selected live design.

The answer should distinguish scheduled maintenance, event routing, runbook effects, AI suggestions and business results. The local companions only test decision rules on supplied data; they do not prove AWS permissions, cost, event delivery, OS patching or independent learner competence.
