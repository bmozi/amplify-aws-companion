# Put each database read where its promise can be kept

Read [the illustrated Unit 21 decision](../../reader/BOOK-LOCATORS.md#book-00750a33d2735e31). Assume Maya's booking service uses a fictional RDS PostgreSQL DB-instance writer. The manager's report may be one minute behind; a customer booking confirmation may not appear lost after commit. These are design cases, not an AWS replica configuration exercise. Answer each before opening the [assessor reasoning](ASSESSOR.md).

For every case, name the operation and freshness promise, the chosen read endpoint, the authoritative write location, failure behavior, one positive and one negative check, cost drivers and what observation would reverse the decision. Compare a plausible alternative, not a service slogan.

| Case | Changed fact | Decide |
| --- | --- | --- |
| 1. The delayed confirmation | Booking `B-42` commits on the writer. A selected asynchronous replica still shows the previous state. | Which response/read confirms acceptance? What may the report display, and how is its age shown? |
| 2. “Multi-AZ gives free readers” | The team has an RDS Multi-AZ **DB instance** with one standby and points reports at the standby. | Can it serve that read? Contrast with a DB-instance read replica and a Multi-AZ DB cluster reader without conflating the deployment types. |
| 3. A replica with no traffic | A read replica is healthy, but the application still sends every report query to the writer. | Which application routing and permission observations prove the intended read actually moved? Why did provisioning alone change no load? |
| 4. A slow report query | The writer's slow query scans more rows than needed. A replica would run the same query, and booking commits are also slow. | Compare query/index review, a replica and writer/resource changes. Which bottleneck can each address? Use representative read/write and result-correctness evidence. |
| 5. Reader outage | Two app workers each have a pool of 40 connections; a replica fails and all report reads fall back to a writer already near its connection and I/O limit. | Budget total connections and load after failure. Should the report wait, degrade or overload the writer? Name a bounded fallback and recovery receipt. |
| 6. Wrongly fresh copy | A manager asks for the latest report after an accidental deletion, and the replica has already copied it. A backup from before deletion lacks later valid bookings. | Which copy is useful for read scaling, which for recovery, and what independent business record reconciles the gap? A replica is not a backup. |
| 7. The fallback budget | In a fictional drill, the writer permits 100 application connections. Booking traffic may need 55 and operations reserve 15. Two report workers each allow 40 connections. The reader fails. | How many writer connections remain for **both** reporting workers together? What happens if each keeps its 40-connection maximum? Propose a shared limit and a visible response for reports that cannot run. What else must be checked before enabling fallback? |

For cases 1 and 6, run the [local recovery-copy drill](../recovery-reconciliation/README.md). For cases 4 and 5, run [query plans](../query-plans/README.md), [connection-pool behavior](../connection-pool/README.md), and [capacity arithmetic](../database-capacity/README.md). Use the [cache consistency](../cache-consistency/README.md) and [cold-cache burst](../cold-cache-burst/README.md) exercises to assess the third read path. These tools use local SQLite, process fixtures and synthetic inputs; they cannot configure, time or price an RDS replica.

For case 7, write the subtraction and the maximum offered connections before consulting the assessor. Then change only the booking allowance from 55 to 75: can the same report limit still fit? A connection budget is a ceiling on open connections, not proof that the writer has sufficient CPU, I/O or query capacity.

Ask Codex to identify the first unsupported freshness or failure claim in your diagram. Give it synthetic IDs and observations, not customer data or credentials. Before any live database test, verify exact engine/version and selected Region support, a scoped non-root identity, a conservative whole-run estimate and credit reserve chosen for the account, stop and deletion rules, backup/retention consequences and delayed billing. No database is created by this packet.
