# Assessor reasoning: database read architecture

Read after an independent attempt. The cases are fictional; no AWS database or learner result was observed.

1. **Delayed confirmation:** Return a confirmed result from the authoritative commit path; if a subsequent read is required, use a path meeting the specified read-after-write need. Do not query a lagging asynchronous replica and tell the customer the booking vanished. A report may use that reader if its actual data time/lag fits the one-minute tolerance, with a pause or fallback if it does not.
2. **Multi-AZ types:** A Multi-AZ DB **instance** standby provides high availability and cannot serve reads. A separately created DB-instance read replica can serve eligible read-only queries but is asynchronous and separately billed. A Multi-AZ DB **cluster** has readable replicas and distinct topology/cost. Identify the selected deployment type and engine support before drawing an endpoint.
3. **No moved read:** Observe the application's target endpoint, credential role, actual query path, writer/reader query and resource metrics, and customer result. Creating a replica does not reroute clients automatically. Verify a report read on the reader and a write attempt on the proper writer path; test how fallback is controlled.
4. **Slow query:** A replica can move report load off the writer but may run the same expensive query; it does not make booking commits faster. Inspect the plan, rows, I/O and indexes against representative data, then measure read/write effects and exact result rows. A writer size or storage change is a candidate only after the binding limit is known. Compare cost and operational risk of each remedy.
5. **Reader outage:** The two pools alone can offer up to 80 connections before other clients, retries or administrators. An unrestricted fallback can transfer both report load and pool pressure to the writer. Give report reads a bounded concurrency/time budget or pause with a visible stale/unavailable state, then reopen only after measured writer/reader headroom and correct results. A health metric is not a capacity promise.
6. **Wrongly fresh copy:** The replica follows source changes, including the bad deletion. A prior backup can restore an earlier state in isolation, but later valid bookings need reconciliation from trustworthy records. The [local recovery lab](../recovery-reconciliation/README.md) demonstrates that distinction with a synthetic confirmation ledger; it is not RDS replication or recovery evidence.
7. **Fallback budget:** The fictional connection budget leaves `100 - 55 - 15 = 30` connections for reporting across both workers. Their separate maxima offer `40 + 40 = 80`, which can exceed that allowance by 50; this is offered capacity, not a claim that 80 connections are actually open. A shared cap of at most 30, for example two enforced limits of 15 if there are exactly two workers, protects the stated connection allowance; excess reports need a bounded wait, stale result if acceptable, or an explicit unavailable response. When booking needs 75, the reporting allowance falls to `100 - 75 - 15 = 10`, so the previous 30-connection cap no longer fits. A shared coordinator or correctly updated per-worker limits are needed when worker counts change. Before enabling fallback, measure query and writer I/O/CPU headroom, timeouts, connection use, customer results and the selected database's actual limits; connection arithmetic alone does not prove safe operation.

The strong answer separates read scaling, availability and historical recovery. It states which operations need current authority and which tolerate lag, observes actual routing, and keeps the writer's commit and connection limits in view. Local fixtures and paper cases do not prove selected AWS configuration, latency, cost, failover or independent learner performance.
