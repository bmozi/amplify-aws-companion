# Assessor: customer, client and pod credentials

Keep these notes separate until the learner has recorded a first answer. Credit a decision only when it names the actor, credential, binding, exact AWS action/resource or application operation, and a meaningful negative case. A generic “least privilege role” answer is incomplete.

1. **API upload.** The API checks Maya's authenticated identity against the repair record. Its worker uses a scoped workload role to write the selected object prefix. Leo's valid sign-in must fail the application ownership check; a worker write outside its intended prefix must fail at the selected AWS authorization boundary. These are different denials.
2. **Direct upload.** A presigned request delegates the signing role's bounded S3 operation for the URL's lifetime and request shape; the issuing API must first check repair ownership. An identity pool instead vends temporary client AWS credentials, adding a client IAM-role and bucket-policy surface. In either design, the server must bind the upload to the correct repair and check completion/content rules. Compare transfer path, credential exposure, revocation window, CORS and operational cost for the actual workload.
3. **Namespace move.** An association for `repairs/photo-writer` does not follow `preview/photo-writer` automatically. Inspect the pod's serviceAccountName, namespace, association, agent health and SDK credential provider. A successful AWS call might be using unexpected node or static credentials; inspect the actual caller before calling the path safe. The offline worksheet reports a binding mismatch, not a simulated AWS denial.
4. **Shared node.** A narrow pod role does not neutralize a broad node role if pods can reach node credentials. Constrain the node role, restrict metadata access as appropriate to the platform, and verify which principal the worker and metrics pod actually use. Test a safe neighboring-prefix denial with the unwanted pod, not a destructive action.
5. **Cross-account.** The role associated with Pod Identity is in the cluster account. Cross-account access needs an explicitly reviewed target design: resource policy plus source-role permissions where supported, or an authorized target-role assumption chain, with any applicable KMS key grants and policies. Read back both sides and test a selected allowed and denied object request. Do not infer access from the EKS association alone.
6. **Failure.** Queue bounded work and surface an operator/customer state rather than silently switching to a permanent key or broad node credentials. Define retry limit, duplicate protection, maximum delay and a stop condition. Credential acquisition failure and S3 AccessDenied after a valid role session require different investigation.

**Changed-case challenge:** The service account is correct, but a stale static access key precedes Pod Identity in the SDK credential chain. A successful S3 write is **not** proof Pod Identity worked. Require an actual caller readback, remove the unintended key, repeat a useful allowed request and a safe out-of-scope denial, then capture the role/association/policy versions and time.

The local tests establish only that the toy worksheet catches named omissions. A selected deployment would still need current AWS setup, actual principal and request observations, cost and cleanup reconciliation, and independent learner review.
