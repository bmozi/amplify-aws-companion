# Processing-selection assessor notes

These provisional criteria allow different justified designs. Familiar service names alone do not satisfy the cases.

1. A batch scheduler can address submission, waiting and supported compute allocation while preserving a valid executable. Rewriting in Spark needs a processing reason, such as an appropriate distributed operation, not merely a nightly schedule. Require supported dependencies, resource sizing, retries and verified outputs. Scheduling does not parallelize arbitrary program internals.
2. Compare catalog/integration needs, connectors, transformations, operating ownership and full costs. The schema describes representation; its inferred type cannot establish a money unit or business acceptance rule. Require an explicit source contract and reconciled output. Glue is a candidate, not a correctness guarantee.
3. Check exact runtime/framework versions, library installation, execution configuration, supported interfaces, security/network access, startup, logs, recovery and representative performance. Establish equivalent expected outputs before interpreting timing. Do not infer a tested deployment option from a framework's name.
4. Completion is 70 seconds in this simultaneous four-partition model; the 25-second average describes mean assigned duration. Eight workers still leave one unchanged 70-second partition. Investigate skew and whether that partition can be divided with a correct combine rule. Preserve key relationships and output facts. This calculation does not measure a real distributed engine.
5. A scheduled compatible worker is a credible initial candidate. Bound working memory, duration, dependencies, volume and failure recovery. Identify observed limits or changed requirements that justify another model. Ten MB on disk is not a reliable upper bound on memory after parsing or joining.
6. End-to-end time is 55 minutes, exceeding the deadline by 10. Separate queue wait, computation and publication. Extra workers help only if they address the actual bottleneck without overloading dependencies. Investigate waiting capacity/priorities and publication work as well as compute; do not infer the remedy from duration arithmetic alone.

For the transfer, require a replay input boundary, separate candidate output, exact record/aggregate checks, a deliberate reader-selection step, recovery ownership and retained-source policy. Include read/transform/write/query/storage/log costs and reruns. These are design criteria; the local Parquet drills do not prove atomic cloud dataset publication, source completeness or distributed performance.
