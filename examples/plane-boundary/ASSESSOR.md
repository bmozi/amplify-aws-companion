# Assessor: keep each receipt in its lane

Use this after preserving a first answer. These are authored reasoning criteria, not an observed learner score or a calibrated certification item.

## Case 1

An infrastructure-update result supports a named change only after the exact account, resource, revision and status are checked. A homepage HTTP 200 supports that one page response. The reported Save error contradicts a claim that this attempt completed successfully; the stored-result state remains unknown until an authorized readback or trustworthy write evidence is examined. A bounded investigation correlates one synthetic request ID/time with application response and write result, then reads the authoritative record under the intended identity. A second identity must be denied through the actual API and object-read paths. Hiding a button is presentation behavior, not authorization evidence.

## Case 2

Candidate B is the stronger hypothesis for the stipulated inability to create a resource during recovery because its required resources are prepared beforehand. It is not a success claim: the standby may be stale, unreachable, too small, wrongly permissioned or outside the measured recovery deadline. Before an incident, verify capacity, data freshness, switch authority, access, cost and a runnable reversal path. During a drill, start the clock at the agreed customer-impact point; observe the switch, allowed and denied requests, accepted-record reconciliation and customer completion by the target. Stop on unbounded spend, wrong target, cross-customer access, uncertain accepted data or a failed reversal. If the latest accepted repair is absent, fast routing does not satisfy a promise to preserve acknowledged work. The owner must decide whether to recover it, disclose an agreed loss or reject the design. Candidate A can avoid pre-provisioned idle footprint when creation is available and the recovery objective permits its measured delay, but that advantage does not rescue it in the stated failure.

## Case 3

CloudTrail Event history shows management events within its stated scope; it does not include data events. Absence of a management event does not rule out an S3 object read. Determine whether object-level events were configured for that resource and window, then inspect any collected event with the exact object, principal and time alongside current policies, access routes and application evidence. If no suitable past events exist, do not manufacture a historical conclusion. New collection starts prospectively. Decide which resource types, selectors, retention, access to logs and expected volume/cost fit the investigation need; an indiscriminate enablement is neither retroactive nor free.

## Decision quality

A strong answer labels configuration, service operation and customer outcome separately, names one observation that would reject the preferred design, acknowledges a credible advantage of the alternative, and leaves uncollected evidence unknown. The AI critique is assistance, not independent assessment. The case neither executes AWS failover nor measures a 20-minute recovery.
