# Who owns this resource when the bill arrives?

Maya's repair company has separate development and production accounts. Each team must mark billable resources with `CostCenter`. One team writes `costcenter`, one creates an untagged resource, and a third removes the tag a week later. A dashboard can show the damage after the fact, but Maya also wants preventable mistakes stopped before deployment. The answer needs **several controls with different jobs**, plus an exception path for resources that cannot be tagged in their create request.

This illustrated **organization design exercise** supports [SAP-C03 skill 3.3.3](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-professional-03/solutions-architect-professional-03-domain3.html). It extends [accounts and governance](../../reader/BOOK-LOCATORS.md#book-71a7c1be66a5700e). This exercise creates no Organizations policy, AWS Config rule, or billable resource.

## Give each control one honest job

| Control | What it can establish | What it cannot establish by itself |
| --- | --- | --- |
| **Organizations tag policy: basic compliance** | Standard spelling/case and allowed values for tags on supported resource types; enforcement can reject noncompliant *tagged* operations where supported. | It does not block a resource created with no tags. Untagged resources do not appear as noncompliant in its ordinary compliance results. [AWS tag-policy enforcement](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_tag-policies-enforcement.html), [best practices](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_tag-policies-best-practices.html). |
| **Organizations “Required tag key” plus supported IaC validation** | A required-key definition can be checked before supported CloudFormation, Terraform, or Pulumi deployments; configure warn or fail behavior in the selected integration. | A report rule alone is not a universal API-level deny. Confirm the actual integration, provider version, supported resource type, account and Region. [AWS IaC enforcement guide](https://docs.aws.amazon.com/organizations/latest/userguide/enforce-required-tag-keys-iac.html). |
| **SCP for selected member-account API requests** | A tested deny can constrain an IAM principal's create request when the service/action exposes request-tag conditions; guard untag and tag-mutation APIs separately where supported. | SCPs do not grant permission, do not govern the management account or service-linked roles, and cannot make an action include a tag if that action has no tag-on-create field. [AWS SCP scope](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html), [EC2 tag-on-create example](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/supported-iam-actions-tagging.html). |
| **AWS Config `required-tags` for supported recorded types** | Find a resource whose recorded tags do not match the rule, after creation or change; supply a review trigger. | It does not prevent creation. Tag recording and supported types vary; AWS says the managed `AWS-SetRequiredTags` automation document does not work as remediation for this rule. [AWS Config rule](https://docs.aws.amazon.com/config/latest/developerguide/required-tags.html). |

The policy order matters. Decide the required key and approved values, identify **specific resource types and API actions**, verify tag-on-create and tag-on-update support, then choose where to warn, block, detect, or remediate. Do not paste a universal `aws:RequestTag` condition onto every create action. AWS documents `aws:RequestTag` and `aws:TagKeys` for actions that support the condition; a `ForAllValues` set test can pass on a missing key unless paired with a presence test. Review the actual service authorization reference and IAM condition semantics before writing an SCP. [IAM tag conditions](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_tags.html), [missing-key behavior](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition_examples-multi-valued-context-keys.html).

## Fill the design matrix before reading the assessor

For each case name the **resource/action support you must verify**, expected create/update/untag result, prevention or detection layer, exception owner, and a negative test. Assume all names and accounts here are fictional.

1. **Wrong value at create:** An EC2 instance request includes `CostCenter=Unknown`. The team has an enforced basic tag policy for that supported resource type and an otherwise permitted IAM create path. What should the tag policy do? What result would show the deployment was actually stopped?
2. **Missing key at create:** The request creates the same EC2 resource without `CostCenter`. Why does basic tag-policy enforcement alone miss this? Compare a configured Terraform required-tag validation gate with a narrowly tested member-account SCP on a tag-on-create action.
3. **No tag-on-create support:** A *hypothetical* resource API can add tags only after creation. Maya copies the missing-tag SCP from the EC2 case to this action. What happens to every create? Design a bounded create-then-tag workflow, an exception window, ownership and a detection/reconciliation check, or choose a resource type that supports the requirement. Do not claim a specific AWS service has this limitation without checking its current API.
4. **Untag and bypass:** A team removes `CostCenter` later; a service-linked role creates a resource; and the management account hosts a workload. Which earlier create gate is irrelevant to the first change? Which principals lie outside the SCP? How would an existing-resource inventory and reviewed remediation reveal these paths?
5. **Stale finding:** Config flags a resource as untagged, then its owner fixes it. Before automation changes anything, what current observation and exact resource identity must be checked? What could a broad tag-based remediation accidentally touch?

Ask Codex to produce a **supported-action matrix**, not a guessed universal policy: service/resource, create API, tag-on-create field, request condition keys, separate tag/untag APIs, IaC integration coverage, Config recording support, service-created resource path, and an authorized negative test. Require current official sources for each non-hypothetical row. Have it challenge the design with a wrong-case key, absent tag, service-linked role and resource created outside Terraform. Compare your decisions with the [assessor](ASSESSOR.md).

For a live organization, start in one test account/OU, observe create, update and untag results, then inspect actual resource tags and billing allocation separately. AWS recommends testing before attaching restrictive SCPs broadly. This exercise is paper-only; it uses no credits or AWS resources. A later separately authorized trial in a suitable environment needs a whole-run estimate, account-appropriate spending and reserve limits, an owner, cleanup and current price and plan checks. Tag presence is not proof of correct cost allocation, and this design lesson is not live policy evidence.
