# Assessor notes: ownership handoff

These are reasoning checks for the fictional packet, not proof that a live Amplify-generated table can be safely transferred. Credit an answer that names an explicit stopping point and tests the business promise, even if it selects a different bounded design.

1. **Use without owning.** Keep CloudFormation as the lifecycle owner if the requirement is access. Grant only the required data actions to the new service and test the authorized read. A Terraform-managed consumer may reference the table, but must not also declare it as a managed table merely to obtain an ID. Revisit only if a stated operating requirement outweighs the handoff risk.
2. **Early import.** A Terraform import plan maps an existing object into state; it does not tell CloudFormation to release it. Both tools can later propose updates or deletion. Stop. Inspect stack membership and durable backend definitions, then choose a sequenced release or another architecture. A no-op after import cannot prove single ownership.
3. **Deletion warning.** Stop before execution. A Terraform state copy contains management metadata, not table rows. Confirm the physical ID, effective resource policy, data recovery copy, change-set action and dependencies. A `Retain` policy must be in effect when CloudFormation removes the resource from its scope. If a supported backend update cannot arrange that, reject the in-place route.
4. **Wrong destination.** Match account ID, Region, table ARN/name or provider-specific import ID, old stack physical ID, target Terraform provider alias, state key/workspace and intended environment. A no-op can be consistent with managing the wrong existing table or state history. Compare with independent AWS resource observations before writing.
5. **Customer path.** Check generated endpoints/configuration, API schema, authorization, resolver or handler links, IAM, table identity and a known before/after order through the actual app. Preserve event and data evidence. Do not run both owners in a hurried rollback, and do not re-create a same-named empty table over data. Decide whether to restore old definitions, repair client integration or move traffic only after inspecting each proposed action.
6. **New target.** This is a migration, not an import. Establish a consistent source snapshot or replay/dual-write strategy, reconcile item counts and representative records, define conflict and late-write rules, check read/write permissions, cut over clients at a recorded point and retain a tested return path. Keep old CloudFormation ownership through the agreed cutover stage. Budget for two tables, migration work and old-resource retention; use account-specific pricing before a real run.

The key separation: retention preserves an object, import records a Terraform binding, and customer acceptance demonstrates useful behavior. None implies the other two. The official references are the [CloudFormation DeletionPolicy](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html) and [Terraform import guide](https://developer.hashicorp.com/terraform/language/import/single-resource). Resource-type and Amplify-generated workflow support must be checked at the time of a real handoff.
