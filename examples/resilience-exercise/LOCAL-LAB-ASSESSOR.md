# Assessor reasoning for the A22 loopback experiment

This is author guidance, not an independent learner score or AWS observation. Accept answers that identify both the customer-visible uncertainty and the actual business effect. Require a different observation for each claim: target selection, stop state, new request behavior, and accepted-request reconciliation.

1. If the first call did not commit, the same-ID retry creates the booking once. If it did commit, that retry returns the earlier receipt. The caller cannot choose between those histories from a timeout. Reusing the ID makes both histories converge on one logical booking inside this fixture; using a fresh ID risks duplication after the committed history.
2. No. Green new probes show that current traffic can succeed; a stale audit cannot establish what happened to earlier accepted work. Restore or independently reconcile the request-to-booking ledger before calling the business state recovered. This lab's `/audit` path shares the server process, so it is not an independent production observer.
3. Stop has removed the intentional delay, but two confirmed effects remain. Identify both rows and the correct customer/capacity state; follow an approved repair procedure and verify the resulting state. A healthy HTTP response and a stopped controller do not undo either record.
4. The exact-target gate must reject both the wrong worker and a selector that includes it along with the lab worker. Short duration limits one dimension of exposure; it does not make an unrelated team's target authorized or harmless.
5. The sequence remains a design hypothesis: commit may precede a lost reply, stable request identity can make retries safe, and stopping injection is not business recovery. The one-process lock, memory store and shared operator/observer path do not prove cross-process atomicity, IAM denial, real FIS targeting, CloudWatch alarm behavior, durable persistence or measured RTO/RPO. Before any selected live experiment, confirm non-root scoped authority, exact target, alarm/stop access, current Region/service eligibility and full estimated cost within the account owner's chosen limit and a suitable credit reserve. Then observe actual customer requests, effects, stop/repair and delayed billing. Organization-dependent variants remain design-only in this exercise.

The timing field is wall time for one local run from the first timeout to the second post-stop probe. It is intentionally not compared with the tabletop's fictional 120-second recovery target or generalized from the small sample. A changed run can legitimately produce a different elapsed number without changing the key correctness result.
