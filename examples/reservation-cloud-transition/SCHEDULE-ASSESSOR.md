# A03 schedule exercise: assessor reasoning

1. A quiet **Scheduler delivery** queue says only that no failed target delivery was observed in that queue. It does not establish that Lambda code ran, processed all 16 holds, saw every GSI entry or left no due hold. The first tick's `page_limit_reached=true` calls for another pass. The second tick reaching its visible end still needs later reconciliation because the GSI is eventually consistent.
2. A page-two code exception belongs to the **Lambda asynchronous on-failure** path after its configured attempts or age, assuming the opt-in resources were actually installed and the destination works. It is not a Scheduler delivery failure merely because Scheduler started the request. The first page may already have returned five seats. Rerun from the beginning; terminal records or conditional state checks prevent another increment for those five. Inspect the actual hold/course records if an outcome remains ambiguous. The source declares both failure destinations only when the schedule flag is true; no cloud event was observed.
3. Scheduler's end date stops new occurrences according to its schedule semantics. It does not delete the schedule or necessarily cancel an already accepted asynchronous Lambda event. The handler's separate lab expiry rejects work it begins after that time; work begun before can finish later. Failure records, queues, Lambda, log groups, IAM role, table and schedule still need exact removal and later billing review.
4. A one-minute recurrence plus asynchronous delivery, index lag, processing time and retries cannot establish exact availability at second 600. A strict promise requires a separately defined time authority, concurrency contract and measured service path, or honest customer wording that permits delay. DynamoDB TTL is not the seat-release authority. Do not replace a missing proof with a more confident diagram.

The direct route is a bounded source candidate for the *tiny synthetic lab*. A queue-mediated route could become preferable if buffering and backpressure matter, but it needs its own consumer behavior, polling/redrive cost and failure tests. Before enabling the direct route, the operator must complete the scheduled worksheet, inspect the exact plan and account, confirm a scoped identity and current credits, attend the four console alarms and due-age check, then verify cleanup and live behavior. The alarms have no notification action. Local Moto tests and Terraform validation prove only authored release behavior and source structure, not effective AWS orchestration.

The [local diagnostic](schedule_diagnostic.py) is a small counterexample to queue-only incident reasoning. Its `quiet_queues_unknown_work` case has no failure record but no completed Lambda result; `fifteen_entry_cap` has a successful result but known remaining work; `index_looked_empty` has a completed pass but a due base record. All three defeat the shortcut's “all clear.” The `both_failure_records` case may represent separate attempts or inconsistent evidence; it demands two investigations and correlation by occurrence/request ID before attributing a single cause. The synthetic `observed_clear_pass` supports only a clear observation at that time. The drill has no actual Scheduler, Lambda, queue, index propagation or independent learner attempt.
