# A03 cloud-transition assessor reasoning

These are answer criteria for a fictional design. No learner, provider or AWS transaction has been assessed or executed.

The new ten-minute promise favors an explicit hold state over A03's immediate-confirmation contract, provided Maya accepts a late-capture reconciliation process. Immediate confirmation might be preferable if the business guarantees a seat before payment and deliberately manages unpaid reservations. Neither option is universally better.

The authority map must derive the customer from authentication, keep provider events authenticated and separate internal hold ID from payment/event IDs. A repeated acquisition under the same stable request identity must recover its earlier result rather than consume another seat. A new purchase requires a new identity and a stated policy for one active hold per customer/course.

Acquisition must condition capacity and create the hold together. Confirmation changes a still-eligible `HELD` row without decrementing again. Expiration or cancellation changes only `HELD` to a terminal state and returns capacity in the same transaction. A second worker's state condition then fails; it must inspect the committed state before calling the attempt successful or retrying a new operation. A provider event record and compensation obligation need stable identities so duplicate delivery does not create duplicate obligations. An actual refund is an external effect that the database transaction cannot complete or roll back.

For the changed cases:

1. At the chosen equality boundary, Bob can obtain the freed seat once the expiry transition commits. Alice cannot take Bob's seat. A valid late capture creates a pending compensation/customer-resolution obligation; “refund pending” is not “refunded.”
2. Only one conditional `HELD` transition may release capacity. After an ambiguous timeout, inspect the hold and course state with the required consistency; do not blindly add one again. A transaction error is not synonymous with `SOLD_OUT`.
3. If cancellation commits first, it releases once and later confirmation must fail. If confirmation commits first, this exercise's held-only cancellation returns the confirmed state and leaves capacity occupied. A confirmed-booking cancellation is a separate policy.
4. The repeated capture ID and matching payload should recover one recorded result. A distinct successful capture is another external effect and may require a second compensation obligation, even though it never creates another seat. A reused ID with changed payment/amount/hold is a conflict for investigation.
5. TTL is asynchronous housekeeping. An expired item may still be readable and billable before deletion; the business transition must enforce eligibility and release. If history is deleted, a later duplicate may lose its stable prior outcome. Retain a separately reviewed deduplication/audit record for the necessary window.
6. A condition using sampled `now=9.999` proves eligibility relative to **that value**, not that the remote commit occurred before second 10. Define the product's accepted boundary and clock/latency uncertainty. A margin that stops accepting confirmations early is one possible conservative policy; it changes the effective customer deadline and must be disclosed. Do not claim strict cutoff until the chosen time authority and concurrency behavior have been implemented and measured.
7. A pending local obligation cannot reveal whether the provider acted. Verify the provider's idempotency-key scope, retention, payload matching, lookup and uncertain-result process. Keep the case unresolved when those facts are absent; do not send a new random refund ID.
8. Zero matches on the first page does not finish the scan; follow its `next_cursor` until a page has none. If another worker releases the later hold first, the conditional path returns the already-changed state and must not increment capacity again. A scan is not a snapshot of concurrent writes, so a later pass from the beginning may be needed. Filters apply after reads; estimate the examined items and strong-read cost, not only returned holds. An unresolved transition should stop the page and withhold a success cursor.
9. The GSI is a discovery aid, not current state. Its eventually consistent query can omit recent additions or return removed entries. The worker strongly reads each returned base item and conditionally changes only `HELD` to `EXPIRED` while returning capacity once; the same index page must not be interpreted as proof that no other due hold exists. Follow cursors and repeat later, with the table scan retained for records created before the index attribute was introduced. Estimate index query/storage/update charges in addition to base reads and transactions. A single `HELD` partition is a bounded lab choice, not a proven high-volume key design.
10. The first tick can release 15 holds and stop with more visible work; the next can release the sixteenth. If page two fails, page one's releases remain committed and the call raises rather than presenting an all-clear result. Repeating the tick starts at the beginning; already changed holds either disappear from the sparse index or are rejected by the base-state condition, so capacity is returned only for remaining `HELD` rows. A false `page_limit_reached` means no more entries were visible to this pass, not that index propagation or pre-index reconciliation is finished. A future recurring schedule would need its own end time, role, delivery retry/dead-letter handling, Lambda execution-failure destination or equivalent observation, and a whole-run estimate for every request, function, index/base operation, log, failure path and cleanup. Scheduler delivery success does not prove Lambda code success. The lab's two-hour stop does not release a hold or destroy infrastructure. Neither periodic polling nor a sampled database condition proves exact release at the ten-minute deadline.

A strong proposal names the conditional transaction per transition, a durable retry identity, the read needed after an ambiguous outcome, and a customer-visible state that does not overstate external completion. It distinguishes DynamoDB's atomic write from a provider effect. `TransactWriteItems` cannot target the same item twice within one request, and strongly consistent reads are needed when the latest committed state matters immediately after a transaction. The actual design must also define indexes/discovery, retained-history windows, permissions, alarms, provider contracts and current cost.

The existing SQLite lab checks authored transitions, separate-connection races and a local process restart. Moto now checks A03's **immediate** transaction and the separate hold source's acquire/confirm/cancel/explicit-expire and bounded table-scan and indexed-query paths, including empty filtered pages, one-time release, another worker's release, a 16-hold two-tick backlog, a second-page failure/retry and emulated lost replies. The Terraform source declares a sparse GSI; no index or schedule was created in AWS. These checks do not prove AWS index propagation or provide automatic scheduling, high-volume partitioning or payment integration. Live concurrent AWS writes, identity denial, deadlines, recovery, provider reconciliation, independent learner transfer and the book's final visual gate remain open.
