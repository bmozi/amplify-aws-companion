# Notification-route assessor reasoning

These are authored design criteria, not independent learner attempts or live service results. The [exercise](ROUTE-CHOICE.md) uses fictional customers and no provider credentials.

1. A direct push is a candidate when the app already has a current, authorized recipient/device route and consent decision. The direct send API is a request boundary; it does not supply Pinpoint's retiring stored endpoint registry, segment or campaign. A Connect-backed Amplify resource is a different, larger candidate if registration and profile capability justify it. Neither route's request acknowledgment proves device display or reading. Verify provider feedback and define the customer metric separately.
2. The new Amplify `defineNotifications()` path is not just a client helper. Without `domainName`, the documented setup creates an Amazon Connect instance and Customer Profiles domain, plus the generated app API and push application/channel configuration. The backend requires Auth for signed requests; APNs/FCM key material belongs in secrets, not source. A campaign's audience, schedule, consent, template and measurements remain separate design and cost questions. Price the selected Connect/profile, push, campaign and generated/supporting components, verify Region/account eligibility and plan cleanup before considering a cloud experiment.
3. A signed-in Auth/Data page is the closest match to an offer available only inside this website. It needs exact order-level authorization, another-customer denial, retention, withdrawal and actual page-observation checks. It is a custom application feature, not an Amplify or Connect replacement for Pinpoint in-app campaigns. Direct push and Connect-backed device registration solve different outside-app notification jobs.
4. Updated clients can create/update profiles and register devices as active users return, according to the migration guide. That does not prove inactive users' audience attributes or tokens have moved. A historical Pinpoint dashboard cannot serve as a current Customer Profiles or delivery receipt. Pinpoint-backed analytics event recording has a separate migration path to Kinesis Data Streams or Data Firehose; switching registration does not move those events. Record old versus new population, missing users, data policy and new event evidence before claiming completion.

No case establishes current prices, Free-plan eligibility, delivery, app display, consent freshness, IAM, Connect resources or account credit use. A source-backed capability is a candidate; a deployed and observed result needs separate evidence.
