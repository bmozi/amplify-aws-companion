# Choose the notification route that matches the promise

Maya's bakery says, “Tell customers when an order is ready.” That sentence leaves three different products on the table. A one-off push reaches outside the app. A campaign selects an audience and schedule. A private offer page waits for the customer to sign in. The tools, proof and continuing costs differ.

This is a source-linked **design exercise**, not an invitation to deploy messaging. First read the [three-route diagram](../../book/figures/notification-three-routes.svg) and write a decision for each case. Name the required recipient identity and consent check, AWS and outside-provider components, proof of the customer's outcome, cost drivers, owner and cleanup. Then compare with the [assessor reasoning](ROUTE-CHOICE-ASSESSOR.md).

1. **One cake-ready notice.** The bakery already owns an authorized customer/device registry and wants to send one transactional push to a consented device. It does not need audience segments. A teammate proposes the retired Pinpoint campaign console because it once stored endpoint IDs. Compare a direct AWS End User Messaging Push send with a new Amplify registration backend. Which existing facts would make either path eligible, and what can a successful send response prove?
2. **A mobile campaign.** The bakery wants to register devices as customers sign in and later select a consenting audience for a scheduled promotion. The team has no Connect instance or Customer Profiles domain. An engineer says `defineNotifications()` will only add a small client helper. Explain what Amplify's current setup guide says the default backend creates, what separate campaign decision remains, where APNs/FCM credentials belong and which account/Region/cost/cleanup facts must be reviewed first.
3. **A private page offer.** An offer should appear only on Maya's signed-in order page; no push or app installation is required. A Pinpoint-era tutorial calls this “in-app messaging.” Decide whether a custom Auth/Data page, direct push or Connect-backed notification fits. Specify the other-customer denial and withdrawal checks. State whether this is an automatic replacement for Pinpoint in-app campaigns.
4. **A partial migration.** An older app used Pinpoint `identifyUser`, stored endpoints and Pinpoint analytics. Its new client now uses Customer Profiles for identification and device registration, but many inactive customers have not reopened the app. A dashboard still counts the old Pinpoint audience, and someone wants to call the migration complete. Name what can repopulate as users return, what remains unproved for inactive users, and how event recording differs from push registration. Decide which old evidence cannot be carried into the new result.

The current [Amplify setup guide](https://docs.amplify.aws/react/build-a-backend/add-aws-services/notifications/set-up-notifications/) says `defineNotifications` uses Cognito identity-pool credentials and a generated registration API backed by Amazon Connect Customer Profiles. With no existing-domain `domainName`, it creates a Connect instance and Customer Profiles domain. APNs/FCM credentials are secrets; the guide then describes an AWS End User Messaging application for push channels. Its [migration guide](https://docs.amplify.aws/react/build-a-backend/add-aws-services/pinpoint-migration/) separates that client/backend change from analytics event streaming and says profiles repopulate as users sign in and open the updated app. AWS's [Pinpoint end-of-support guide](https://docs.aws.amazon.com/pinpoint/latest/userguide/migrate.html) says direct push APIs continue but stored endpoints, engagement features and in-app messaging do not.

No route is cost-free merely because a client API exists. Check current [Amazon Connect Customer pricing](https://aws.amazon.com/products/connect/customer/pricing/), [End User Messaging pricing](https://aws.amazon.com/end-user-messaging/pricing/) and all generated/supporting resources for the chosen Region and account. Do not assume a displayed free allowance covers your account or custom profile data. Keep this packet on paper until scoped identity, service eligibility, current credits, a complete estimate against chosen spending and reserve limits, a one-active-lab decision, stop conditions and cleanup are established.

Ask Codex to challenge your first answer with one changed fact: the customer withdraws consent, the device token is stale, a provider rejects the push, or the requested “offer” must appear in the website without a mobile app. Require it to distinguish source-backed product capability from a deployed result and a recipient-observed outcome.
