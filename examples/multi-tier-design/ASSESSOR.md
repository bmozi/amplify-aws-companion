# Multi-tier design reference reasoning

Use this after drawing the four cases in the [exercise](README.md). A tier is a responsibility or access boundary, not a requirement to buy another server. These are design examples, not deployed AWS architectures.

| Case | Defensible first answer | Fact that could reverse it |
| --- | --- | --- |
| Small internal tool | Keep a simple form and the smallest already-supported backend that meets its actual audience, data and recovery needs. Do not add a CDN, load balancer, private subnet and separate database merely to draw three tiers. | Public access, a stronger recovery promise, sensitive records, more users or independently growing workloads could justify a new boundary. |
| Public repair API | Give the browser a public web/API entry. Have application code establish the signed-in customer's identity and check ownership of the specific repair. Put a relational database behind a private network path only if that database and compute choice need one. Store photos in S3 as managed object storage, with an authorized upload/download route and object policy. | A direct-to-S3 upload can remove application bandwidth, but only after the application grants a narrow, short-lived upload authority and later verifies the object belongs to the accepted repair. A stricter private-network requirement changes route and endpoint design, not S3's location. |
| Long-running image work | Record an accepted job with a stable ID, then send retryable work to SQS. A worker processes it, records result status and stores an output only once under the chosen idempotency rule. The first response says *accepted*, not *completed*. Show the error and retry path. | If processing becomes quick and bounded enough to meet the response promise, the queue may be unnecessary. If a worker needs a private database, its VPC connection and route to SQS/S3 need separate review. |
| Private report | Add a reporting path only after measuring source load, query duration, freshness need and who may read private fields. Keep source ownership and result-copy access explicit. | A smaller indexed query may meet the deadline without another tier; a strict freshness or privacy requirement may demand a different copy, permission and recovery design. |

For the public API, test two different questions. A network rule asks whether the application can reach the database at all. The business rule asks whether Alice may read repair 42. A successful network connection cannot answer the second question. A browser's inability to connect directly to the database also does not prove that an API enforces repair ownership.

For the async case, draw the queue and object store **outside** the application subnet. SQS [interface VPC endpoints](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-internetwork-traffic-privacy.html) and S3 [gateway endpoints](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-s3.html) are ways for VPC resources to reach those services; they do not relocate them into the VPC. If a Lambda function must reach a private VPC resource, [attach it to the selected VPC subnets](https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc.html) and review its other outbound routes. Choose only the routes the design needs, then estimate any NAT, interface endpoint, transfer, request, storage and logging meters that apply. An endpoint policy or security group also does not replace tenant authorization in application code.

The table's shorthand “record ... then send” needs an explicit recovery mechanism: if the first write commits and the second fails, the accepted job can remain stranded. One candidate is an **outbox**: write the job and a pending-send record in the same supported database transaction. A separate sender reads committed pending records and delivers them to the queue; it retries and records progress. A lost send response can produce a duplicate, so the worker still needs a stable job identity and an idempotent effect. Monitor old pending records and reconcile them; a pending outbox row is not proof that a worker completed the image. [AWS's transactional outbox explanation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) describes the dual-write problem and duplicate-delivery concern. The exact transaction boundary, retry policy, service configuration and recovery behavior need implementation and testing for the chosen design.

For a changed-condition redraw, mark exactly which arrow, permission, capacity limit, retry rule and cost line changed. For example, if a worker is interrupted after writing the photo but before acknowledging the queue message, a redelivery must find the same job ID and decide whether the output already exists. If the internal tool becomes public, the change is larger than adding a public IP: name authentication, resource-level authorization, exposure, monitoring, recovery and cost boundaries.

This exercise remains on paper. Before a cloud run, select a scoped non-root identity, check service eligibility and regional prices, estimate the whole run against your spending limit and reserve, and name a stop condition and cleanup owner. This exercise provisions nothing and cannot prove AWS access behavior.
