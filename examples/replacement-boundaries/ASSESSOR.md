# Assessor notes: replacement boundaries

Internal criteria for original fictional cases. These notes do not establish learner outcomes or AWS implementation competence. Reward precise boundaries and defensible alternatives rather than a preferred service name.

1. One worker was changed outside the replacement recipe, while another retains the original behavior. Preserve the incident and actual diff, reproduce valid and invalid input behavior, correct reviewed source/build inputs, test a replacement, transition safely and verify serving identities. Do not erase the useful running repair merely to remove drift before a safe alternative is available. Tests must detect both the original rejection and newly permitted invalid behavior.
2. Image identity constrains image bytes, not every input or permission. Record non-secret configuration revision, effective identity/permissions, dependency destinations and relevant runtime observations. Compare the exact customer operation. A digest match cannot prove the discount or database authorization contract.
3. Creating new workers does not fix unconstrained dependency selection. Record resolved dependency identity and provenance, build and test a controlled artifact, and define a patch/update process. Dynamic installation needs its own reproducibility and startup-failure treatment. A lock or pin provides identity control, not an advisory disposition or a successful compatibility test.
4. The uploaded data is inside the retirement boundary. Establish durability, ownership, integrity and application references before moving it to an appropriate persistent boundary. Verify the customer can retrieve the complete authorized object after replacement. A backup or copy command without reconciliation is insufficient; no particular storage service is automatically correct without requirements.
5. Old code availability is different from compatibility with new data. Require an explicit reader/writer matrix and a tested recovery target. Accept staged schema evolution or a justified forward repair; do not accept silent deletion of newer customer records as rollback. Invoices or external charges already issued need separate reconciliation.

Transfer: require the hard deadline, failure consequence, repair confidence, available capacity and recovery conditions to be stated. An in-place procedure can be controlled, but its actual per-worker outcomes and durable-source reconciliation must be recorded. A replacement can reduce dependence on worker history, but must fit capacity and timing constraints and preserve data. Do not infer either path is safe from its label. An emergency exception needs an owner, expiry/review condition and a verifiable return to the intended process.

Reject claims that immutable workers imply immutable customer data, that infrastructure code always replaces resources, or that an unchanged image guarantees unchanged behavior. No live deployment was performed by this exercise.
