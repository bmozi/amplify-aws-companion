# Multi-account paths: share, notify, preserve evidence

This fictional paper packet follows the [three-path governance lesson](../../reader/BOOK-LOCATORS.md#book-5c453ea72e36ceb9) and [A07](../../curriculum/ARCHITECTURE-STUDIES.md#a07-organizational-foundation). It creates no Organization, share, event bus or trail. Answer before reading the [assessor reasoning](ASSESSOR.md). For each case, draw the owner and consumer account, selected Region, principal/action/resource path, expected allowed and denied behavior, failure signal, cost owner, stop decision and smallest observation that could disprove the design.

1. **The account split.** Harbor has one small personal experiment and a growing customer booking system. Compare (a) one account with scoped roles, (b) separate experiment and production accounts, and (c) production, network, operations and log accounts under an organization. State which business requirement justifies each added boundary and what new operating work it creates. This case does not create an Organization.
2. **The shared subnet.** In a hypothetical organization, the network account owns a supported subnet in Region A and shares it with the booking account through RAM. The booking team claims the share also permits it to edit the network account's route tables and that a green share status proves customer reachability. Identify the missing permissions, owner decisions, route/security/placement checks and an intended denial. Now move the booking account outside the share's OU: what must be rechecked before a migration?
3. **The lost page.** A booking deployment rule targets an operations-account EventBridge bus. The bus policy permits the sending account, but no alert reaches the operator. The receiver rule matches the event source but not the sending account; the target recently lost permission and no DLQ was configured. Trace the sender rule and role, bus permission, receiver match, target delivery and recipient. Propose a near-match that must not page and an observable delivery-failure path. Do not infer that the deployment or customer service recovered.
4. **The incomplete audit.** An organization trail reaches a log account, but its event selection includes management events and excludes the object-level S3 read the team wants to investigate. A dashboard nevertheless says “all accounts logged.” State exactly what the trail can and cannot support. Add the resource/Region selector, destination permission, encryption, retention, read authorization and cost questions that must be reviewed before changing configuration. Explain why an EventBridge page does not repair the missing historical record.
5. **The new Region.** Harbor expands booking into Region B. The RAM subnet share, event rule and audit delivery were checked only in A. Draft a region-by-region evidence table for all three paths. Identify which resources or features need separate eligibility and price checks, and which customer operation must be retested. A passing local [account-onboarding guard](../account-onboarding/README.md) and [synthetic audit join](../security-audit-evidence/README.md) may help reasoning but do not prove AWS behavior.
6. **The departing division.** The training division leaves the organization but still depends on a shared network path and historical logs. Propose a staged exit with consumer inventory, data/keys, resource share, alert routing, log-read authority, retained cost, recovery access and explicit owner signoff. Distinguish revoking future access from deleting retained evidence or moving existing resources. State the rollback or safe-stop point.

Ask Codex to draw the three paths separately, then remove one permission or change one account/Region. Require it to distinguish source documentation, fictional facts and untested assumptions. A useful answer does not confuse a notification with durable audit evidence or a resource share with account administration. Independent learner and live cloud review are pending.
