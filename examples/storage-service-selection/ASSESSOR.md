# Assessor notes: cost-effective storage service

The point is a defensible sequence of reasoning, not a single cheapest-service answer.

- **Photo library:** S3 general purpose is a good first candidate for independently addressed objects. Compare storage class, request and retrieval volume, data transfer, versioning, lifecycle, processing and recovery. If the application needs shared POSIX paths, coordinated in-place edits or file locking, validate whether its object API can satisfy those requirements before selecting S3.
- **Shared Linux workspace:** EFS is a candidate for a shared NFS file system. It does not automatically solve conflicting writes. Measure concurrency and throughput; select a compatible storage/lifecycle class and throughput mode; include networking, backup, permissions and recovery. If Windows/SMB or a particular file system behavior is required, assess the appropriate FSx family rather than forcing this Linux/NFS comparison.
- **Single-machine database disk:** EBS is a candidate for a durable block device attached to EC2. Capacity and performance are separate inputs, and the instance's own bandwidth ceiling matters. Include EC2, provisioned EBS capacity/performance, snapshots, recovery/initialization and resources that persist after stop or detach. A snapshot is not a tested application restore.
- **Changed cases:** the interface changed, so reopen service selection. POSIX locking, Windows SMB/ACL requirements and dozens of shared readers are not solved by attaching a lower-cost volume. The business may choose to redesign the application to use S3 objects, but that is an application change with indexing, consistency, authorization and migration work.
- **Cost method:** eliminate candidates that cannot satisfy the contract. For eligible designs, use current Regional pricing and the actual usage drivers. Compare monthly and recovery-event cost under the same workload horizon. Include retained copies, requests, transfer, performance, compute, snapshots, monitoring and labor. If prices alone cannot decide, perform a bounded representative benchmark and test restore; do not infer performance from a service name.

## Two-door case: what a defensible answer notices

No candidate wins from the supplied facts. **A** makes S3 the publication destination but requires an editor change and explicit approval/version handling. **B** gives the editor a separate file contract but needs a copy owner, approved-version identity, retry/reconciliation and a recovery plan for both stores. **C** may fit the NFS plus S3 API shape through S3 Files, but the two access paths, delayed export, API/file conflicts and whole cost must be tested. The bucket is the S3 Files system of record; that fact does not make every intermediate mounted edit approved customer content. A sound provisional choice names its rejected alternative and the missing workload observation that could reverse it.

1. A POSIX denial on the mount does not cancel `s3:GetObject`. Ben's API permission is the observed privacy failure; review IAM and bucket policies for his role and test a direct forbidden object read after the change. Do not broaden mount permissions to repair the wrong door. [AWS permission distinction](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-posix-permissions.html).
2. The bucket's API version takes precedence in the stated conflict. Maya's mounted edit is in lost and found, outside automatic bucket export. Preserve and compare it under an authorized reviewer; decide whether to publish it as a new approved object version or discard it, then verify the customer path. Lost-and-found retention is a cost and cleanup item. [AWS conflict behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html).
3. The NFS rename cannot prove one atomic S3 prefix switch. The bucket may show both prefixes during per-object copy/delete. A reviewed manifest or versioned catalog pointer is an application design candidate; test its reader and failure behavior before relying on it. [AWS rename behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html).
4. Count active file-system bytes and metadata, file reads/writes, synchronization work, S3 PUT/GET/list and versioned bytes, retention, transfer, and any lost-and-found data. For B also include the separate file system and transfer/reconciliation job; for A include application development and operations. File count, sizes, operations, active set, duration, Region and current price are missing. Existing bucket ownership does not make the bridge free. [AWS metering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-metering.html), [S3 prices](https://aws.amazon.com/s3/pricing/).
5. SMB with Active Directory and NTFS ACLs is a different interface and identity contract. Amazon FSx for Windows File Server is a candidate to evaluate; verify the actual client, directory, ACL migration, network and supported availability/backup behavior, then compare storage, throughput, backup and transfer pricing. This does not establish that the business should provision it. [AWS Windows share access](https://docs.aws.amazon.com/fsx/latest/WindowsGuide/using-file-shares.html), [Windows ACLs](https://docs.aws.amazon.com/fsx/latest/WindowsGuide/limit-access-file-folder.html), [pricing](https://aws.amazon.com/fsx/windows/pricing/).
