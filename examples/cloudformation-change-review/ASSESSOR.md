# Assessor: a proposed change is only one layer of evidence

Read after making your own prediction. The local output is a narrow exercise, not a statement about an installed AWS stack.

1. **Replacement and objects.** Hold the customer cutover. Count and identify old objects, confirm the new destination and its access path, define copy/reconciliation or another migration method, test representative and denied reads, and account for both retained and new storage. The template's `Retain` flags do not move bytes. The separate bucket policy needs its own retention decision: without `DeletionPolicy: Retain`, AWS says it is removed when the stack is deleted, even if the bucket remains. Changing the policy's bucket target requires replacement; the study now intends to retain the old policy too. Confirm effective access on both physical buckets and account settings, then assign cleanup ownership and cost. A real change set and stack event record would narrow infrastructure uncertainty, while an application read would narrow customer uncertainty.
2. **Tag and drift.** The local script saw only two files in memory. Inspect the actual stack and resource state, the console edit, and an appropriate drift or drift-aware change-set result before treating the tag update as the only live difference. Decide whether the emergency edit belongs in desired configuration; do not erase it mechanically.
3. **Public access.** Hold. A TLS-only deny stops insecure transport; it does not by itself decide who may read over TLS. Public-access block settings and the rest of the bucket/account policy still matter. “No interruption” describes CloudFormation's property update behavior, not the security consequence.
4. **No replacement, failed customer read.** Trace the caller identity, bucket/object policy, encryption/key access, network path, changed application configuration and the exact failing request. The infrastructure controller's replacement classification cannot certify an end-to-end read. Record the first failed boundary before changing permissions.
5. **Unchanged bucket, changed policy.** Hold the transport claim. The bucket-only property diff is empty, but the separate `TransportPolicy` resource has lost its HTTP deny. Inspect the full template and a real change set, verify effective policy and Block Public Access at the target scope, and test a denied HTTP request as well as the intended HTTPS read. The local model reports the separate-resource edit; it does not execute those requests or establish effective permissions.
6. **Retained storage and cleanup.** The worksheet's old bucket has 30 GiB and the new one 18 GiB. At its explicitly fictional USD 0.03/GiB-month for 14/30 of a month, old storage is USD 0.42 and combined storage is USD 0.672. This counts only the stated storage quantities. It does not price copy requests, transfer, application use, logging, future versions or the time after the assumed window. Inventory and reconcile old and copied objects, verify representative customer reads and the old policy, name the cleanup authority, then verify deletion and later billing. Do not delete merely because the new bucket exists; do not call the subtotal a live AWS estimate.

**Good transfer answer:** name what the template comparison proves, the official property behavior it uses, the live evidence still absent, the customer promise, the old and new resource owners, and the full cost/cleanup path. A learner who only says “CloudFormation says safe” has not completed this exercise.

**Second-checker answer:** `security_gate.py` holds `public` because `BlockPublicPolicy` is false, and holds `transport` because the non-TLS deny is gone. It passes `name`, which the change-impact review holds for replacement and data-migration reasons. This is the lesson's deliberate disagreement: no single green local check proves a safe update. A real validator, applicable security rules, actual change set, effective permission tests and customer read answer different questions.
