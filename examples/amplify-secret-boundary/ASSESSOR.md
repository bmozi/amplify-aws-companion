# Assessor notes for the browser and secret boundary

Use only after the learner's first prediction. These are authored criteria, not a learner result or a live security review.

The unsafe build serves the fictional `VITE_` key in JavaScript and the second fictional key in `/partner.json`. The safe build serves only the intended public destination from its JavaScript; the server-only marker is absent from the inspected static files. The lab's assertions and loopback GETs test these exact fixtures. They do not establish that a real secret is managed by Amplify or that every output path was scanned.

In changed case 1, this repository's GitHub job builds its own static ZIP. An Amplify Hosting console variable is not automatically an input to that separate GitHub process. The operator would need an intentional GitHub input and a fresh source/configuration and cost review; putting a secret in a browser-bound input would still be wrong. In case 2, `secret()` is a supported Gen 2 backend reference, but a real review must check the intended environment's secret definition, function configuration/runtime, IAM and caller authorization, response, logs and rotation. The local Vite exercise tests none of those. In case 3, removing the prefix does not remove the copied public file. In case 4, treat the provider key as exposed: revoke or rotate it with the supplier, inspect any retained/served old artifact and usage, then verify the new path and absence of unexpected effects. Do not claim a clean rebuild retroactively made the old key private.

Look for a reader who distinguishes an **address** in `amplify_outputs.json` from permission to use the backend; a build-environment setting from a backend runtime secret; source exclusion from served-artifact inspection; and local observed bytes from AWS account evidence. Ask one unfamiliar variant, such as a secret in a source map or a server-rendered deployment artifact. A correct response names the artifact and access path to inspect rather than saying all server-side code is automatically private. Record assistance and remaining uncertainty in the learning record. Do not score this small packet as certification readiness.

The optional `server_lab.py` continues the path through a local HTTP handler. The normal authorized response says the fictional item is available but omits the invented supplier key; another caller and a missing caller both get 403, and the local event list contains no key. Its unsafe debug mode proves that a server can still disclose a key in an otherwise authorized response. In changed case 5, the recipient can read the response, so the server's location does not excuse the field. In case 6, a log reader and any export/retention path become relevant; the current fixture deliberately has no such leak, so answer from a proposed failure and name the actual deployed logs and access controls that would need inspection. The fixed bearer string is not real identity, the simulated supplier step is not an external integration, and neither result proves AWS function/secret/IAM behavior.
