# Assessor: two independent roads

1. **AAAA before a usable IPv6 route:** IPv4 remains a candidate if its A record and full IPv4 path still work. IPv6 is blocked at the missing route. An AAAA answer alone says where to try, not that the application responds. Test from a genuinely IPv6-only client; a dual-stack client may fall back and hide the failure.
2. **Unhealthy IPv4 target:** The load balancer's client-facing families are separate from its IPv4 target leg. Both customer paths depend on that target group here, so both fail when its targets cannot serve. A target health indicator is one diagnostic, not a substitute for an end-to-end response.
3. **Rollback:** Removing AAAA leaves the old IPv4 path available if it was kept healthy. It does not help IPv6-only customers. DNS caches can continue returning the old answer until they expire; plan a measured rollback and keep the IPv6 path safe while those answers exist. Record actual observations and timing before promising recovery.
4. **IPv4-only supplier:** An egress-only internet gateway handles outbound IPv6, not IPv6-to-IPv4 translation. A dual-stack worker can use its IPv4 path if that route and policy work. An IPv6-only worker may need DNS64 to synthesize a destination and NAT64 through a correctly routed NAT gateway; then verify supplier, permission, return path, and current NAT/data-transfer charges. If the supplier loses its A record and has no AAAA record, that DNS64 plan cannot synthesize a destination from an absent IPv4 answer.

Accept a different architecture only when the learner identifies every direction, address family, route, rule, failure observation, rollback effect, and cost meter. The local `path_lab.py` intentionally has a simplified Boolean gate for each condition; it cannot infer AWS route selection, NACL behavior, DNS caching, target registration or live packet delivery. A reader who says “the script passed, therefore IPv6 is deployed” has missed the evidence boundary.
