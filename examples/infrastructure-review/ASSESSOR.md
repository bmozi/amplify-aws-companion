# Infrastructure review: expected reasoning

Use these notes after the learner's first answer. They provide editorial criteria, not an independent technical certification or learner result.

1. **Rename:** the plan contradicts the stated preservation requirement. Hold the apply while identifying the object/address relationship and missing backup evidence. A supported address migration can preserve the tool's association with an existing object; the complete resulting plan and application requirements still need review. A small source diff is not a small-impact guarantee.
2. **Mapped replacement:** the mapping and attribute change are separate. Retain the original attribute for a pure refactor if that matches the approved intent, or review the intentional replacement as its own change with data, endpoint, permissions, downtime and recovery evidence. Reject an answer that treats the presence of a moved block as a veto on every replacement.
3. **Different upgrade positions:** account for both environments' current revisions and state addresses. Keep the required migration history available to environments that still need it. A successful test upgrade does not imply production has already moved. No second management owner should be introduced merely to avoid describing the migration.
4. **Uncertain writer:** a working homepage says nothing about whether the infrastructure writer remains active. Inspect the original job/process using its actual handle and recorded run identity. Avoid starting a competing writer or force-unlocking an active one. After termination, inspect partial resource changes, state and errors before planning again. A timeout observing the job is not proof of termination.
5. **Old state:** verify the selected backend/workspace and access before declaring loss. Preserve private recovery evidence. The stale copy does not recreate the deleted database or remove the replacement. Reconcile actual objects, addresses and intended ownership through supported procedures, then review the plan. Customer data has a separate restore and validation path. Reject blindly pushing an old state copy and applying old code.
6. **Failed isolation:** no-op infrastructure and HTTP availability passed their narrow checks; customer privacy failed. Recovery is incomplete. Assess the exposed path and contain it without broadening permissions, preserve necessary incident evidence, correct the enforcing authorization boundary, and repeat intended access plus cross-customer denial through the API as well as the UI. A hidden button is insufficient.

7. **Wrong history accepted:** an empty destination has no existing state lineage against which to reject the supplied history. Matching test configuration and test state can legitimately yield a no-op while answering the wrong operational question. A folder name supplies no account or resource identity. Identify the intended backend/workspace, account, source and inputs; reconcile actual resource identities and ownership with protected run records. The negative control proves this local acceptance failure mode, not the correctness of any cloud recovery.

For the final handoff, require a named decision owner, environment and source revision; the consequential actions; actual observations versus assumptions; a stop condition; recovery limits after new writes; and cost/retention responsibility. Do not average a data-loss or forbidden-access failure into an acceptable score. Missing evidence should produce a specific next observation, not invented certainty.

A transfer answer may choose different supported recovery mechanisms, but must explain why they match the observed state. The local Terraform drill proves a built-in resource's lifecycle and address move, local state rejection safeguards and snapshot restoration; its wrong-history control shows that acceptance and no-op can describe the wrong environment. It supplies no remote-backend lock test, AWS resource recovery, access-denial test or production migration rehearsal.
