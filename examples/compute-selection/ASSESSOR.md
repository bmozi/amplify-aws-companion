# Compute selection assessor notes

These are internal provisional criteria, not recorded learner performance. Accept alternative designs with evidence satisfying the stated requirements.

1. A bounded event function is plausible, not proven. Require representative and upper-bound legitimate inputs, runtime/library compatibility, whole-request latency, initialization, retry/duplicate behavior, permissions and downstream limits. An average can hide a failing tail. A successful laptop run is not a Lambda measurement.
2. Under the stated equal-duration model, eight workers need 125 waves × 30 seconds = 3,750 seconds, or 62.5 minutes. Ten need 100 waves = 3,000 seconds, or 50 minutes. At 1,200 attempts, ten need 120 waves = 3,600 seconds, consuming the entire hour. These omit startup, scheduling, uneven jobs, delays between retries and constrained dependencies. More workers are not automatically permitted or useful. Require an explicit bounded measurement plan before live sizing.
3. Twenty-five minutes exceeds the documented standard 900-second invocation limit. Name the exact service mode rather than generalizing this limit to all Lambda capabilities. Compare supported alternative execution modes and container/VM options using the full contract. Splitting work requires safe persisted progress and effects; restarting a partial external operation can duplicate it. A container image changes packaging, not the selected execution service's timeout contract.
4. Fargate's infrastructure maintenance does not update the application's container image and libraries or design its IAM/network policy. Customer-managed EC2 adds host/agent maintenance and replacement responsibilities. Require named ownership and a tested update/recovery process; more managed infrastructure does not mean no operating work.
5. Require the actual host feature, compatibility/support requirements and executable evidence from a representative package. Consider whether the claimed need is an obsolete deployment convention or a real kernel/device/runtime dependency. Neither a vendor label nor an ideological preference is sufficient. Verify persistent-state placement and replacement behavior. Reopen the choice when dependencies, support, workload or team capability changes.
6. The completion ceiling remains eight/second after doubling workers. The backlog grows by (12 − 8) × 300 = 1,200 jobs. With verified capacity of 16/second and continued arrivals of 12/second, net drain is four/second, requiring 300 seconds. These constant-rate calculations omit retries, variable durations and changeover. Low CPU may reflect waiting; work can accumulate after the input queue. Require accepted-to-durable-completion accounting, latency/age and dependency evidence. Increasing database capacity is a tested hypothesis here, not a guaranteed outcome from resizing it.
7. Changeover adds (12 − 8) × 60 = 240 jobs, making 1,440. Net drain after changeover is 16 − 12 = four/second, so draining takes 360 seconds; total elapsed time is 420 seconds. The model assumes work is conserved. Losing an unsaved result or double-counting a retry violates that assumption. Require durable ownership/progress, safe retry identity, drain or recovery behavior and evidence that accepted work reaches one valid outcome. No numerical answer establishes a real autoscaling policy or safe scale-in.

8. Current backlog is 600 / 5 = 120 messages per instance; candidate target is 120 / 2 = 60 messages per instance, implying ten identical instances for the unchanged snapshot. At four seconds, the target becomes 30 and the snapshot count 20. These are planning ratios, not a guaranteed policy response or customer deadline. Require evidence about dependency capacity, duration tails, arrivals, warmup, available capacity and configured limits. Queue wait excludes later processing; visible backlog excludes work already being handled. Zero instances makes the ratio undefined; missing observations are not measured zero. Define and test a supported activation path or costed minimum fleet before relying on scale from zero.

A strong answer distinguishes documented constraints, authored arithmetic, measured behavior and unresolved assumptions. Do not award correctness merely for selecting a familiar AWS logo or the cheapest incomplete estimate. Live experiments remain separate from these design cases and must preserve the account's spending boundaries.
