# Assessor notes for the AI-route decision

The cases are an author key, not a calibrated exam or evidence of learner understanding. Accept another bounded design if it keeps authority, costs and customer acceptance explicit.

1. **Static answer first.** A published menu or approved data lookup meets the stated promise without inference. Daily change requires an authoritative hours record, publication/version observation and a stale-page check; it does not by itself require a model. A public AI route would introduce requests and potential abuse without solving freshness automatically.
2. **Authenticated is not order ownership.** Both Alice and Bob can satisfy a route-level signed-in rule. A server-side lookup must derive the caller from trusted identity, enforce access to `A17`, select allowed facts and refuse Bob. Test the actual API as Bob, not merely the UI button. Do not let a caller-supplied `orderId` or prompt authorize the retrieval. Current Amplify generation-route authorization choices do not provide an owner rule by themselves; verify the exact supported integration before implementation.
3. **History is a separate promise.** A conversation route fits multi-turn stored history better than repeated one-off generation calls. Amplify creates conversation/message records and documents owner-scoped conversation access. Check that Alice can resume and Bob cannot list or load her history; define retention and verify deletion of records and any retained logs or copies. Count additional AppSync, Lambda, DynamoDB, model and log use rather than pricing just the latest prompt.
4. **Words are not effects.** The sentence proves only model output. A refund requires an application-controlled gate with authenticated actor, exact order and amount, current approval, stable operation ID and observed provider result. A lost response may require lookup/reconciliation, not a new refund. The model can propose a tool call; it cannot grant itself authority.
5. **Idle infrastructure still counts.** Amplify's Knowledge Base example warns that its default OpenSearch Serverless store has a continuing cost. Price that store for creation through verified deletion, ingestion/indexing, storage, retrieval, model and logging before considering the whole run against the account owner's chosen estimated-run limit and credit reserve. A tiny authorized excerpt set or a design-only exercise may teach the intended boundary without that resource. Do not assume any retrieval system is free because prompt count is low.
6. **Logging changes the data path.** Bedrock model invocation logging is off by default. If enabled for the relevant endpoint and Region, supported request and response data can go to CloudWatch Logs or S3; any enabled image/document logging has its own handling. Review destination access, encryption, retention, usage and deletion. Use invented text for diagnosis and inspect request metadata or a narrower sanitized trace when sufficient. A debug log is not a license to copy customer data.
7. **Build and fluency are incomplete evidence.** Version the same evaluation set, compare supported facts, forbidden cross-user access, deadline fabrication and refusal/uncertainty behavior, then inspect actual application responses. Price input **and output** tokens, retries and supporting service usage for the selected model/Region. A lower input-token price alone may lose when output length, failures or customer impact changes.

Recheck them before a live build. These answers do not establish current model access, live permissions, delivery quality, price or cleanup.
