# Assessor reasoning for changed-promise impact

Read this after preserving the first worklist prediction and design. These explanations use fictional facts and do not provide complete architectures.

**One-shop restore.** A database-only answer misses photos, pending work and a technician scheduler's uncertain outside effect. Selective reconstruction may avoid duplicated per-shop stores but needs exact tenant selection, write ownership, version conflict handling and a tested merge. A selected dedicated boundary may simplify part of a restore, yet shared identity, workers, files or effects can still cross it; repeated resources add operating and retained-copy cost. Reject a candidate if Shop B's post-backup request disappears, Shop A's referenced photo is absent, an unrelated operator can read a restore copy, or a technician assignment is repeated. A successful local row restore is weaker than customer-visible recovery.

The new `customer_route` decision is a distinct check: after a clean candidate restore, send a Shop A request to the chosen candidate and a Shop B request to its current state. A correct database with the wrong route still fails the promise. The foundation map assigns that decision to the entry and delivery questions; it does not create or test an AWS router.

**Two school reviewers.** A clean scan still does not approve publication. The second human decision must be distinct, current and bound to the exact version. Compare a revised private intake state machine with a separate selected-publication record; either needs duplicate-event handling, rejection/revocation behavior, access checks on every read path and an attributable decision trail. Reject a design if one reviewer counts twice, an old approval releases new bytes, or a previously emailed direct link opens before quorum. A normal application route returning 403 does not establish denial through an object or cache path.

**Tenant burst.** A scheduling or fair-queue change can limit one tenant's share of workers, but cannot by itself add database capacity or prove an accepted-work deadline. A dedicated selected resource can reduce one shared bottleneck while increasing provisioning and cost, and it cannot fix a shared worker or forged tenant identity. Compare per-tenant accepted-to-complete time, backlog, retries, database waits and whole-path usage. Reject an aggregate green dashboard if one tenant misses its deadline.

**Five-minute transit alert.** Start the clock at the confirmed closure, with the route and authorized operator recorded. The 5:03 all-clear is older than the 5:04 closure; receiving it at 5:05 must not make riders think the route has reopened. A version or other authoritative ordering rule must protect both the public status and outbound notices. Acceptance of 4,000 text sends is channel evidence, not observed rider reach. The app update is evidence for that app path. Yesterday's display at the diverted stop is a failed current-information path if the promise includes that stop. The assessor should reject an answer that substitutes a provider receipt or aggregate send count for the stated rider result.

An opt-out during fanout exposes a race: the design must say which consent snapshot or send-time check governs each attempt, and what can be stopped after an already accepted send. An application-only design has fewer channel and contact-data paths, but cannot satisfy a promise to riders without the app. A multi-channel route adds contact selection, duplicate and contradictory notices, retry identities, retained preferences, accessibility checks, peak charges and operational reconciliation. A narrower, explicitly app-only promise for riders known to have app access could make the simpler candidate worth comparing; the business owner would need to approve that changed promise and test it. Neither alternative is established by this paper case.

The [local timeline](transit_timeline.py) sharpens the evidence boundary. At minute 5 the version-2 all-clear is stale because version 3 was confirmed at minute 4, so a proposed send is blocked. The old stop display at minute 7 is an **observed stale notice** and remains a failed path. Rider B's minute-6 send is blocked because the opt-out took effect at minute 5. Rider A's text is accepted but reach is unproved; the app observation at minute 7 is current and within five minutes of the latest fact. Moving that observation to minute 10 makes that one path late. None of these rows establishes reach for all affected riders, independent timestamps, live provider behavior or an AWS implementation. Reject a learner answer that combines the app observation and text acceptance into a made-up count of riders reached.

The new `change_rollout` decision asks who owns jobs accepted by old workers while the fairness rule changes. Do not treat a clean new queue configuration as proof that acknowledged older work reached completion. The foundation map places this under delivery; a local graph cannot verify an actual deployment handoff.

**Automation limit.** The graph walks links that people supplied. It can reveal a disconnected authored node but not an absent concept. If both `outside_effect` and its incoming link vanish, graph traversal alone passes; the separately authored seven-question mapping now rejects the missing known node. If someone also remaps “work” and “recovery” to surviving nodes, both checks pass while the scheduler effect is still absent. This is a deliberate demonstration of the remaining semantic limit, not a safe design. Ask the learner to add one plausible omitted dependency and one rejecting observation, then review whether that addition changes the alternatives or cost. A machine-complete worklist is ready for human review, not for deployment.
