# Assessor reasoning: integrated restore

Read after an independent first attempt. The local program accepts only the supplied clean combination: 10:10 database, `v1` object bytes, and no replay of sent dispatch D111. The independent confirmation supplies the expected amount and digest. It is fictional, and its presence is an assumption.

1. **Unavailable clean point:** The 10:00 database omits B111; the 10:11 database contains a wrong amount and photo reference. Neither is safe by itself. A separate verified business record could support a controlled repair to a separate candidate; without it the intended state is unknown. Do not overwrite the original based on a guess.
2. **Version choice:** A version-aware read of `v1` is needed. In a versioning-enabled S3 bucket a current delete marker does not, by itself, erase a retained earlier version. If versioning was never enabled or that version was permanently removed, the lab's assumed recovery source is absent. Find a separate valid backup or hold.
3. **Lost authority:** The ledger is the acceptance reference. Neither the database's own value nor a generated plausible value independently confirms the customer's promise. The decision stays on hold.
4. **External dispatch:** A database restore cannot undo or verify a third-party send. D111 is supplied as already sent, so replay is refused. If status is uncertain, use the external system's durable identifier or receipt and an explicit reconciliation procedure before any retry.
5. **Backup scope:** A scheduled database copy alone does not retain the referenced object. Assign the selected resources to suitable plans, confirm the service's supported protection and retention behavior, preserve access and decryption paths, restore separately, validate the joined business state, estimate ongoing versions/backups and clean up drill resources. AWS Backup plans automate assigned-resource protection; they do not make independently scheduled resources a single atomic recovery point.
6. **Regional strategy:** Backup-and-restore keeps less continuously running recovery capacity but has more restore work; pilot light keeps essential data/core services ready; warm standby keeps a scaled-down working stack; active/active serves from more than one location and makes write ownership and conflict control harder. Each needs identity, keys, configuration, object and database state, application capacity, routing, external-effect reconciliation and a measured acceptance path. The correct choice depends on business RTO/RPO, failure scope and full cost. The fictional timestamps and local test establish none of those live values.
7. **Guessed version:** The fixture checks the trusted actor before asking Moto for a version, so Shop B cannot use the exercise's route to read Shop A's bytes. That is a local application denial, not effective AWS authorization: the broad mock client could ask directly. In a real trial, verify that the recovery role can list only the needed versions and read only the intended customer/version, while unrelated customer and raw version-specific requests fail under the effective identity, bucket and key policies. Keep Block Public Access, encryption and TLS in the reviewed design. The old version and staged candidate add storage and request costs; neither a green backup job nor the route's local denial proves customer recovery.

The original decision-model tests cover a successful joined state and five negative-control categories. The added Moto tests exercise S3-shaped version API behavior but do not test live S3, RDS, AWS Backup, encryption, IAM, network access, Region loss, live recovery time, cloud cost or independent learner performance.
