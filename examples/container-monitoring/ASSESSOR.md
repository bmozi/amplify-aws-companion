# Assessor: container monitoring

The answer must separate container health from customer success. Four running tasks, low CPU and no restarts do not offset 86 database timeouts in 100 booking probes. The customer lane should page; the container lane helps diagnosis. Accept either ECS or EKS if the learner uses its actual collection path and does not transplant metric names blindly.

Look for a request/correlation ID joining the entry event, task or pod, deploy version and database call. The learner should avoid personal data in logs and should state what the probe covers. They should distinguish an absent metric or silent probe from a measured zero-error interval. A missing-signal alarm and an outside-path check are reasonable responses to the changed condition.

For the bounded fault test, expect a predicted observation in both lanes, a safe environment and stop condition, a real customer-path measurement, and a rollback criterion. A green task count with a failing booking path should fail the release gate. If all probes pass but real users still fail, probe coverage is an open question, not proof of production health.

No tabletop answer proves an actual CloudWatch configuration, telemetry delivery, response time or learner mastery.
