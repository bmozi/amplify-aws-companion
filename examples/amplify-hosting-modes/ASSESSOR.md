# Assessor reasoning: static and server-rendered routes

Use this after recording your first answer. These explanations are not a calibrated exam. The platform facts were checked against AWS [manual-deploy](https://docs.aws.amazon.com/amplify/latest/userguide/manual-deploys.html), [SSR deployment](https://docs.aws.amazon.com/amplify/latest/userguide/server-side-rendering-amplify.html), [deployment specification](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-deployment-specification.html), [cache-policy](https://docs.aws.amazon.com/amplify/latest/userguide/cache-configuration-type.html) and [pricing](https://aws.amazon.com/amplify/pricing/) pages on October 19, 2026; recheck before a real design.

1. **Private note:** Static delivery is compatible with private data fetched later. The browser's identity and Data authorization must be tested; use two controlled synthetic users, confirm each reads its own note and receives denial for the other's record. A public static shell is not evidence that data is public, nor does the label “private app” require SSR. The client-output destinations also need inspection.
2. **First response:** The new contract rules out a first response containing only a shell and later browser fetch. SSR is a candidate if a supported server route can authenticate the caller, fetch the authorized current status and render it into HTML within the latency/freshness promise. Server code needs its own effective authority; the browser's identity is not automatically inherited by an arbitrary server fetch. Inspect cache keys and response headers and test the first served HTML for two users plus an unauthenticated visitor. A pre-rendered public response would need another design to meet per-account freshness.
3. **Delivery:** This manual ZIP publisher builds and uploads static files; AWS does not support manual SSR deployment. Choose a currently supported Git/framework/adapter deployment path and verify its `static`, `compute` and route output as appropriate. Review the new release identity and permissions. Observe the selected commit's build/job, then fetch a route whose dynamic response changes under controlled inputs; separately test Auth/Data allowed and denied requests. A green upload or marker for static files cannot establish compute execution.
4. **Meters:** Outside allowances, static listed components are `5 × $0.15 + 0.01 × $0.023 = $0.75023`. SSR adds `100,000 / 1,000,000 × $0.30 + 6 × $0.20 = $1.23`, giving `$1.98023` for these selected Hosting components. At 40 GB served, transfer alone is `$6`, before storage, SSR, backend or other services. Neither calculation is a whole-run estimate: establish actual allowed credits/free usage, Region and dates, build costs on the chosen route, backend calls/storage, logs, optional image/WAF work, retries, retained data, cleanup and a margin. Compare the result with the limit chosen for the account; a subtotal below that limit still cannot authorize the run. GitHub Actions, if used, has separate billing.
5. **Shared shelf:** A deployment job proves only a stage of release. Cache-policy defaults are configuration, not an observed authorization outcome. In the fictional incident, stop serving the affected personalized route or disable its shared caching while preserving evidence, inspect the served HTML and cache headers/keys/route rules, then repair the ownership or cache boundary. Test at least two signed-in identities and an unauthenticated request with fresh and warmed cache states, including a denial. Do not infer that a logged-in browser automatically protects an HTML response already served from a shared cache.

The transfer has multiple valid answers. Credit an answer only if it names the first-response promise, which route holds identity and data authority, whether dynamic work is actually needed, a release mechanism that can deploy that route, positive/negative response observations and a full meter inventory. A lower request count or attractive SEO claim does not replace those checks. No case demonstrates a real account's effective controls, price, credit balance or learner transfer.

## Hosting owner cases

6. **Existing website:** A new `amplify/hosting.ts` file is source, not a migration or deployment receipt. In the hypothetical case, the Terraform-managed Amplify app and branch remain their own resources until an explicit reviewed change. `defineHosting()` with `ampx deploy` would synthesize a separate self-managed hosting stack with S3/CloudFront and any selected compute; inspect exact stack/resource ownership before choosing migration or coexistence. Coexistence can incur two delivery paths and bills. Nothing in the file alone changes the served site.
7. **Production request:** AWS labels self-managed hosting **preview**, says its APIs may change, and does not recommend it for production. A production recommendation cannot treat that as a supported settled path. Compare the customer's exact edge/WAF and compliance requirements with currently supported managed Hosting options or a separately owned CDK/CloudFront design; verify capability, operating burden and full cost before selecting either. The evidence here does not establish which alternative meets the real customer requirement.
8. **Second switch:** `AMPLIFY_PUBLISH_ENABLED=false` guards only the checked-in manual GitHub workflow. `definePipeline()` can create a separately triggered CodePipeline, and an external CI job can call `ampx deploy`; neither reads this variable unless its own implementation explicitly does so. Inventory every active route and its repository connection, trigger, role trust and active sessions. Stopping new triggers does not delete a serving distribution or backend. A false flag is not an account-wide off switch.
9. **Broad command:** The [preview getting-started guide](https://docs.amplify.aws/react/deploy-and-host/self-hosting/getting-started/) describes no-scope `ampx deploy` as deploying both backend and frontend stacks; `--frontend` is the frontend-only option for an already deployed backend. Before any authorized use, inspect the actual package/version, synthesized change and IAM scope. A successful command would still need served revision, sign-in, owner-allow and unrelated-user-denial observations. The private notes are not protected by a build exit code.
10. **Worksheet:** The USD 0.75023 figure describes selected managed Amplify Hosting storage/transfer assumptions, not a self-managed whole-run price. For a preview self-managed design, identify exact generated S3 and CloudFront resources, transfer/request/storage, optional SSR and image compute, logging/alarms, WAF, CI, certificates/domain, backend and retention/cleanup. A feature can add regional or global resources. Obtain current rates, eligibility, usage and credits for the selected account and Region; then price verification, contingency and cleanup against the account owner's chosen estimate limit and credit reserve. Without that and a scoped identity, keep the path design-only.

The transfer answer may keep a static guide and authorized browser API today, then change rendering only if the first-response promise truly requires it. Hosting ownership can remain managed or be evaluated separately; an SSR requirement does not itself require self-managed preview. Credit an answer that distinguishes rendering, delivery ownership, data authority, publication trigger, current preview status and whole-run cost. These paper cases are not a deployed comparison or a current account quote.
