# Assessor reasoning: cross-account Amplify

Credit an answer when it distinguishes the Hosting account, target backend account, generated browser destination and effective data authorization. These are author keys for fictional cases, not learner results or live AWS evidence.

1. **Green frontend:** A Hosting success proves only that its build and publication path completed. The backend deployer could not assume the target role, so the new backend behavior is unproved. Check the intended account/Region/branch, the target role trust and scoped permissions, pipeline failure and prior backend state before a controlled retry. After a successful deploy, prove an allowed order and an unrelated customer's denial at the backend, then inspect the served revision.
2. **Wrong outputs:** The browser can route Auth/Data/Storage calls to practice despite a production URL and correct source commit. Compare planned account, Region, branch and backend identifiers with the generated outputs and final built artifact before publishing. After publication, verify the served bytes and actual request destination, then test both an allowed request and an unrelated-user denial. Matching configuration is not an authorization test.
3. **Production preview:** Obscurity and a page password do not make the referenced backend disposable. Authorized preview testers may write production data, and a browser defect or exposed destination adds risk. Use synthetic fixtures in a distinct practice or preview backend and outputs, with a reviewed role, account-specific meters and explicit teardown. If a production read-only preview is required, its authorization and side effects need their own design and tests.
4. **Separate bills:** Hosting build, storage and transfer remain with the Hosting account; backend storage, requests, function and logs remain with the target account. Deleting a frontend branch does not establish deletion of backend stacks or retained data. Inventory and remove only the owned resources in both accounts; record post-deletion resource readback and later billing reconciliation. Quiet metrics and a zero-current-charge screen are incomplete because billing can lag.

The linked local destination lab should reject a browser configuration that disagrees with its separately supplied approved map, including a copied live endpoint inside an otherwise practice bundle. It cannot establish a deployed backend account or a served-browser destination. The outputs inspector and built-output audit have narrower local claims documented in their own reader instructions; a strong answer names those limits instead of treating a matching hash as a complete release receipt.

The [AWS cross-account example](https://docs.amplify.aws/react/deploy-and-host/amplify-hosting/cross-account-deployments/) separates backend `pipeline-deploy` from frontend `generate outputs` and Hosting build. The precise provider, trust policy and deployment mechanism must be rechecked for the real organization. This design exercise does not configure such trust; a real run needs separate authorization and cost controls.
