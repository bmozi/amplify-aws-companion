# Choose a target, then modernize a seam

Maya's repair shop is moving an inherited booking system. Customers expect bookings and payment references to survive. Staff edit shared drawings, and a nightly report summarizes completed work. Work through the [target-platform lesson](../../reader/BOOK-LOCATORS.md#book-9fc6a96254952815) before opening the [separate assessor](ASSESSOR.md). These are architecture decisions with fictional constraints, not deployed AWS tests.

## Try the report seam locally

From the repository root, run `python3 examples/modernization-targets/outbox_lab.py`, then `python3 -m unittest discover -s examples/modernization-targets -p 'test_*.py' -v`. Python's standard library is sufficient. The in-memory SQLite booking and outbox rows commit together. The local relay copies pending rows to a list that stands in for delivery. A synthetic crash after that copy but before acknowledgment causes the same event to arrive twice. A stable event ID lets the report projection count it once. Compare the `before_delivery` and `after_reconciliation` output before reading the code.

The first synthetic crash occurs **inside** the booking transaction, so neither booking nor outbox row survives. The second occurs **after** delivery but before the relay marks the row published, so replay is necessary. A `published` flag only means this local relay acknowledged its copy; it does not prove the report completed. One test also commits a booking and outbox row to a temporary SQLite file, exits that process before its first send, and starts a second process that finds and delivers the pending row. The tests also expose a changed duplicate payload, a mismatched event ID and a wrong report amount. Explain why a report-total match alone would be weaker than checking booking IDs and amounts.

To see that restart case rather than only a test result, run `python3 examples/modernization-targets/restart_demo.py`. Before the writer exits, the output shows one booking and a missing report. The second process finds one pending send, records an accepted local delivery and shows the matching report amount. Predict those values before running it. The temporary file is removed afterward; the list representing delivery is local memory, not a queue service.

Change the case: the second process opens a different, empty SQLite file. Can an empty result prove that the first process accepted no booking? The test `test_reopening_a_different_empty_file_cannot_recover_the_obligation` shows that the second file has no pending work while the original still contains the unreconciled booking. A real recovery plan needs to identify and protect the authoritative store; a clean empty replacement is not a recovery receipt.

The main model is sequential and in-memory; the restart test uses a temporary file and two sequential local processes. Neither represents a machine crash, storage failure, concurrent relay or an AWS delivery. The model does not implement SQS, Lambda, a transactional AWS relay, concurrent workers, payment capture, staff authorization or a production database. In a real design, define durable outbox polling/CDC, queue permissions, retry and retention, dead-letter triage, idempotent downstream effects, source-to-report reconciliation and operator ownership. [AWS's transactional-outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) explains the two-write gap; [Lambda's SQS integration](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html) documents repeated deliveries and batch-failure behavior. A FIFO queue's delivery feature cannot by itself guarantee exactly-once payment or report effects.

For each case, write a one-page decision: business contract, candidate and rejected alternative, authoritative data and write owner, accepted failure/recovery behavior, security boundary, validation test, 12-month cost categories and a cleanup or operating owner. Mark observations and assumptions separately. A service name alone is not a rationale.

1. **Compute and containers.** The existing application runs on a supported Linux VM and can be moved with a short downtime. Its vendor will not provide a maintained container image this quarter. Compare EC2 rehosting, Elastic Beanstalk and ECS/Fargate. State what would have to change before EKS or ECS Express Mode becomes justified. Then reverse the fact: the vendor delivers a supported image, the team already operates ECS and wants repeatable scaling. Revisit the choice, including ECR, health checks, image security, rollback and underlying cost.
2. **Storage.** Drawings are edited through a shared file path by two staff workstations. Exports are immutable files retrieved by key. Pick candidate storage interfaces for both and explain why an EBS volume attached to one app server, S3 objects, EFS and a Windows-compatible FSx offering are not interchangeable. Change the case: an on-site tool must keep a volume interface through the migration. Investigate Volume Gateway, its connection and cached-write recovery. Name the actual client operations and outage tests before purchase.
3. **Database.** The booking ledger uses relational constraints and joins; search results can be rebuilt. Compare an RDS-compatible move, self-managed EC2 database, DynamoDB redesign and OpenSearch index. Name schema/version, transaction, migration, recovery and read freshness tests. Change the case: a new lookup feature has a stable key access pattern and no join requirement. Decide whether a separate DynamoDB table earns its extra data contract. Never make the derived search index the sole booking record.
4. **A gradual seam.** The night report now takes an hour and sometimes retries. Keep the accepted booking write path intact. Compare an SQS worker, SNS notification, EventBridge routing and Step Functions orchestration for the report and a separate customer notification. Choose Lambda or a container for the worker from actual runtime and downstream limits. Explain how an event is durably tied to a committed booking, how duplicates are handled, and how a failed report is reconciled. Change the rule: finance now needs the report before the booking response returns. Which asynchronous proposal no longer meets the promise?
5. **Purpose-built state and money.** Booking reads spike at 9 a.m.; the authoritative relational writes are modest. Compare a measured read-path fix, ElastiCache, Aurora Serverless and a DynamoDB redesign. Record cache invalidation, capacity boundaries, cold/scale behavior to test, backup and total cost; do not assume a cache or serverless label makes the bill smaller. A promotional credit covers this month's estimated bill but expires during year one. Recompute the same architecture's resource cost without treating credits as savings.

Transfer: the shop acquires a second location with a Windows-only drawing tool, a stricter recovery promise and a two-person operations team. Revisit the five decisions as a connected architecture. Identify the first assumption that breaks, the minimum reversible change, and the evidence that would make a larger redesign worthwhile. Ask Codex to challenge your dependency map and cost categories; verify its factual service claims against current AWS documentation.
