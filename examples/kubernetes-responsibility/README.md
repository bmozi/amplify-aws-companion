# Kubernetes responsibility review

Original design-only practice for [the container lesson](../../reader/BOOK-LOCATORS.md#book-8444a5a7a3bbe0d5). No cluster or Kubernetes simulator is supplied. Answer before opening [assessor reasoning](ASSESSOR.md).

For each case, identify the observed fact, unsupported conclusion, responsible layer and next evidence. Then compare the operating work of the candidate platforms for the stated team.

1. **The unnecessary migration.** A two-person team runs one ordinary containerized API. Its proposal says “move to EKS because advanced systems use Kubernetes.” No Kubernetes API, controller or integration requirement is identified. Is that a sufficient reason? Name a changed requirement that would justify a new evaluation rather than assuming the current platform always wins.
2. **Desired replicas versus useful capacity.** A fictional Deployment requests three replicas. Two Pods are ready; the third remains pending because no eligible node has enough requested capacity. An operator reports “three healthy servers.” Rewrite the report and propose separate scheduling and customer-outcome observations. Do not assume a pending Pod means the container image is broken.
3. **Managed nodes and a broken release.** After a switch to EKS Auto Mode, a developer removes readiness checks and stops testing schema compatibility because “AWS operates the infrastructure.” Explain the responsibilities that remain. Which evidence would distinguish successful node replacement from a successful application release?
4. **The portable file.** A team copies a Kubernetes manifest to another cluster. It refers to an unavailable storage class, a cloud-specific load-balancer configuration and an AWS permission association that was not recreated. The manifest parses. Does the application work? List the dependencies that must be verified before calling the migration portable.
5. **The complete upgrade.** The control-plane update reports success. The operator closes the change without checking nodes, add-ons, controllers, clients or business transactions. Define the missing compatibility and operating evidence. Check the current AWS procedure rather than assuming every compute mode has the same update responsibility or that any rollback is universally available.
6. **The empty deployment.** The team reduces application replicas to zero and claims its experimental cluster costs nothing. Explain what must be inventoried and priced: cluster, remaining compute, load balancers, storage, observability, addresses and traffic where applicable. Distinguish no application Pods from no billable resources. Do not create a cluster to answer this case.

Submit a one-page responsibility map: application release, Kubernetes desired-state control, compute lifecycle, network entry, workload AWS access, persistent data, upgrade and retirement. Assign an owner and verification method to each. Include a concrete alternative and the requirement that would reverse your choice.

## Price the hours even when no Pods run

Use the [worked lesson](../../reader/BOOK-LOCATORS.md#book-efed0cfac6bfddcf) and the dated [AWS EKS](https://aws.amazon.com/eks/pricing/), [ECS](https://aws.amazon.com/ecs/pricing/) and [Fargate](https://aws.amazon.com/fargate/pricing/) pricing pages. This is arithmetic on a public list rate, **not** a live estimate, deployment or recommendation for this account. Write an inventory and calculation before opening [assessor reasoning](ASSESSOR.md#cost-cases).

7. **Forgotten learning cluster.** Assume a standard-support EKS cluster remains for 48 hours at the documented USD 0.10 per cluster-hour list rate; its Pods run for only four hours. Calculate the cluster charge floor. Would scaling Pods to zero satisfy a USD 5 *whole-run* estimate? Name at least four additional meter or resource categories that must be checked, and say what cleanup evidence would be needed.
8. **Shorter window, incomplete estimate.** Maya changes the cluster lifetime to 12 hours and quotes only the cluster charge. Calculate that floor. She now claims the experiment is safely below USD 5. Identify the missing price, quantity and lifetime inputs; explain why a smaller known floor is not a spending cap. Include EKS Auto Mode node-management charges if that mode is selected.
9. **Same application, different platform.** A colleague says, “ECS is free, so our two-task API will cost nothing.” State precisely which fee distinction AWS documents, then list the Fargate, ingress, data, network and observability inputs needed for a comparable outcome. Name one technical or staffing requirement that could justify EKS despite its cluster charge. Do not declare a cost winner until the same customer workload and acceptance measures have been tested.

For each case, keep public list prices separate from current account eligibility and credits. A credit changes payment, not resource consumption. Work through these cases on paper before considering a separately authorized implementation.

Ask Codex to review the map for an unowned dependency and an unsupported automation claim. Give it only fictional requirements, require current primary references for service behavior, and leave provisioning disabled. For any separately planned cloud experiment, estimate the whole run and choose spending and credit-reserve limits for the account in use.
