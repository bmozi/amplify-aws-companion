# Architecture design studies across business contexts

These design exercises extend the architecture catalog with concrete constraints and answer guidance. They do not represent 24 deployed solutions. Use fictional data. For each study, draw the normal request path, identity boundary and failure path; compare two options; estimate the smallest useful experiment; and state the evidence still required. Cloud execution needs a separately reviewed implementation and cost plan.

The [three-context transfer packet](../examples/architecture-transfer/README.md) connects A02, A04 and A10 through one reusable request-path diagram, six changed conditions and a museum transfer. Its [separate assessor](../examples/architecture-transfer/ASSESSOR.md) explains which business promises force different authority, state, recovery and cost decisions. It is an authored paper lab, not an integrated AWS deployment or a measured learner result.

The [four-case change-impact worklist](../examples/architecture-change-impact/README.md) adds a fictional time-sensitive transit alert to restore, school approval and tenant-burst cases. Its diagram follows the alert from a confirmed closure to the rider result. The graph and seven-question map check authored coverage. A small [timeline fixture](../examples/architecture-change-impact/transit_timeline.py) now separates late proposed sends, observed stale displays, send-time consent, channel acceptance, path observation and a five-minute event clock. The assessor tests whether a channel receipt is being mistaken for rider reach. No alert was sent or real deadline measured.

The [food-bank pickup journey](../examples/food-bank-pickup/README.md) adds one integrated local customer path: durable intake, a lost-reply retry, one-box inventory contention, confirmation-before-ready clock order and partner-scoped record/label reads. A separate two-ledger fixture commits a stock decision after losing its reply, then reconciles by stable operation ID after reopening both files; an unavailable lookup keeps the request uncertain. Its [assessor](../examples/food-bank-pickup/ASSESSOR.md) challenges the one-depot fixture with eight depots, ambiguous external stock, private files, peak demand and selective recovery. These are same-machine SQLite models, not a deployed food-bank service, external API contract or capacity result.

The [clinic offline-transfer case](../examples/clinic-offline-intake/README.md) separates a device receipt from central acceptance and human escalation. Its [stale-close extension](../examples/clinic-offline-intake/README.md#when-an-old-device-says-the-repair-is-finished) changes the problem again: a newer hazard exists before an older device sends “repair complete.” The local authority checks the work-order revision at the write and preserves the new report. The separate assessor requires a human decision and a review of all write paths; this does not prove cloud sync, clinical safety or actual repair.

## A01 Personal learning portal

A learner stores private notes and photographs. Another learner must not read them. Trace browser identity through the API and file access path; compare an Amplify-managed backend with directly managed service resources. The managed approach reduces setup work while hiding some ownership details that the lesson must expose. Use the recorded two-user denial checks as bounded evidence. Extend testing to real email recovery and API ownership changes before claiming those flows. Ask AI to identify a path the interface hides but the API permits.

The [OPS 04 five-practice observability review](../examples/ops04-field-lab/README.md) starts with the same portal but asks a different question: does a learner actually save and retrieve a private note when the static page is green? Its source inspection, four-receipt illustration, runnable fictional ledger reconciliation and changed-case assessor keep KPI, application, user, dependency and trace evidence separate. The AWS design remains unimplemented; no RUM, canary, trace or alarm is installed.

The [SUS 06 release-process review](well-architected-reviews/A01-SUS06.md) uses this portal's gated GitHub publisher to distinguish source checks, build work, approved publication and served customer behavior. It compares hypothetical push-trigger and no-update choices without claiming a GitHub runner or device measurement; the actual publication switch remains off.

## A02 Repair request processing

A repair shop accepts repeat submissions while the scheduler is unavailable. Compare synchronous completion with durable acceptance and later processing. The latter fits a business that tolerates delayed confirmation, provided status remains visible. Trace request, outbox, queue and worker; locate the atomic business effect. Inject dispatch and dependency failure. Bound queue retention, retries and worker concurrency. The existing implementation simulates scheduling inside the database; an external scheduler needs a verified retry/reconciliation contract. Ask AI for an ambiguous-timeout scenario and explain why another blind retry may be wrong.

Run the [local customer request journey](../examples/request-journey/README.md) before grading that status promise. Its loopback route uses the existing A02 Moto domain: the customer sees durable receipt, a truthful pending state through worker outage and a completed simulated effect after recovery. Its separate assessor asks whether the unchanged one-hour contact promise is actually met. The exercise has synthetic source-visible tokens, no Amplify screen or real customer authentication, and no live AWS deployment.

## A16 Recovery across Regions

A fictional business sets a recovery-time target and acceptable data-loss window. Compare backup/restore, a minimal standby and a continuously provisioned standby. Pick the least complex option that can be demonstrated against those requirements. Include service availability, quotas, keys, secrets, DNS and operator access in the target location.
