The existing [governed-sharing packet](../../examples/governed-sharing/README.md) supplies bypass, concurrent-writer and revoked-grant transfer. ## Skill 02 — Give independent consumers recoverable progress

Begin with the six [ingestion cases](../../examples/ingestion-review/README.md), then consult their separate assessor notes. Teaching is in unit 14, “Choose what each consumer must receive,” with the adjacent checkpoint and backlog sections. The [checkpoint recovery lab](../../examples/checkpoint-recovery/README.md) supplies actual local child-process exit/restart evidence: early progress loses an effect, while destination identity/content checks make replay safe for the fixture's transactional counter. It does not implement a streaming service client.

For transfer, draw a sales source feeding an operational dashboard and a fraud application. The dashboard needs fresh results; the fraud team must independently recompute the preceding seven days after a rule repair. The input can include duplicate deliveries and late sales. One consumer can be unavailable while the other remains healthy. Compare a shared work queue with independently progressing consumers over retained history. State which choice satisfies which requirement and what could make a scheduled batch sufficient instead.

Annotate the proposed design with business event identity, per-consumer progress, raw-source retention, output version, producer/consumer access boundaries and the destination where repeated application becomes safe. Walk through a crash after the effect but before progress, then a crash in the opposite order. Explain what happens when parallel work completes beyond an unresolved record. Do not call the result exactly-once merely because a progress marker exists.

Change the requirement: the replay begins near the end of the available retention period and takes time to finish. A retention setting of exactly seven days is not automatically sufficient for a seven-day replay. The earliest required records can expire while work remains. Identify margin, actual lag, service behavior and an alternative retained source to verify. Also separate rebuilding an analytical output from sending customer receipts again. Name both output freshness and reconciliation evidence; low error counts alone are insufficient.

Assessor criteria: require a coherent source-to-output path for each application, independent progress, bounded retention/recovery reasoning, duplicate/conflict handling, explicit access and side-effect boundaries, and an observation plan. Accept different service choices when justified. Reject a design that promises each application every event by having them compete for and delete work from one queue, or that treats a local SQLite transaction as atomic with external payments. For the fictional rate exercise, require the 6000-record backlog, 300-second drain after arrivals fall to 80/second, and no drain at 100/second arrivals with 100/second completion capacity.

Evidence is partial design reasoning and local crash/restart behavior. Actual service selection/configuration, partition/key distribution, throughput and consumer-lag measurements, retention recovery, producer authentication, IAM denial tests, replay costs and independent design/learner review remain unverified. These cases authorize no streaming resources or cloud fault injection.

Teaching: unit 14, “Choose processing compute from the shape of the work.” Complete the six [processing-selection cases](../../examples/processing-selection/README.md) before consulting their assessor notes. Distinguish scheduling an existing executable from selecting a transformation or distributed engine. Compare Batch, Glue and EMR candidates against the required interface, framework/dependencies, operating model and evidence; include a simpler worker when the job does not require distributed processing.

The changed cases require separating a 70-second longest partition from a 25-second mean, and a 55-minute end-to-end job from its 20-minute compute portion. These authored calculations were checked locally; no distributed performance was measured. Runtime compatibility, selected service configuration, measured representative workloads, IAM, failure recovery, price reconciliation and independent assessment remain open.

## Skill 07 — Preserve meaning while changing representation

The processing-platform choice is assessed separately above; a conversion result alone does not establish that choice.

Run the [contracted CSV conversion drill](../../examples/analytics-query/README.md#convert-a-contracted-csv-before-optimizing-it) using its pinned DuckDB environment. Before running, explain how `001`, literal `NULL`, blank amount, a refund and a timestamp without its required timezone marker should behave. Then predict a conversion defect that preserves row count and total but changes identity.

Teaching: unit 14, “Change the file format without changing the facts.” Evidence: schema_lab.py writes a real CSV, validates the small batch, creates an explicitly typed table, writes Parquet and reads the expected values and column types back. The total is 1010 cents. Fifteen invalid batches leave no output, and an existing output is refused unchanged. A deliberately stripped leading-zero ID fails the complete-row oracle.

Assessment requires preserving identifiers, units, accepted timestamp instants and the currency contract, not just producing a readable file. Explain why an unknown header, unsupported currency or unexpected decimal precision calls for a contract decision. Compare whole-batch rejection with owned, durable quarantine; identify the memory and concurrency limits of the local exercise. Extend the design for a second currency and explicit offsets with independent expected results before editing.

The [mixed-version drill](../../examples/analytics-query/README.md#read-old-and-new-contracts-together) adds local coexistence evidence. A successful aggregate over aligned column names returns the incorrect 1230 cents; version-aware translation preserves three expected rows and the correct 1010 cents. Eight invalid mixed batches leave no output. Original source hashes remain unchanged, and an existing result is refused. A deliberately invented default channel fails the complete-row assertion while money remains unchanged.

Assess this changed case without editing the expected result to match the program: the new writer adds a currency and omits a historical channel. Explain whether the old reader can consume the new records, whether the new reader can consume the old records, and which facts remain unknown. Propose independent expected rows for mixed currencies, duplicate IDs across versions and a version-3 payload that resembles version 2. Require currency-separated totals or an explicit conversion policy, stable identity, unknown-version rejection until supported, and no invented historical channel. A reader who merely enables column-name alignment has not solved the interpretation problem.

This is partial local conversion and bounded version-coexistence evidence. Cloud schema evolution, realistic volumes, compression/row-group choices, crash-safe publication, concurrent writers, exhaustive physical-schema validation, source authorization and a selected AWS conversion path remain unverified. The Firehose paragraph describes documented input/schema requirements, not a tested integration. Independent technical and learner review remain pending. No complete task or certification readiness is inferred.
