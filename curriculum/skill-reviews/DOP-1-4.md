# Individual skill review for DOP-C02 task 1.4

Internal editorial review, updated October 19, 2026. The official [Domain 1 page](https://docs.aws.amazon.com/aws-certification/latest/devops-engineer-professional-02/devops-engineer-professional-02-domain1.html) currently lists four separate task 1.4 skills: artifact-repository security permissions, deployment-agent configuration, deployment troubleshooting, and use of deployment methods such as blue/green and canary. The ordinals in our ledger are editorial identifiers, not AWS-issued IDs. This review maps all four listed skills individually; every mapping remains partial.

## Configure security permissions for artifact-repository access — skill 01

Unit 06's “Give each release job only its own repository key” applies the identity lesson to dependency readers, package publishers, application deployers and administrators. The [six design-only cases](../../examples/artifact-repository-access/README.md) and [separate assessor](../../examples/artifact-repository-access/ASSESSOR.md) ask for caller, action, resource, policy locations and evidence. They distinguish CodeArtifact package/repository/domain permissions and cross-account policy paths from ECR image-repository and S3 object/bucket authorization. They also require a meaningful allowed operation and a valid forbidden operation without damaging test data.

Current AWS documentation confirms that CodeArtifact has identity-based and resource-based permissions; its domain and repository resources differ from package resources; package clients can need token and metadata permissions in addition to repository reads. Cross-account access requires both the caller's identity permission and an owner-side resource policy, subject to applicable denies. Exact actions vary by client/package format and must be checked in the current permission reference. See [CodeArtifact permission/resource reference](https://docs.aws.amazon.com/codeartifact/latest/ug/auth-and-access-control-permissions-reference.html), [repository policies](https://docs.aws.amazon.com/codeartifact/latest/ug/repo-policies.html), [CodeArtifact IAM support](https://docs.aws.amazon.com/codeartifact/latest/ug/security_iam_service-with-iam.html), and [IAM access-denied diagnosis](https://docs.aws.amazon.com/IAM/latest/UserGuide/troubleshoot_access-denied.html).

Evidence remains partial and design-only. No IAM policy was authored for a real repository, no CodeArtifact/ECR/S3 access was configured, and no live allow/deny, token, cross-account or pipeline execution was tested. Before implementation, select one repository/client, verify each required action and supported resource ARN in the current service authorization reference, review all policy layers and pipeline authority, then test a safe allowed operation and a meaningful denial using the scoped non-root identity in a disposable path. Choose and verify an appropriate credit reserve and estimated-run ceiling for any separately approved cloud practice. Independent technical and learner review remain pending.

## Configure deployment agents — skill 02

Unit 03's “Put the EC2 deployment agent on the right machine” explains the EC2/On-Premises CodeDeploy agent, supported OS/version checks, outbound communication, revision retrieval, lifecycle hooks and the distinct CodeDeploy service role and EC2 instance profile. The [six design-only setup cases](../../examples/codedeploy-agent-setup/README.md) and [assessor notes](../../examples/codedeploy-agent-setup/ASSESSOR.md) test target selection, agent state/version, private-network path, role separation, ECS/Lambda boundary, image/update strategy and ordered troubleshooting.

Current AWS documentation says the agent is required for EC2/On-Premises CodeDeploy and not for ECS or Lambda; agent minimum version and OS/architecture support are explicitly versioned and should be rechecked at implementation time. AWS documents outbound HTTPS over port 443, an EC2 instance profile for revision-source access and a separate CodeDeploy service role for control-plane operations. Systems Manager can install/update the agent when its own managed-node requirements and permissions are satisfied. See [agent support and version](https://docs.aws.amazon.com/codedeploy/latest/userguide/codedeploy-agent.html), [Systems Manager installation](https://docs.aws.amazon.com/codedeploy/latest/userguide/codedeploy-agent-operations-install-ssm.html), [instance profile](https://docs.aws.amazon.com/codedeploy/latest/userguide/getting-started-create-iam-instance-profile.html), [service role](https://docs.aws.amazon.com/codedeploy/latest/userguide/getting-started-create-service-role.html), and [instance troubleshooting](https://docs.aws.amazon.com/codedeploy/latest/userguide/troubleshooting-ec2-instances.html).

Coverage is partial and design-only. No agent was installed, no instance or role changed, and no CodeDeploy deployment was run. A practical assessment still needs a selected supported OS/AMI and Region, an approved agent version, separate least-privilege instance/service roles, a safe target-selection proof, network and artifact evidence, failure/recovery observations and cost/cleanup records. The current AWS session is expired; no account state was checked during this update. Independent technical and learner review remain pending.

## Troubleshoot deployment issues — skill 03

Unit 03's “Find the first failed boundary” introduces a six-stage diagnostic path from exact revision identity through actual recovery. The [six synthetic case packets](../../examples/deployment-troubleshooting/README.md) and [separate assessor notes](../../examples/deployment-troubleshooting/ASSESSOR.md) cover an EC2 prior-revision stop hook, a bundle retrieval/Region clue, an ECS image-pull and task-health failure, a stopped Lambda weighted alias, an ECS all-at-once health failure despite “Succeeded,” and a stop request that remains pending after partial lifecycle effects.

The cases follow current AWS CodeDeploy troubleshooting guidance for deployment/instance logs and platform-specific evidence. In particular, EC2 `ApplicationStop` uses the previous successful revision; ECS task-set and target-group health differ from CodeDeploy's top-level result; a stopped Lambda deployment without rollback can leave a weighted alias; and stopping/failed deployments may have already run scripts or changed files. The exercise requires evidence before retries or policy edits and treats rollback as another deployment, not erasure.

Coverage is partial and synthetic. No incident was queried, no deployment was stopped or retried, and no rollback or customer request was observed. A live assessment needs the exact deployment ID/revision, platform events/logs, caller and target identity, evidence of partial effects, one bounded repair, and a verified business outcome. The deployment remains blocked on an expired AWS session, so current account state was not checked. Independent technical and learner review remain pending.

## Use different deployment methods — skill 04

Unit 03's “Choose a deployment method by the promise you need” separates the controller from the release label: EC2 in-place/blue-green and instance concurrency; Lambda alias weights; CodeDeploy ECS replacement task sets and two target groups; and the ECS controller's rolling, blue/green, linear and canary strategies. The [seven design-only transfer cases](../../examples/deployment-method-selection/README.md) and [separate assessor](../../examples/deployment-method-selection/ASSESSOR.md) ask learners to name the exposure unit, health/business evidence, representative observation window, overlap cost, data compatibility and verified recovery. One case calculates ECS rolling task bounds with the scheduler's round-up/round-down rules; another compares native ECS canary, CodeDeploy ECS canary and rolling replacement without equating task overlap with request weight.

The current AWS task page lists use of different deployment methods, including blue/green and canary. Current CodeDeploy documentation distinguishes EC2 instance deployment configurations from Lambda and ECS traffic-shifting configurations; ECS CodeDeploy blue/green uses a load balancer and two target groups, while native ECS rolling uses minimum/maximum healthy percentages and its own failure detection. See [DOP-C02 Domain 1](https://docs.aws.amazon.com/aws-certification/latest/devops-engineer-professional-02/devops-engineer-professional-02-domain1.html), [CodeDeploy configurations](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-configurations.html), [EC2/On-Premises workflow](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-steps-server.html), [CodeDeploy ECS workflow](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-steps-ecs.html), [CodeDeploy Lambda workflow](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-steps-lambda.html), and [native ECS rolling deployments](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html).

Coverage is partial and design-only. The existing loopback canary is deterministic synthetic traffic; no AWS weighted shift, CodeDeploy deployment, ECS capacity behavior, representative production sample, current bill or customer rollback was observed. A practical assessment needs a selected controller and Region, permission-scoped configuration, measured traffic/capacity and cost, stop/rollback test, business-side-effect reconciliation and verified cleanup.
