# A01: six best-practice questions, one bounded workload review

Reviewed October 21, 2026 against the current linked AWS question pages. This is an authored **sample of one best practice per pillar** for the Amplify field lab's repair-request journey. It does not answer every question in a pillar, record a Well-Architected Tool milestone, assign an AWS risk rating, or establish current account compliance. The linked source and [reader playbook](../../docs/FIELD-LAB-READER-PLAYBOOK.md) support the teaching review; dated owner execution records are separate and the AWS session was expired during this review.

The workload boundary is the browser, sign-in, private request and attachment, backend processing, status read, hosting publication, monitoring, and cleanup. A page that loads is one observation inside that boundary. Before a real review, confirm this boundary and the actual service/resource inventory with the owner; do not infer current deployed topology from source alone. The [Unit 32 worked explanation](../../reader/BOOK-LOCATORS.md#book-c0fb4ecf2653015f) and [changed-case exercise](../../examples/well-architected-review/README.md) teach the same method in plain language.

| [OPS07-BP03 — Use runbooks to perform procedures](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops-07.html) | An operator needs a repeatable way to stop publication, investigate a missed assignment, and retire resources. | [Reader operating plan](../../docs/FIELD-LAB-READER-PLAYBOOK.md) and the [GitHub publication guide](../../reader/GITHUB-TO-AMPLIFY-FIELD-LESSON.md) document actions and stop switches. Written instructions are not an observed on-call execution. | Have a scoped operator follow the exact procedure on an authorized bounded case; capture start state, decisions, alert/notification evidence, stop action, resource inventory and later cost reconciliation. |
| [SEC03-BP02 — Grant least privilege access](https://docs.aws.amazon.com/wellarchitected/latest/framework/sec-03.html) | A publisher and a signed-in borrower need different authority; neither may gain another user's files because an ID is known. | The [publisher Terraform candidate](../../infra/github-publisher/main.tf) scopes one branch; [tenant-isolation tests](../../examples/tenant-isolation/README.md) exercise local denials. The publisher role is not known to be installed, and local tests do not prove live IAM/Cognito/AppSync/S3 enforcement. | Inspect the current role and effective authority, then perform scoped allowed and forbidden live operations across record, list, write and file paths. Keep organization-wide guardrails design-only in this exercise. |
| [REL04-BP04 — Make mutating operations idempotent](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel-04.html) | A lost acceptance reply must not create two repair jobs when the customer retries. | The [request contract lab](../../examples/api-contract/README.md) checks same-intent replay and changed-intent conflict locally. It cannot prove the deployed app's retry key, retention or concurrent path. | Trace one bounded accepted request through a dropped response, replay and status read under scoped identities; record the authoritative request ID and any duplicate external effect. |
| [PERF05-BP04 — Load test your workload](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf-05.html) | A monthly average cannot show whether the busiest shop gets its assignment on time. | [Local scaling models](../../examples/reliability-growth/README.md) teach bottleneck and backlog reasoning. They are not a representative Amplify/AppSync/data/function benchmark. | Agree on arrival shape and deadline first; run only a cost-reviewed, bounded selected path, observe end-to-end tail outcomes and stop when the run or account guardrail triggers. |
| [COST02-BP05 — Implement cost controls](https://docs.aws.amazon.com/wellarchitected/latest/framework/cost-02.html) | A working app can consume credits through hosting, backend requests, logs and retained data. | The author's account uses a USD 5 estimate ceiling and USD 100 reserve in its [credit policy](../../reader/COST-AND-CREDIT-FIELD-LESSON.md), preflight code and pending [whole-run record](../../examples/costs/publisher-run-estimate.json). Readers choose limits for their own accounts. The record remains `review_needed`; neither a budget nor an estimate is a hard spend cap. | Refresh the selected account's plan and credit terms, prices, audience and all meters; record a supervised run, teardown inventory and later pre-credit usage. No live run follows from this review. |
| [SUS04-BP03 — Use policies to manage the lifecycle of your datasets](https://docs.aws.amazon.com/wellarchitected/latest/framework/sus-04.html) | Old attachments and backups can remain after the visible request is gone. Removing them too early can defeat recovery; keeping all forever adds resource use and access exposure. | The [SUS 04 data review](A02-A03-SUS04.md) explains retention by business purpose with fictional cases. It is not an approved policy for actual customer data or a measured lifecycle configuration. | Obtain the data owner's retention and restore decisions, inventory all copies, verify lifecycle/deletion behavior and measure relevant resource use before making a sustainability claim. |

These are **partial teaching and source-evidence mappings**. For each row, “next evidence” is a real dependency, not a box to mark complete from the lesson. A formal AWS review would apply all relevant framework and lens questions to the confirmed workload, record answers and risks, prioritize improvements, and save a dated milestone. [AWS describes milestones](https://docs.aws.amazon.com/wellarchitected/latest/userguide/milestones.html) as snapshots of workload state; this file is a local teaching review, not such a snapshot.

## Changed-condition check

Suppose one repair shop requires a seven-day private-file retention limit, while a second shop requires selective restoration of yesterday's requests without rolling back anyone else. Which of the six sampled practices now needs new evidence first? Identify the privacy/data owner, the restore owner, the current unknowns and one observation that could reject a proposed shared store. Ask Codex to identify a missing copy or permission path, then verify that path against the actual design. A sound answer should not delete a needed recovery copy by reflex or call a restore successful from a database row alone. Use the [branch-library assessor](../../examples/well-architected-review/ASSESSOR.md) for general transfer criteria; no independent response has been collected for this specific changed case.
