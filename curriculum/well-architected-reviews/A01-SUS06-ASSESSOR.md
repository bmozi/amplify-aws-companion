# Assessor: SUS 06 release-work decision

Read the [case](A01-SUS06.md#changed-condition-exercise-forty-pushes-and-one-release) after your first answer. This is authored reasoning, not a GitHub run, sustainability measurement or learner result.

Forty pushes could start the three-job publisher forty times under the proposed automatic trigger: up to 120 job starts, assuming every gate is opened and jobs are not skipped. The current manual `workflow_dispatch` plus disabled repository variable has **zero recorded runs at the last read**. If one approved release were manually invoked and all gates passed, it would start one typecheck, one build and one publish job. These are conditional job-start counts, not runner duration, billable minutes, resource use or energy. A source-check workflow on each change could add its own work; it is a separate proposal, not present in the current publisher.

A sound improvement keeps the ability to test source changes promptly and to apply a critical dependency fix outside a monthly calendar. It does not need to publish every push. The reviewed source, lockfiles, build artifact, exact commit/run marker and hash must remain connected. The full-tree typecheck does not need the account browser output; the smaller static builder receives that output only after install and does not need AWS credentials; the publisher receives the ZIP and temporary scoped role, not an npm installation. Combining jobs might reduce duplicated runner setup, but putting dependency execution beside the AWS role or browser output before installation changes the trust boundary. Measure the actual runner work before claiming a net resource benefit from either layout.

“Never update” ignores security, compatibility, customer and efficiency changes. The current 44 affected full-tree entries are not all proven exploitable, yet a zero-finding browser-builder audit does not dispose of them. A critical compatible fix should follow a bounded source/build/security/customer check and a deliberately approved release or rollback decision. Likewise, an older phone or slow network test must measure task success and payload behavior, not only whether a desktop build passes. Device Farm may be a candidate after current price and account eligibility review; nothing in this packet authorizes its use.

A strong answer keeps customer correctness, role scope, cost and resource evidence together. It labels the organization's environmental goal as absent, distinguishes job counts from observed usage and carbon, and records the actual off switch before discussing hypothetical automation.
