# SUS 05: choose the machine only after naming the work

Reviewed October 19, 2026 against the four [AWS Well-Architected SUS 05 hardware and service practices](https://docs.aws.amazon.com/wellarchitected/latest/framework/sus-05.html). This is a workload-specific teaching review of A02 repair processing and A03 seat reservations. It is not a Well-Architected Tool finding, an EC2 or accelerator benchmark, a comparison of measured energy/carbon, or permission to provision a second architecture in any account. Inspect the current [A02/A03 Terraform](../../architectures/reliable-workflows/infra/main.tf) and [SUS 02 deadline lab](../../examples/demand-alignment/README.md) before the exercise.

## The repair shop needs completed repairs, not a named machine

Maya's 90 fictional repair requests arrive in a burst. An engineer proposes replacing the bounded Lambda/SQS worker with an always-running EC2 instance. Another proposes a GPU because “faster hardware is greener.” Neither has shown that the new path durably accepts each request, finishes the same correct repairs by the deadline, recovers after interruption or costs within the approved run. A service label and a device label are options, not evidence.

![The same repair promise branches to the existing managed Lambda and SQS path, a hypothetical always-on EC2 worker, and an accelerator only if a new workload needs it. A comparison gate requires identical correct timely outcomes, whole-path resource and cost evidence, recovery, and teardown.](../../book/figures/hardware-choice-evidence.svg)

The current disposable Terraform root declares SQS work and failed queues, a DynamoDB table, four Lambda functions and a Lambda/SQS event-source mapping with maximum concurrency two. It does **not** declare an EC2 instance, container fleet, GPU or model endpoint. Lambda and SQS are managed services, yet they still consume AWS hardware and billable/observable service work. The team owns the application contract, data, permissions, cost decisions and cleanup of provisioned resources. The [SUS 02 worksheet](../../examples/demand-alignment/README.md) counts fictional provisioned worker-minutes; it does not identify Lambda hardware or give an EC2-to-Lambda energy conversion.

The **comparison unit** is one correct, timely customer outcome under the same input and failure case. An EC2 instance-hour, a Lambda GB-second, one SQS request and a GPU-hour are different physical and billing quantities. Adding them into a single “hardware score” without a defensible conversion would hide assumptions. Cost is separately calculated from dated regional rates and actual quantities; environmental impact needs a defined measurement method and boundary. AWS's guidance for managed services describes potential shared-utilization benefits, but this book has not measured the underlying service allocation for this shop.

## Changed-condition exercise: the attractive GPU

Start with the 90-repair burst and minute-four completion promise from [SUS 02](A02-A03-SUS02.md). A teammate says, “Move the worker to one always-on EC2 instance; it is easier to reason about. Add a GPU to make the new image-check step faster. We can call the system greener because each individual image finishes sooner.” The image step is a **new hypothetical requirement**: 10,000 customer photographs arrive monthly, mostly in one two-hour window. No accuracy, latency, processor-time, idle, transfer, retained-image or price measurements are supplied.

Before reading the [assessor](A02-A03-SUS05-ASSESSOR.md), draw the current and proposed paths. Keep the request receipt, repair deadline, last-seat transaction and image permission boundary separate. Compare two bounded alternatives: (a) keep the existing managed repair path and test a temporary image processor only for its window; (b) move both jobs to the always-on EC2/GPU design. State what would disqualify either, what measurements and current prices are needed, and how to shut the experiment down. Then change the image requirement: the shop now needs a verified answer within 30 seconds at any hour. Which assumptions and cost/availability meters change? Ask Codex to make the strongest case for the GPU, then require it to name a CPU or managed-service counterexample and the evidence that would resolve the choice. Do not accept a brand or “performance per watt” slogan as measured shop evidence.

**Review disposition:** all four SUS 05 practices now have source-linked, workload-specific teaching and a changed case. The current Terraform supports the stated managed-service inventory only. No real EC2/GPU option, whole-path cost, energy/carbon, independent learner response or exact-final book review was tested. This exercise uses no AWS resource or credit; any later live trial needs current plan and credit checks and account-appropriate limits.
