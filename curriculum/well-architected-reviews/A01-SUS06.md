This is a teaching review of the A01 Amplify frontend and its [manual GitHub publisher](../../examples/github-workflows/amplify-publish.yml), not an organization sustainability program, a measured CI energy audit, a Device Farm run or a live publication. The repository's switch was last read as `AMPLIFY_PUBLISH_ENABLED=false`, with zero workflow runs at that read. The workflow source requires `main`, a manual `yes` and the enabled switch; source review is separate from a real GitHub run.

## A green build is only one kind of green

Maya changes a repair-shop page. A build can prove that files were produced. It cannot prove that the new page handles a slow phone, that a customer still gets the right repair status, that an update uses fewer resources, or that publishing it is authorized. Keeping the old site forever avoids build work but can leave security and usability defects. Publishing every push can waste release work and broaden the chance that unreviewed code reaches customers. The useful loop is **state the customer and resource question, test a bounded change, review the artifact and authority, release deliberately, then observe the customer path**.

![A proposed improvement starts with an explicit customer and resource question, passes source and browser checks, then crosses a manual publish gate before customer-path observation. The loop records build work and measured outcome separately; the current GitHub gate is off and no workflow run is claimed.](../../book/figures/sustainability-release-loop.svg)

The checked-in publisher has three jobs. `typecheck` installs the larger Amplify development tree without account output or an AWS role; `build` installs the smaller frontend lockfile, audits it, stages browser inputs and packages static files; `publish` alone requests temporary AWS credentials. That separation limits what each job can access, but it also means two installs and two GitHub jobs before publication. Our October 19 local builder audit found zero findings while the full development tree had 44 affected entries. Neither finding count measures the compute or energy of GitHub's runners. The workflow has never run on GitHub in this project; its job durations and billable minutes are unknown. [Publisher dependency field lesson](../../reader/DEPENDENCY-FIELD-LESSON.md).

## Changed-condition exercise: forty pushes and one release

Assume **40 fictional commits** during a month and **one reviewed customer release**. A teammate proposes triggering all three publisher jobs on every push “to make the pipeline sustainable.” Another proposes never updating because the current site works. A third wants to merge the two build jobs to reduce installs and give that merged job the AWS role. The actual workflow remains manual and disabled; these are proposals, not observed GitHub usage.

Before reading the [assessor](A01-SUS06-ASSESSOR.md), compare the three proposals with the current gated route. Count possible job **starts** under each proposal but do not invent runner-minutes or carbon from that count. State which source/security checks should run on change, which artifact should be promoted once, where account output and AWS credentials belong, how a bad release is stopped or rolled back, and what a representative customer-device test would observe. Now change the facts: a critical dependency fix arrives after the monthly release. How would the update path avoid an unnecessary delay without turning every source push into an automatic production release? Ask Codex to propose a lower-resource build layout; require it to preserve the exact secret, artifact and OIDC trust boundaries and to state the measurements needed to claim a resource improvement.
