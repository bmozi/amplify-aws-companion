# SUS 04 data-life assessor

This is author reasoning for the [changed-condition exercise](A02-A03-SUS04.md#changed-condition-exercise-restore-the-wrong-life), not a sample learner result or a complete legal/data policy.

1. The accepted request and appointment/reservation are candidates for authoritative business records. An outbox row describes work yet to be delivered; a queue message is a transport copy; a derived report is only safely recreatable if its inputs, code and deadline permit. The named product/data owner must decide exact classification and retention. Item kind alone is not a legal class.
2. A table-wide restore into a new table can contain Shop A's pre-closure rows and yesterday's unsent outbox. It must not replace today's active table or reopen a customer path by default. Check tenant status and current business state, compare item identities/versions, and selectively reconcile the one lost Shop B result under an authorized operator workflow. Keep the restore isolated and delete it when no longer needed. Test both customer paths after cutover.
3. TTL is delayed background deletion, not immediate denial, business hold release or a customer-facing erasure receipt. No TTL is configured in this lab. The current domain has manual conditional hold transitions; that remains the seat authority until a separately verified production design exists.
4. Reconciliation from the restored table needs an idempotency and outbox rule so an old request does not send a second effect. If Shop B's appointment has a separate authenticated source, prove its completeness and restoration time before choosing reconstruction. In the first changed case it does not, making recoverability a real requirement. In the second changed case the report may be rebuildable, but verify inputs, code, deadline and resource/cost estimate before excluding that *report copy* from backup.
5. Compare costs before credits: retained table/index bytes, backups, temporary restored table, read/write requests, queue/log work, data movement and cleanup. The fictional 20 MB says little about request volume, restore duration, access control, backup pricing or customer correctness. No carbon percentage follows from a byte count. A live run requires a whole-run estimate within the account owner's chosen ceiling, an appropriate credit reserve and current-account checks.

A strong answer states a customer outcome and a denied Shop A access path, not only a smaller data footprint. It records unresolved sensitivity, retention, RTO/RPO, exact permissions, regional prices, restore time and independent learner review. The exercise never proves that current synthetic records can or should be restored from AWS.
