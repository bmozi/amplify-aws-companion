From a blank account
to a working app.

A guided lesson in what AWS Amplify does, why you might use it, and how the files in this project bring an application to life.

Open the hands-on lab →

Suppose you want a small website where you can keep learning notes and attach files. You want to open it from another computer and still find your work. You also want your notes to stay private.

The page you see is only part of that job. Something must deliver the page, recognize you, remember your notes, and protect your files. Amplify gives you tools to connect those pieces. You still decide what the app does and who may use its data.

What you will learn

By the end, you should be able to explain the difference between the page and the services behind it, trace a saved note to its storage, identify the files that define the app, plan a safe deployment and explain why closing a browser does not stop every cloud charge.

You can complete the browser exercises without coding experience. Rebuilding the environment requires basic terminal use, an AWS account, and permission to create resources. Take one lesson at a time.

Lesson 1

Start with what the person does.

When you open this notebook, your browser downloads the page and the code that draws its buttons. We call that visible part the frontend. When you save a note, your browser asks a service in AWS to store it. Those behind-the-scenes services are the backend.

You click Save→API checks the request→Database stores the note

An API is a defined way for software to ask other software to do something. Here, the request says, “Save this note for the person who is signed in.” The API uses your sign-in information and permission rules before allowing the operation.

What you needPlain explanationAWS name
A page people can openDeliver the website over an HTTPS address.Amplify Hosting
A way to sign inCheck the account and issue a temporary signed-in session.Amazon Cognito
A way to ask for dataReceive requests for notes and apply the access rules.AWS AppSync
A place to remember notesStore structured records such as a title and its text.Amazon DynamoDB
A place for filesStore uploaded file contents separately from note records.Amazon S3
Your own server-side actionRun a small piece of code when a request arrives.AWS Lambda

Amplify is not one server containing all of these things. Its hosting service, backend tools, client libraries, and ready-made interface components help you assemble and use AWS services. That is why you can see Cognito, S3, and other resources separately in your AWS account.

Check your understanding

If you change the page color, should your saved notes disappear? No. The page code and the saved records are different parts of the system. A deployment can change the page while leaving the database alone.

Lesson 2

Write down what should exist.

You could click through the AWS console and create each resource by hand. That can help you learn, but it is easy to forget a setting. This project puts the intended setup in files. Tools read those files and create or update the resources. This practice is called infrastructure as code.

We use two tools with different responsibilities. Terraform creates the Amplify Hosting app and its lab branch. A branch is a named version of the hosted application. Amplify Gen 2 reads TypeScript definitions for sign-in, notes, files, and the function. It uses AWS CloudFormation to manage that backend.

Each resource has one owner. If both Terraform and Amplify tried to control the same database, one tool could undo the other's changes. Our files keep those responsibilities separate.

Open this fileWhat it tells the tools
infra/hosting/main.tfCreate the Hosting app and lab branch in the expected AWS account.
app/amplify/backend.tsPut the backend pieces together.
app/amplify/auth/resource.tsLet people sign in with email.
app/amplify/data/resource.tsDescribe an Entry and make its records private to their owner.
app/amplify/storage/resource.tsGive each signed-in identity a private file path.
app/amplify/functions/inspect/handler.tsCount words and characters when the inspector runs.
app/src/main.tsxDraw the app and connect its buttons to the backend.
app/src/style.cssControl appearance and mobile layout.

The complete local file map is docs/FILE-MAP.md. The package-lock.json and Terraform lockfile record dependency versions. They help another run use the same tool components.

Why does Terraform have a state file?

The configuration describes what you want. The state file records which actual AWS resources Terraform is managing. Losing it can make safe updates and deletion harder. State and saved plans can contain sensitive values, so keep them private. A lockfile records provider versions; it is not the same thing as a state file.

Check your understanding

To change the color of the Save button, start with the frontend style file. To change what a note contains, start with the data definition and then update the form. You now know where to look instead of treating the project as one mysterious block.

Lesson 3

Plan a deployment before you run it.

Provision means create cloud resources. Deploy means put a version of code or configuration into use. This project has four connected jobs: Terraform defines Amplify Hosting, Amplify Gen 2 defines the backend, the frontend build makes browser files, and the publication workflow sends reviewed files to Hosting. A successful local build proves only that browser files were made.

Imagine renting a small workshop. First check that you have the right address and keys. Next read the lease and the estimate. Then ask the builder to prepare the room. Finally walk through the door and test that it works. A cloud deployment needs the same order.

1. Check the address and authority.

Use a temporary, suitably scoped non-root AWS identity. Confirm the account and Region, the intended Amplify app and branch, and the roles that would create resources. Your own profile name and account ID belong in your private configuration, not in a copied command from this lesson. The source-side scripts/publisher-account-preflight.py explains a read-only address check; a denied read leaves that fact unknown. Do not switch to root to get around a denial.

2. Estimate the whole run.

Check your current plan, credit terms and existing usage. Estimate Hosting build work, requests, data transfer, storage, backend activity, logs, verification and cleanup. Choose your own spending limit and reserve before creating anything. A budget alert warns you after measured usage; it is not an automatic stop button.

3. Read the proposed changes.

Open infra/hosting/main.tf for the Hosting owner and app/amplify/backend.ts for the backend owner. Terraform state tells Terraform which real resources it manages. A saved plan shows its proposed changes; review the account, Region, creations, updates and deletions before any apply. Backend deployment also uses CloudFormation roles, so inspect the permissions those roles can exercise. The docs/FIELD-LAB-READER-PLAYBOOK.md in the companion repository walks through this review.

4. Build, publish and observe.

Install the versions recorded by app/package-lock.json and run the local frontend build. The checked-in GitHub publication caller has a manual enable switch. Its reusable workflow repeats release checks, builds the upload bundle and then uses a short-lived AWS role in a separate job. Enabling that one workflow does not authorize every GitHub repository or every workflow. Inspect the workflow target and its role trust before a release; keep the switch off when no release is intended.

After an authorized deployment, open the returned site and test a real sign-in, save, refresh and private file path. Test that another authorized test user cannot read the first user's record or file. A source review, build, Terraform plan or green workflow by itself cannot establish that customer path.

What you should be able to explain

Point to the file that owns Hosting, the files that own the backend, the workflow that publishes the browser files, the account and cost checks that come first, and the observations that would prove the app actually works.

Where are the exact commands?

The companion repository keeps the current flags and prerequisites beside the operations they control: infra/hosting/, scripts/deploy-backend.py, scripts/deploy-frontend.py and docs/FIELD-LAB-READER-PLAYBOOK.md. Those helpers are tied to the owner's project and must be reviewed and adapted before use in another account. If credentials expire, renew the intended scoped session. If an output file is missing, complete and verify the backend step before a frontend build. If an API request is denied, inspect sign-in and authorization rules rather than removing them.

Work with AI, then verify

Give Codex the relevant source and sanitized evidence. Ask: “Map each deployment job to its owner, identity, target and possible charge. List what still needs account or customer-path verification.”

Your check: Compare the answer with source, a reviewed plan, your cost estimate and observed results. Keep credentials and private account receipts out of a public package.

Lesson 4

Learn by making one thing happen.

Use invented notes and small test files. The lab is an experiment. You do not need private documents to understand what it does.

Exercise A: Give the app an identity.

  1. Choose Create Account in the app.
  2. Enter an email you can receive and choose your own password.
  3. Enter the email-confirmation code AWS sends, then sign in.

You have created an account in this app's Cognito user pool. A user pool is the app's directory of people who can sign in. This account is separate from your AWS console account. The app does not need your AWS administrator password.

Look for: your email in the app and the Sign out button. Email delivery and recovery should be checked with your real mailbox; our automated test identities deliberately did not send email.

Exercise B: Make the app remember.

  1. Open Data + real-time. Save a note titled “My first discovery.”
  2. Refresh the page. The note should remain.
  3. Choose Edit, change its text, and save again.
  4. Open another tab with the same account. Mark the note Explored in the first tab.

The second tab should update without a page refresh. It has a subscription: an open connection through which AppSync can deliver relevant changes. The saved note lives in DynamoDB, not just in the first tab's memory.

Make a prediction: if you sign into a different app account, should this note appear? No. The model's owner rule restricts who can read and change it. Authentication answers “Who are you?” Authorization answers “What may you do?” We need both.

Exercise C: Store a file.

  1. Open Storage and upload a small text file.
  2. Open it and check its contents.
  3. Refresh the file list, then delete the test file.

S3 stores the file. The app's identity pool exchanges your signed-in session for temporary AWS permissions. Those permissions are limited to your private path. A file's name is not a security boundary; the permissions are.

The app opens a short-lived signed link. Anyone who receives that link can use it until it expires, so do not share it unless you intend to share access. The interface's 5 MB upload limit is a convenience check, not a server-enforced account quota.

Exercise D: Run your own action.

  1. Open Functions. Enter “one two three.”
  2. Choose Run Lambda function.
  3. Find words: 3 in the returned result.

Your browser sends an authenticated request to AppSync. AppSync calls Lambda. Lambda runs the handler, counts the words, and returns a result. This shows server-side code without maintaining a continuously running server yourself. It is ordinary code, not an AI model guessing the count.

Text in the page→Authorized API request→Lambda counts words→Result in the page

Lesson 5

Change a small part and follow the result.

Start with a harmless frontend change. In app/src/main.tsx, change the wording of a learning instruction. Build the frontend locally, review its output, and publish through the selected gated workflow only after the address, identity and cost checks in Lesson 3. Reload the hosted page after an authorized release. The words should change while the saved notes remain.

Next, inspect the backend model. This line means that each Entry must have a title:

title: a.string().required()

a.string() means a text value. required() means the record cannot omit that value. An owner authorization rule follows the model definition. Together, these describe the shape of the record and who may use it.

As a separate experiment, add an optional category: a.string() field to the Entry definition. Review a proposed backend update, add a category input and display to the frontend, then build and publish through the authorized path. Test existing and new records afterward. Older entries will not automatically contain a category, so the page must handle an empty value. Do not begin by removing fields from data you care about.

What you should be able to explain

A frontend wording change needs a new frontend build. A model change needs a backend update and usually a matching frontend change. Keeping those files together helps you review both sides of the behavior.

Lesson 6

Know what stays on after you leave.

Closing the browser does not remove the cloud resources. A conventional database, NAT gateway, or load balancer can keep charging while nobody uses the page. This lab uses serverless services for its core features, but requests, stored files, build work, and data transfer can still cost money.

A budget alert is a warning, not a switch that cuts off all spending. Review AWS Billing and remember that usage reports can arrive later than the activity. Credits can also make a bill look different from the underlying usage charges.

Deleting the Hosting app is not a complete backend cleanup. Terraform owns Hosting; Amplify owns separate backend stacks. The local operating guide explains the deletion order and the checks for retained files, database tables, user pools, logs, and deployment assets.

Before deleting: decide whether the data is disposable. Disposable lab data may be removed after you confirm its owner and retention needs. A future app with valuable data needs a recovery decision before deletion.

When you finish a cleanup, look for the actual remaining resources. An empty Terraform state proves only that Terraform no longer tracks its resources. It does not prove that every other service in the AWS account is empty.
