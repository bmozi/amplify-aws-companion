Make a code change travel through a pipeline

Explain and configure build, deployment, preview isolation, and frontend rollback.

Your outcome

Explain and configure build, deployment, preview isolation, and frontend rollback.

Suggested time: 60–90 minutes. Configuration lab; needs a Git repository connection before cloud execution.

Imagine a recipe card that says exactly how to prepare a meal. A pipeline is a repeatable recipe for turning a source-code revision into a running application. Continuous integration (CI) checks changes together. Continuous delivery or deployment (CD) prepares or publishes a version after those checks.

Reviewed source→Install locked dependencies→Deploy backend→Build page→Test actual behavior

Read the recipe

Open examples/advanced/amplify.yml.example. It is a candidate for a separate Git-connected teaching app, not an active configuration. appRoot: app points to this repository's application folder. npm ci installs the lockfile. pipeline-deploy selects the current branch's backend. The frontend build publishes dist.

Connect a controlled experiment

  1. Create a private source repository rooted at this project, after reviewing the file list. Exclude state, evidence, generated outputs, credentials, and practice work. Commit source and lockfiles.
  2. Copy the example to amplify.yml at repository root and commit it. Ensure the build image supports the Node version required by the lockfile and Python 3 for the lesson builder.
  3. Create a separate Amplify Hosting app connected to that repository, select one learning branch, and set the monorepo root to app. Confirm AMPLIFY_MONOREPO_APP_ROOT=app. Complete Git provider authorization yourself.
  4. Configure its backend deployment service role using the current Amplify setup guidance. Do not place access keys into the YAML.
  5. Record the new app's ID and its ownership: this exercise uses console-managed Hosting, not the existing Terraform Hosting state. Do not import or recreate the original app.
  6. Commit one harmless heading change. Follow the build logs and open the deployed result. Record the source revision, build job, backend identifiers, and visible words.

Try a preview and a rollback

Connect one feature branch in the new app. Check that it has separate backend identifiers before testing. Sharing a backend is a valid deliberate design, but it does not give data isolation. Limit automatic branch matching to intended learning branches; every preview can create resources.

To practice a frontend rollback, revert the heading change in Git and deploy the new revert commit. The earlier text should return while notes remain. A code rollback does not restore deleted data or undo every schema change. Lesson 11 explains how to keep old and new clients compatible.

Cleanup and diagnosis

Disconnect the exercise branch and check its backend stacks and retained resources. Remove the separate teaching app when finished. Do not assume deleting a Git branch removed all AWS resources. A build failure before publication may leave the prior frontend available; inspect the backend separately because an earlier pipeline stage may already have changed it.

Use AI as your engineering partner

Give Codex the relevant source files and sanitized evidence. Ask: “Explain each candidate pipeline stage and propose a failed-test scenario that must stop deployment. Do not deploy or expand permissions.”

Verify: Verify the pipeline actually stops; a green source build is not a deployed pipeline. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.

Evidence to collect

  • Explain every stage in the candidate build file.
  • Record the commit that produced the observed page.
  • Demonstrate preview isolation and a harmless frontend rollback.

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
