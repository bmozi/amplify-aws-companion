Give the app an address and a trusted sign-in route

Connect DNS, HTTPS, and identity redirects without mixing their responsibilities.

Advanced courseFoundation lessonHands-on lab
Your outcome

Connect DNS, HTTPS, and identity redirects without mixing their responsibilities.

Suggested time: 60–90 minutes. Optional exercise; requires a controlled domain and provider registration.

A street address tells a visitor where to go. An ID check tells the building who the visitor is. A custom domain and social sign-in solve those different problems. Changing the website address does not automatically update every sign-in return address.

Part A: a readable address

  1. Choose a subdomain of a domain you control, such as learn.your-domain. Record the current DNS records before editing. DNS is the system that maps names to destinations.
  2. For a separate teaching app, open Amplify Hosting's custom-domain setup. Enter the owned domain, choose the subdomain-to-branch mapping, and inspect the generated validation and routing records.
  3. At the actual DNS provider, add the records AWS supplies. Use the exact values; do not guess a certificate-validation hostname.
  4. Wait for certificate validation and domain availability. Open HTTPS and refresh a deep link such as the course page. Confirm the certificate covers the hostname.

Keep the original Amplify address available during the test. If changing the existing Terraform-owned app, define its domain association in Terraform and review the plan; do not create competing unmanaged configuration. Domain registration and DNS hosting can have charges separate from Amplify.

Part B: let a provider identify the visitor

For social sign-in, the external provider sends the visitor back to Cognito, and Cognito sends them back to your application. These are two distinct redirect steps.

  1. Register a test application with the selected identity provider. Configure its allowed return URI using the actual Cognito domain and provider instructions.
  2. In the practice Amplify auth definition, configure the provider using secrets, plus exact application callback and logout URLs. Keep the provider secret out of browser code and version control.
  3. Deploy, regenerate outputs, and add the documented sign-in redirect action to the practice UI.
  4. Test successful sign-in, cancelled consent, sign-out, and a return to the correct environment. A preview URL needs deliberate redirect handling; do not broadly allow arbitrary destinations.
  5. Confirm a local-email user and a provider user do not unexpectedly gain access to each other's notes. Similar email text alone is not proof that two identities are linked.

Diagnose and undo

A redirect mismatch often means the scheme, hostname, path, port, or trailing slash differs from the registered value. Compare exact strings at each hop. Do not weaken access controls to hide a configuration error.

When finished, remove the teaching domain association and only its exercise DNS records. Disable the test provider client and remove its secrets if no longer used. Leave shared domain records intact. Domain renewal is a separate lifecycle; deleting an app does not cancel a registration.

Use AI as your engineering partner

Give Codex the relevant source files and sanitized evidence. Ask: “Explain the DNS and sign-in redirect path and identify settings that must match exactly. Do not deploy or expand permissions.”

Verify: Inspect real DNS, certificate and redirect behavior; do not expose credentials while debugging. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.

Evidence to collect

  • Explain DNS routing versus certificate validation.
  • Trace both sign-in redirect hops.
  • Test cancellation and sign-out as well as successful sign-in.

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
