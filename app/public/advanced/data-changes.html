Your outcome

Make an additive schema change, support older records, and test access as well as appearance.

Suggested time: 45–60 minutes. Sandbox coding exercise; requires Lesson 9 backend.

A teacher adds a Category column to an existing notebook. The old pages still exist, but nobody has filled in that new column. A database schema change has the same problem: new code must cope with old records.

Use the practice copy from Lesson 9. Save an entry before changing anything. Then edit practice/advanced/amplify/data/resource.ts, adding this field inside the existing Entry model. Preserve its other fields and owner rule:

category: a.string(),

This makes category optional. Deploy the sandbox again with Lesson 9's one-shot command. Restart the local app after deployment. Confirm the old entry still loads before changing the UI.

Teach both sides about the field

  1. In the practice src/main.tsx, find the create and update calls for client.models.Entry.
  2. Add a text input and React state for category. Pass the value with each create/update. When opening Edit, initialize it with entry.category ?? ''.
  3. Display entry.category || 'Uncategorized' beside the title. That fallback is a display choice, not a database backfill.
  4. Run npm run build --prefix practice/advanced to catch mismatches between the model and client code.
  5. Test the old uncategorized entry, a new categorized entry, and an edit followed by refresh. Use a second user to repeat the denial checks.

Understand expand, migrate, contract

Expand means add a compatible field or API. Migrate means deliberately move old data and clients to the new representation. Contract means remove the old representation only after it is no longer needed. A rename can behave like removing one field and adding another; it is not automatically a safe data migration.

For this small exercise, edit three old entries manually to assign categories. For a larger collection, plan a migration that handles pagination, records what it changed, retries safely, and can be checked against a before-count. Do not run an unbounded script that assumes the first page contains every record.

Failure exercise

Before any deployment, predict what would happen if category became required while older clients omitted it. Write the answer: those creates can fail. Keep the optional field for this lesson. The important engineering skill is recognizing compatibility before a real user experiences the failure.

Undo and cost

Revert the UI to stop displaying category; the optional backend field can remain while you decide whether its data matters. Only remove it after a deliberate data decision. Delete the disposable sandbox using Lesson 9 when the exercise is finished. Normal database and deployment usage still applies.

Use AI as your engineering partner

Give Codex the relevant source files and sanitized evidence. Ask: “Propose an additive schema change and a test using an older record. Explain rollback limits. Do not deploy or expand permissions.”

Verify: Run old/new record tests and inspect retained data; do not assume rollback restores deleted information. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.

Evidence to collect

  • Old records render without a category.
  • New records retain category after refresh.
  • A second user is still denied access.
  • Explain why frontend rollback and data restoration differ.

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
