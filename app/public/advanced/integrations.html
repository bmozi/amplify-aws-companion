Choose maps, messages, and APIs for a real need

Choose an integration by its required behavior and current service lifecycle.

Your outcome

Choose an integration by its required behavior and current service lifecycle.

Suggested time: 45–60 minutes. Architecture exercise with optional service-specific implementation.

Suppose a field worker records a note at a site, then asks a teammate to review it. A map may help locate the site; a notification may help reach the teammate. Neither feature is useful just because it appears in a service menu.

Maps: begin with a public place

Use the linked Amplify Geo guide to select the currently supported Amazon Location integration. Start with a fixed public landmark, not a person's home or live position. Define the map/search resources and their allowed use, then connect the client configuration. Do not assume our existing outputs contain Geo resources.

  1. Write the exact interaction: enter a public place name, show a result, choose it, save a place reference with the note.
  2. Keep permissions limited to required map/search operations and resources. Decide whether anonymous use is intentional before granting it.
  3. Test a valid query, no results, service denial, and the user declining location permission. A fixed-place search should not require device-location access.
  4. Record request volume and retention decisions; remove exercise resources and stored test locations when finished.

Messages: consent and delivery are separate tests

Choose email, SMS, or push because it fits the user. Record who requested the message, who receives it, how consent is represented, and how they stop receiving it. Keep delivery credentials server-side. A successful API call means the service accepted a request; it does not prove the person received or read the message.

Lifecycle checkpoint: AWS lists Amazon Pinpoint end of support as October 30, 2026. This course therefore does not build a new Pinpoint campaigns/analytics dependency. AWS End User Messaging covers continuing messaging channels, while the right analytics/event pipeline depends on your requirements. Consult the current migration guidance before copying an older Amplify tutorial.

Connect another API deliberately

For a third-party service, draw browser → authenticated backend action → external API. Define the request and response fields, timeout, retry rules, and what the user sees if the provider is down. A secret in a frontend environment variable can end up in downloaded JavaScript; putting it in a file named “env” does not make it private.

Write a contract table with four cases: normal result, invalid input, denied access, and provider timeout. Test those cases with a local stub before connecting a paid endpoint. If retries could repeat an external action, apply Lesson 13's idempotency reasoning.

Analytics without collecting everything

Choose one question, such as “how often do note saves fail?” Define a minimal event containing operation, outcome, time, and a non-sensitive correlation ID. Do not include note text or tokens. Aggregate outcomes and choose a retention period. Compare that event count with controlled test attempts before using it as a business metric.

Deliverable and cleanup

Produce a one-page integration decision: user need, selected service, alternative rejected with reason, resource owner, consent, failure behavior, cost unit, and removal steps. This lesson creates a concrete design; it does not claim those optional services are already deployed.

Use AI as your engineering partner

Give Codex the relevant source files and sanitized evidence. Ask: “Compare two integration choices against a concrete need, including lifecycle, data movement and cost. Do not deploy or expand permissions.”

Verify: Check current primary documentation and measure one real behavior before expanding scope. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.

Evidence to collect

  • Choose one integration and define four observable outcomes.
  • Separate accepted message requests from actual delivery.
  • Explain why a legacy tutorial may need a different service today.

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
