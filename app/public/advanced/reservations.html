Use a conditional transaction to enforce capacity and preserve a successful retry.

Suggested time: 45–75 minutes. Runnable local emulation; live contention check prepared, not yet executed.

Two people see one seat

Alice and Bob both open an enrollment page showing one place left. If the app reads the count and later writes the reservation, both can believe they won. The business rule is that confirmed seats cannot exceed capacity.

Alice + Bob → Condition: a seat remains → Decrement + reservation together → One winner

Put the rule where the change happens

The capacity condition belongs inside the write transaction. The count decreases only when a reservation is created. A reservation key combines course and actor; retrying a successful reservation returns the existing result without taking another seat.

Predict and test

If the reservation write fails, should the count change? No. Run the local tests in architectures/reliable-workflows/. Inspect the successful retry and sold-out assertions, and confirm no losing reservation was created. The local emulator checks behavior but does not prove real concurrent contention.

.venv-labs/bin/python architectures/reliable-workflows/tests/test_domain.py DomainTests.test_last_seat_and_idempotent_retry -v

After a reviewed budget and deployment, the separate live harness invokes two real Lambda requests concurrently and checks for one winner and a zero remaining count. Do not claim that result until the harness actually passes.

How this differs from a repair request

Repair work can wait in a queue. A confirmed seat must obey capacity at the instant the transaction commits. The reusable foundation is reliable state change; the business invariant decides the condition. This lab confirms immediately and implements no payment, expiration, cancellation or waitlist.

Use AI as your engineering partner

Ask Codex: “Draw the two-caller timeline for a broken read-then-write design. Explain why the condition and both writes must be atomic. Propose a cancellation test without implementing it.” Verify the code and tests. Challenge the answer with repeated cancellation; returning a seat twice would violate the rule.

Independent challenge

Add cancellation in a practice branch. A repeated cancellation must not return another seat, and a failed cancellation must not change capacity. Explain why delayed TTL deletion is insufficient to enforce an exact hold deadline. End with teardown and an evidence record.

Evidence to collect

  • One successful retry does not consume extra capacity
  • A sold-out response creates no reservation
  • A real concurrent race result only if live verification was performed
  • A design for duplicate-safe cancellation and explicit limits
