Handle a job that arrives twice

Explain duplicate delivery, bounded retries, and why durable state matters.

Advanced courseFoundation lessonHands-on lab
Your outcome

Explain duplicate delivery, bounded retries, and why durable state matters.

Suggested time: 30–45 minutes. Runnable local simulation; cloud design extension is optional.

You press an elevator button twice. You want one ride, not two elevators charged to your account. A cloud worker may receive the same job again when a network response is lost or a previous attempt fails. Idempotency means repeating a request has the intended effect once.

Run the included exercise from the project root. It makes no network requests:

node examples/advanced/retry-lab.mjs

Open the file. The same job ID is delivered twice, but a receipt stored in a Map prevents the second effect. A failing job gets three attempts and then goes to a separate list. The assertions check those outcomes. Change the duplicate job's ID and predict why it now counts as a different job.

What the simulation leaves out

The Map disappears when the process exits. Two workers could both see “not done” before either saves a receipt. A real design needs durable storage and atomic coordination: a check-and-write that cannot be interrupted by a competing worker. If the external side effect is a payment, recording a receipt before or after the payment still leaves failure windows. Use the provider's idempotency support or a suitable transaction/outbox design; this small example is not a payment processor.

Translate the idea to AWS

Amazon SQS can hold jobs while Lambda workers process them. Delivery can repeat. A dead-letter queue holds repeatedly failing messages for investigation. It is not an automatic repair service. With batches, partial-batch failure reporting can prevent successful records from being retried with failed ones.

  1. Draw: authenticated request → queue → worker → result store. Name the job ID and the owner attached to each job.
  2. Write down who may send messages, who may consume them, and how users may read only their own results.
  3. Define maximum attempts, processing timeout, queue visibility timeout, and where exhausted jobs go. Visibility timeout is the period a received message is hidden from other consumers; choose it using the actual worker timeout and AWS guidance.
  4. Before deploying this extension, add the queue and worker under one infrastructure owner, not ad hoc console resources beside an undocumented handler.
  5. Test duplicate delivery, a temporary failure, a permanent failure, and worker restart. Verify effects and queue state, not just log lines.

Cost and cleanup

The supplied simulation costs no AWS usage. A deployed queue extension adds requests, function execution, logs, and retained messages. Stop producers before deleting disposable queues; otherwise work may keep arriving. Record whether unprocessed work is intentionally discarded.

Use AI as your engineering partner

Verify: Run the counterexample; the local Map example is not a distributed correctness proof. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.
