Follow a request when something goes wrong

Trace a request across browser, API, and Lambda; separate symptoms from causes.

Advanced courseFoundation lessonHands-on lab
Your outcome

Trace a request across browser, API, and Lambda; separate symptoms from causes.

Suggested time: 45–60 minutes. Existing-lab inspection; fault injection belongs in the sandbox.

A package does not arrive. “Delivery failed” is a symptom. To find the cause, you trace the parcel through each handoff. A cloud request also moves through handoffs: the browser, an API, a function, and sometimes a database or another service.

Logs describe events. Metrics count or measure them over time. An alarm watches a metric for a condition. Together they help you investigate, but a green deployment indicator does not prove that people can use the app.

Trace one successful request

  1. Open Functions in the lab. Note the current time and submit “one two three.”
  2. Open browser developer tools → Network. Find the AppSync request and inspect its GraphQL response. Do not copy authorization headers into your notes.
  3. In AWS Lambda, locate the inspector function through the Amplify stack's resources. Open Monitor → CloudWatch logs. Use a narrow time range around your request.
  4. Match timestamps and available request identifiers. A browser request ID and Lambda invocation ID are not necessarily the same. Say when correlation is based only on time.

In CloudWatch Logs Insights, select only that log group and a short time range. Run this query; query scanning can incur charges:

fields @timestamp, @message
| sort @timestamp desc
| limit 30

Create a bounded failure in practice

In the sandbox inspector handler, temporarily reject a recognizable value such as FAIL_FOR_LESSON. Deploy the sandbox, invoke it once, and inspect both the UI and response. GraphQL can return an HTTP 200 response containing an errors array, so an HTTP status alone is not your success test.

Then remove the injected rejection, deploy, and repeat the same request. Record symptom, evidence, cause, fix, and successful retest. Never log full private notes or access tokens just to make debugging easier.

Choose a useful alarm

In the practice function's metrics, compare Invocations, Errors, Duration, and Throttles. Design an alarm such as “at least one error during a five-minute practice window.” Select a notification destination you control and confirm its subscription when appropriate. A configured alarm without delivered notification has not tested the whole path. Remove the temporary alarm and destination after the exercise, or manage them in infrastructure code if retained.

Make a small service promise

A service-level objective (SLO) is a measurable target. Write one for this lab: “at least 99 of 100 controlled note-save attempts return a saved record within our chosen time limit.” Define the test window and what counts as failure. This is a proposed target, not a measured claim about the deployed lab.

The frontend works but saves fail

Check app sign-in, API response errors, backend identifiers, function logs, and permissions in that order as evidence directs. An available static page and a working data service are separate observations.

Use AI as your engineering partner

Give Codex the relevant source files and sanitized evidence. Ask: “Given redacted logs and a request identifier, list competing failure hypotheses and the observation that distinguishes them. Do not deploy or expand permissions.”

Verify: Reproduce the cause; do not treat the first plausible explanation as a diagnosis. Explain the result in your own words and name one condition that would change it. Set a spending and action boundary before permitting cloud work.

Evidence to collect

  • Trace one successful invocation with timestamps.
  • Capture an intentional failure and a successful retest in practice.
  • Distinguish HTTP success from application success.

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
