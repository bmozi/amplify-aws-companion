Suggested time: 60–90 minutes. Runnable local emulation; live AWS harness prepared, deployment pending budget.

The customer pressed Submit twice

A heater needs repair. The customer needs to know the request was accepted, even if scheduling is temporarily unavailable. “Accepted” and “finished” are different states.

Intake → Request + outbox → Dispatcher → Queue → Worker → Appointment + DONE

An outbox is a durable reminder that work still needs sending. A transaction commits related changes together. The dispatcher sends before marking the reminder sent. A failure in between can send twice; the worker must tolerate that.

Predict the failure

If we marked the reminder sent first and then the send failed, who would know to retry? If we sent twice, what prevents two appointments? Write your prediction before reading the implementation.

Run the example

Open architectures/reliable-workflows/README.md in the private companion repo. Install its recorded development dependencies and run:

.venv-labs/bin/python -m unittest discover -s architectures/reliable-workflows/tests -v

Read src/domain.py beside test_domain.py. The dispatch-crash test fails after sending but before acknowledgement, then retries. Inspect that one appointment exists and the request is DONE. The dependency-failure test leaves the request accepted until recovery. The batch test reports only the bad message.

Move to AWS deliberately

Complete Lesson 18 first. The README includes Terraform plan/apply commands and a bounded live verification harness. It uses a separate private IAM-invoked stack; synthetic actor labels are not customer authentication. Real queue timing, IAM and contention require live evidence.

The important limit

The appointment is simulated inside the same database transaction. A real scheduling provider is outside that transaction and needs its own duplicate-prevention or reconciliation agreement. Dispatch is manual; nothing drains the outbox until invoked. This is a small teaching implementation, not a production scheduler.

Use AI as your engineering partner

Ask Codex to identify the exact crash windows and propose a counterexample for each. Verify that effect and completion commit together. Ask how the answer changes for an external payment provider. Do not accept “exactly once” without stating the boundary where that claim holds.

Independent challenge and cleanup

Design recovery when an external provider succeeds but the worker loses its response. Identify the evidence needed before retrying. Remove the practice stack, verify the named resources are absent and record remaining uncertainty.

Evidence to collect

  • Predicted and observed state for the send/ack failure
  • One durable simulated appointment after replay
  • Failed dependency leaves recoverable work
  • Explicit distinction between emulated tests and live AWS evidence
  • A teardown record for any live run

Use the source bundle’s examples/advanced/evidence-template.json. Keep credentials and private data out of shared results.
